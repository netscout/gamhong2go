## Section 0: Background -- What 280x192 Hi-Res Graphics Was on the Apple II+

### What It Is

The Apple II+ "HGR" mode is what BASIC enters when you type `HGR`. The user sees a 280-column by 192-row pixel grid. Each pixel is one of effectively six colors -- Black, White, and four artifact pairs (Green/Purple from bit 7=0, Orange/Blue from bit 7=1). The grid is backed by a dedicated 8 KB frame buffer at `$2000`-`$3FFF` (page 1) or `$4000`-`$5FFF` (page 2), separate from the 1 KB text/lo-res buffer.

Each byte of that frame buffer encodes 7 horizontal pixels via bits 0..6, with bit 7 reserved as a per-byte palette selector. The 192 scanlines are stored in a scrambled (non-row-major) order, decoded by `hiResLineAddr` (§3).

The rendering entry point is `RenderHiRes(page2, mixed bool)` at `video/hires.go:60`. The file's opening comment at `video/hires.go:3-9` summarizes the layout: page 1 at `$2000`-`$3FFF`, page 2 at `$4000`-`$5FFF`, each byte controlling 7 pixels (bit 0 = leftmost), bit 7 as palette select.

### Why It Matters

Hi-res sits at the top of the Apple II+ mode taxonomy:

```text
  textMode=true               -> text       (40x24 chars)
  textMode=false, hiRes=false -> lo-res     (40x48 color blocks)
  textMode=false, hiRes=true  -> hi-res     (280x192 pixels)  <-- this doc
  [mixedMode is a modifier bit, not a fourth case; honored inside lo-res/hi-res branches]
```

The dispatch lives in `Render()` at `video/video.go:44-51` (covered in `08.walkthrough_video.md` §7). Hi-res is the `case hiRes:` branch -- it fires when `textMode=false` and `hiRes=true`. At power-on, `TextMode=true` (`io/softswitches.go:56`); `HiRes` zero-values to `false`. Hi-res is reached by a software sequence of `LDA $C050` (clear TextMode) then `LDA $C057` (set HiRes).

Color is a hardware accident-turned-feature: the Apple II+'s 14 MHz dot clock beat against the 3.58 MHz NTSC colorburst in a way that made adjacent on-bits produce different chroma. Wozniak exploited this deliberately -- bit 7 shifts the entire 7-pixel run by half a dot-clock, swapping the artifact palette pair. The emulator approximates this with a 2x4 RGB lookup table (`hiResColors` at `video/hires.go:41-56`) and a per-pixel neighbor-lookup heuristic in `renderHiResLine`.

## Section 1: The 8 KB Hi-Res Frame -- 192 Rows of 40 Bytes Each

### What It Is

Hi-res allocates its own 8 KB frame buffer -- distinct from text/lo-res's 1 KB at `$0400`-`$07FF`. The file-comment at `video/hires.go:3-9` declares: "Page 1: `$2000`-`$3FFF` (8 KB)" and "Page 2: `$4000`-`$5FFF` (8 KB)." Within a page, 192 scanlines of 40 bytes each are stored in scrambled (non-sequential) address order decoded by `hiResLineAddr` (§3).

**Diagram 1: 280x192 frame layout**

```text
  Hi-res page 1: $2000-$3FFF (8,192 bytes; 7,680 used, 512 holes)
  Hi-res page 2: $4000-$5FFF (same structure, base shifted by $2000)

  280 pixels wide (= 40 bytes x 7 pixels)
  +--------+--------+--------+ ... +--------+
  | byte 0 | byte 1 | byte 2 |     |byte 39 |   scanline   0  ($2000)
  +--------+--------+--------+ ... +--------+
  | byte 0 | byte 1 | byte 2 |     |byte 39 |   scanline   1  ($2400)
  +--------+--------+--------+ ... +--------+
  | byte 0 | byte 1 | byte 2 |     |byte 39 |   scanline   2  ($2800)
  +--------+--------+--------+ ... +--------+
                       ...                          (192 rows total,
                                                    address scramble
                                                    detailed in §3)
  +--------+--------+--------+ ... +--------+
  | byte 0 | byte 1 | byte 2 |     |byte 39 |   scanline 191  ($3FD0)
  +--------+--------+--------+ ... +--------+
                                               192 scanlines tall

  Each "byte N" holds 7 pixel bits + 1 palette-shift bit (see §2).
```

### Why It Matters

The frame numbers reveal the scale jump over lo-res:
- 40 bytes per row x 7 pixels = **280 visible pixels per scanline** (vs. 40 blocks in lo-res).
- 192 scanlines x 40 bytes = **7,680 bytes used per page** (vs. 960 bytes for lo-res in the text buffer).
- 192 scanlines x 280 pixels = **53,760 pixel writes per frame** -- the same `v.Pixels` slice as lo-res and text, just fully populated.
- 8,192 bytes - 7,680 used = **512 "hole" bytes** per page that `hiResLineAddr` never returns for line 0..191.

### How the Code Works

The `RenderHiRes` signature at `video/hires.go:60` is:

```go
func (v *Video) RenderHiRes(page2, mixed bool)
```

Its outer loop (covered in §6) iterates `line := 0..maxLine-1`, calling `hiResLineAddr(line, page2)` to get the RAM address for each scanline (`video/hires.go:66-69`). The inner per-byte loop at `video/hires.go:78-80` fetches:

```go
b := v.RAM[addr+uint16(col)]
```

This is a direct read into the same 64 KB slice the CPU writes (`video/video.go:21`: "Direct reference to main RAM"). No copy, no double-buffering. Software mutations between `Render` calls are visible in the next frame (same contract as lo-res, doc 16 §1).

The two pages share identical internal structure; `hiResLineAddr` at `video/hires.go:22-26` selects the base (`$2000` or `$4000`) from the `page2` parameter.

### Real-World Analogy

A film reel where each frame is 192 strips of 40 dots. The two reels (page 1 and page 2) sit on adjacent spindles; the projector picks one with a single switch. Within either reel, the strips are loaded out of order on purpose -- decoded by `hiResLineAddr` (§3).

## Section 2: The Hi-Res Byte -- 7 Pixels Plus 1 Palette-Shift Bit

### What It Is

Each byte in the hi-res frame buffer controls a 7-pixel horizontal run. The file comment at `video/hires.go:7-9` states the layout directly:

- Bits 0..6: pixel data (bit 0 = leftmost)
- Bit 7: palette select (shifts colors by half a pixel)

The unpack at `video/hires.go:81-82` extracts both fields:

```go
palette := int((b >> 7) & 1)
pixels := b & 0x7F
```

The bit loop at `video/hires.go:84-85` walks bits left-to-right:

```go
for bit := 0; bit < 7; bit++ {
    px := col*7 + bit
```

`bit=0` maps to the leftmost pixel of the run; `bit=6` maps to the rightmost. Bit 7 is never visited as `thisPixel` -- the loop condition is `bit < 7`.

### Why It Matters

Bit 7 is the key insight of hi-res. Reserving 1 bit per 7 doubles the effective color count at the cost of one bit per byte. On real hardware, bit 7 triggered a half-dot-clock phase shift in the video shift register, swapping which chroma the NTSC colorburst assigned to each parity position. In the emulator, `hiResColors[palette]` approximates this by swapping the entire color pair without performing an actual geometric shift (see §4 and §8 Q4).

**Diagram 2: one-byte expansion (byte $AB = 0b_1010_1011)**

```text
  One hi-res byte at RAM[$2000+col]    On-screen 7-pixel run
                                       (col=0 example, x=0..6)

    bit  7 6 5 4 3 2 1 0                  px:  0 1 2 3 4 5 6
    val  1 0 1 0 1 0 1 1  = $AB                | | | | | | |
         |  \-----+-----/                      v v v v v v v
         |        bits 0-6                    on on off on off on off
         |        = pixel data
         |        (bit 0 = leftmost)         palette = 1 (bit 7=1)
         |                                   -> Orange/Blue pair
         palette select bit
         (1 = Orange/Blue palette)

  Per-pixel walk in renderHiResLine (hires.go:84-115):
    px=0 (bit 0 = 1): "on"  -> check right neighbor (bit 1 = 1)
                               right neighbor on -> WHITE
    px=1 (bit 1 = 1): "on"  -> check right neighbor (bit 2 = 0)
                               right off; px%2=1 (odd) -> ORANGE (palette 1)
                               check left neighbor (bit 0 = 1) -> upgrade WHITE
    px=2 (bit 2 = 0): "off" -> BLACK
    px=3 (bit 3 = 1): "on"  -> neighbors off -> px%2=1 (odd) -> ORANGE
    px=4 (bit 4 = 0): "off" -> BLACK
    px=5 (bit 5 = 1): "on"  -> neighbors off -> px%2=1 (odd) -> ORANGE
    px=6 (bit 6 = 0): "off" -> BLACK
```

### How the Code Works

The `pixels` mask (`b & 0x7F`) strips the palette bit so the bit loop sees only the 7 pixel bits. The `palette` index (0 or 1) is held constant for the entire 7-bit run of one byte. Within the run, each `thisPixel` is tested with `(pixels >> uint(bit)) & 1` at `video/hires.go:90`. Color selection is explained in full in §4.

### Real-World Analogy

A 7-bit barcode glyph stamped onto a slide. The whole slide can be rotated 180 degrees by flipping a tiny "phase" notch (bit 7) on the corner. Rotation does not move any bar on the barcode -- it just changes which color the projector light interprets each bar as.

## Section 3: The 192-Row Address Scramble (Distinct From the 24-Row Text Scramble)

### What It Is

Hi-res scanlines are NOT stored sequentially in RAM. Line 0 is at `$2000`, but line 1 is at `$2400` (not `$2028`), and line 8 is at `$2080` (not `$2400`). The mapping is computed by `hiResLineAddr` at `video/hires.go:22-35`:

```go
func hiResLineAddr(line int, page2 bool) uint16 {
    base := uint16(0x2000)
    if page2 {
        base = 0x4000
    }
    section := line / 64
    group := (line % 64) / 8
    row := line % 8
    return base + uint16(row)*0x0400 + uint16(group)*0x0080 + uint16(section)*0x0028
}
```

**Diagram 3: formula and 8-row sample table**

```text
  hiResLineAddr(line, page2) = base + (line%8)*$400
                                    + ((line%64)/8)*$80
                                    + (line/64)*$28
  where base = $2000 if page2=false, $4000 if page2=true.

  Sample addresses (page 1, base = $2000):

  line  row  group  section   formula                       addr
  ----  ---  -----  -------   ---------------------------   -----
     0    0     0      0      $2000+0+0+0                   $2000
     1    1     0      0      $2000+$400+0+0                $2400
     7    7     0      0      $2000+$1C00+0+0               $3C00
     8    0     1      0      $2000+0+$80+0                 $2080
    64    0     0      1      $2000+0+0+$28                 $2028
    65    1     0      1      $2000+$400+0+$28              $2428
   128    0     0      2      $2000+0+0+$50                 $2050
   191    7     7      2      $2000+$1C00+$380+$50          $3FD0

  Verified by TestHiResLineAddresses (video/video_test.go:77-99).
  The full 192-row table is not reprinted; the formula plus this
  sample is sufficient. (Compare to doc 16 §4, which similarly
  defers the full 24-row text-scramble table to 08.walkthrough_video.md
  §5 / 06.walkthrough_main_phase3.md §4.)

  NOTE: the doc-comment at video/hires.go:14-19 disagrees with the
  formula. The comment shows "Line 1 -> $2080" but the formula at
  hires.go:31-34 and the test at video_test.go:80-91 both give
  Line 1 -> $2400 and Line 8 -> $2080. The formula and test are
  authoritative. See §8 Q5 for discussion.
```

### Why It Matters

The scramble exists for the same hardware-wiring reason as the 24-row text scramble (see `06.walkthrough_main_phase3.md` §4 and `08.walkthrough_video.md` §5 for the full hardware story). Hi-res extends the trick to 192 lines by adding a third address-bit dimension. The key contrast:

- **Text scramble** (`video/video.go:115-117`): `0x0400 + uint16(row%8)*0x80 + uint16(row/8)*0x28` -- two components, 24 rows.
- **Hi-res scramble** (`video/hires.go:31-34`): `base + (line%8)*$400 + ((line%64)/8)*$80 + (line/64)*$28` -- three components, 192 rows.

The three components are independent weights: `row` contributes `row*$400` (cycling 0-7), `group` contributes `group*$80` (cycling 0-7), and `section` contributes `section*$28` (cycling 0-2). Together they span 8 x 8 x 3 = 192 unique scanlines.

Worked example: line 65.
- `section = 65 / 64 = 1` -> `1 * $28 = $28`
- `group = (65 % 64) / 8 = 1 / 8 = 0` -> `0 * $80 = $00`
- `row = 65 % 8 = 1` -> `1 * $400 = $400`
- Total: `$2000 + $400 + $00 + $28 = $2428`.

### How the Code Works

The function at `video/hires.go:22-35` is called once per scanline from the outer loop (`video/hires.go:67`). No table lookup -- the formula runs live, the same style as `textLineAddr`. Note: the doc-comment table at `video/hires.go:14-19` uses the text-mode stride convention by mistake (treats `line+=1` as the $80 stride rather than the $400 stride), giving wrong addresses for three of the four shown rows. The formula at `video/hires.go:31-34` and the test at `video/video_test.go:77-99` are authoritative; this walkthrough uses them. See §8 Q5.

### Real-World Analogy

The same 7-digit ZIP+4 trick `textLineAddr` uses, but with a "country code" added in front. Text mode mails to one postcode; hi-res mails to a postcode-with-country, where the country field cycles 0/1/2 and stretches the address space by 8x. Same mailroom wiring trick, scaled up.

## Section 4: The Headline Exhibit -- NTSC Color Artifacting From a Monochrome Bit Grid

### What It Is

Each on-bit in the 7-bit pixel field does not simply light a single fixed color. Its color depends on: (a) whether bit 7 is set (palette 0 or 1), (b) whether the pixel sits at an even or odd global column index (`px % 2`), and (c) whether either of its immediate neighbors (left and right within the row) are also on. These three factors reduce to four color indices per palette, stored in the `hiResColors` table at `video/hires.go:41-56`:

```go
var hiResColors = [2][4][3]uint8{
    // Palette 0 (bit 7 = 0): Black, Green, Purple, White
    {
        {0, 0, 0},       // 00 = black
        {17, 221, 0},    // 01 = green (odd pixel lit)
        {221, 34, 221},  // 10 = purple (even pixel lit)
        {255, 255, 255}, // 11 = white
    },
    // Palette 1 (bit 7 = 1): Black, Orange, Blue, White
    {
        {0, 0, 0},       // 00 = black
        {255, 102, 0},   // 01 = orange (odd pixel lit)
        {34, 34, 255},   // 10 = blue (even pixel lit)
        {255, 255, 255}, // 11 = white
    },
}
```

**Diagram 4: palette truth table (RGB triples verbatim from hires.go:42-55)**

```text
  palette=0 (bit 7 = 0)              palette=1 (bit 7 = 1)
  --------------------------         --------------------------
  colorIdx 0 = Black     0,0,0       colorIdx 0 = Black     0,0,0
  colorIdx 1 = Green   17,221,0      colorIdx 1 = Orange 255,102,0
  colorIdx 2 = Purple 221,34,221     colorIdx 2 = Blue    34,34,255
  colorIdx 3 = White  255,255,255    colorIdx 3 = White  255,255,255

  Bit-pattern reveal table (per 7-pixel byte; assume boundary
  neighbors are off for this table):

  bit7  bits0..6   pixels                 result
  ----  ---------  ---------------------  -------------------
   0    0000000    all off                all Black
   0    1111111    all on (each has a     all White
                   lit neighbor)
   0    1010101    px 0,2,4,6 on,         all Purple (even-column)
                   isolated (no neighbor)
   0    0101010    px 1,3,5 on,           all Green  (odd-column)
                   isolated
   1    1010101    same as above          all Blue   (even-column)
   1    0101010    same as above          all Orange (odd-column)
```

### Why It Matters

This is the "color from monochrome bits" trick. On a real Apple II+ composite video output, the 14 MHz dot clock produced chroma by beating against the 3.58 MHz NTSC subcarrier. Adjacent on-bits at the right phase offset produced white; isolated on-bits at even-clock offsets produced one chroma; isolated on-bits at odd-clock offsets produced the complementary chroma. Bit 7 shifted the phase of the entire 7-pixel run by half a dot-clock, swapping which chroma appeared at each parity.

The emulator does not simulate colorburst phase. Instead, it maps the observable pattern to a lookup table: `hiResColors[palette][colorIdx]`. The `palette` index captures bit 7's effect; `colorIdx` captures whether the pixel is off (0), isolated-odd (1), isolated-even (2), or paired-with-neighbor (3).

> The "color from monochrome bits" rule reduces to four cases:
> (a) bit off -> Black;
> (b) bit on, both neighbors off, even column -> Purple/Blue;
> (c) bit on, both neighbors off, odd column -> Green/Orange;
> (d) bit on, at least one neighbor on -> White.
> Bit 7 of the BYTE picks Purple/Green vs. Blue/Orange (the palette
> swap). The emulator implements all four cases by indexing
> `hiResColors[palette][colorIdx]`; the colorIdx is computed in the
> two-pass neighbor scan at `video/hires.go:99-130`. There is no
> half-pixel geometric shift in the framebuffer -- bit 7 only swaps
> the palette pair, not the pixel position.

### How the Code Works

`renderHiResLine` at `video/hires.go:78-140` runs the per-pixel decision in two passes.

**Pass 1 -- right-neighbor check** (`video/hires.go:99-115`):

1. If `thisPixel == 0`: `colorIdx = 0` (Black). Done for this pixel.
2. Else, look right: if `bit < 6`, right-neighbor = `(pixels >> uint(bit+1)) & 1` (within same byte). If `bit == 6` and `col < 39`, right-neighbor = `v.RAM[addr+uint16(col+1)] & 1` (next byte's bit 0). Otherwise 0.
3. If right-neighbor is on: `colorIdx = 3` (White).
4. Else if `px % 2 == 0`: `colorIdx = 2` (Purple/Blue, even column).
5. Else: `colorIdx = 1` (Green/Orange, odd column).

**Pass 2 -- left-neighbor check** (`video/hires.go:118-130`):

6. If `thisPixel == 1` AND `colorIdx != 3` (not yet white): look left. If `bit > 0`, left-neighbor = `(pixels >> uint(bit-1)) & 1`. If `bit == 0` and `col > 0`, left-neighbor = `(v.RAM[addr+uint16(col-1)] >> 6) & 1` (previous byte's bit 6). If left-neighbor is on: upgrade `colorIdx` to 3 (White).

**Pixel write** (`video/hires.go:132-137`):

```go
color := hiResColors[palette][colorIdx]
offset := (line*ScreenW + px) * 4
v.Pixels[offset+0] = color[0]
v.Pixels[offset+1] = color[1]
v.Pixels[offset+2] = color[2]
v.Pixels[offset+3] = 0xFF
```

**Diagram 5: per-pixel decision flowchart**

```text
  for each bit in 0..6:
    px = col*7 + bit
    thisPixel = (pixels >> bit) & 1     (hires.go:90)

    if thisPixel == 0:
        colorIdx = 0                # BLACK (hires.go:96-97)
    else:
        # Pass 1: check right neighbor (hires.go:99-115)
        right_neighbor = (in-byte)   (pixels >> (bit+1)) & 1   if bit < 6
                       | (cross-byte) RAM[addr+col+1] & 1       if bit==6 and col<39
                       | 0                                       otherwise
        if right_neighbor == 1:
            colorIdx = 3            # WHITE
        elif px % 2 == 0:
            colorIdx = 2            # even -> Purple or Blue
        else:
            colorIdx = 1            # odd  -> Green or Orange

        # Pass 2: also check left neighbor (hires.go:118-130)
        if colorIdx != 3:
            left_neighbor = (in-byte)   (pixels >> (bit-1)) & 1   if bit > 0
                          | (cross-byte) (RAM[addr+col-1] >> 6) & 1 if bit==0 and col>0
                          | 0                                        otherwise
            if left_neighbor == 1:
                colorIdx = 3        # WHITE (upgrade)

    color = hiResColors[palette][colorIdx]
    write color + 0xFF alpha to v.Pixels[(line*ScreenW + px)*4]
```

Two neighbor passes are written separately because the first pass does double duty: it detects right-neighbor white AND assigns the parity-based fallback color. The second pass only needs to override-to-white. Cross-byte reads use bit 0 of the next byte (right side) and bit 6 of the previous byte (left side), consistent with the "bit 0 = leftmost" convention. The palette of the neighboring byte is NOT consulted -- each byte's palette applies only to its own 7-pixel run (see §8 Q3 for the hardware-discontinuity consequence).

The column-parity check uses `px % 2` where `px = col*7 + bit`. For `col=0`, this equals `bit % 2`; for `col=1`, `px = 7 + bit`, so even/odd parity is flipped. The truth table in Diagram 4 uses byte-bit-position parity (assuming `col=0`); full-row behavior depends on the starting column.

### Real-World Analogy

A row of seven light bulbs over a half-mirrored stage. Each bulb is on or off; the half-mirror's tilt (bit 7) decides whether reflections look greenish or orangish. When two adjacent bulbs are on, their reflections add up to white regardless of tilt. When a single bulb is on, its reflection is one of two colors depending on whether it sits at an even or odd seat in the row -- and the tilt picks which color of that pair.

## Section 5: Page 1 vs Page 2 -- The Threading That Lo-Res Lacks

### What It Is

`RenderHiRes` accepts a `page2 bool` parameter at `video/hires.go:60` and threads it all the way down to `hiResLineAddr`. This is the critical asymmetry `16.walkthrough_video_lores.md` §5 flagged: lo-res drops the `Page2` softswitch; hi-res honors it.

The full data path:

1. Hardware: CPU reads `$C055` -> `io/softswitches.go:91-96` (`$C054` clears Page2, `$C055` sets it): `s.Page2 = true`.
2. Main loop: `vid.Render(sw.TextMode, sw.MixedMode, sw.HiRes, sw.Page2)` at `main.go:374`.
3. Dispatcher: `video/video.go:48`: `v.RenderHiRes(page2, mixedMode)` (page2 = first arg).
4. `RenderHiRes`: `video/hires.go:67`: `addr := hiResLineAddr(line, page2)`.
5. `hiResLineAddr`: `video/hires.go:23-26`: `base = $2000` or `$4000`.

`TestHiResPage2` at `video/video_test.go:101-107` verifies line 0, page 2 -> `$4000`.

```text
    func hiResLineAddr(line int, page2 bool) uint16 {
        base := uint16(0x2000)
        if page2 {
            base = 0x4000          <- page2 honored HERE
        }
        ...
    }
```

> Where lo-res silently drops the `Page2` softswitch (doc 16 §5),
> hi-res threads it through three function calls all the way down to
> `hiResLineAddr`, where one of two base addresses (`$2000` or
> `$4000`) is selected. The data path mirrors the hardware: in real
> hardware, `$C055` flips a single mux bit in the address-generator
> circuit and the very next scanline reads come from page 2. In the
> emulator, the next call to `RenderHiRes` passes the new `page2`
> boolean and `hiResLineAddr` reads from the new base.

### How the Code Works

Lo-res comparison: `RenderLoRes(mixed bool)` at `video/lores.go` has no `page2` parameter, and `textLineAddr(row int)` at `video/video.go:115-117` has no `page2` parameter either. The dispatcher at `video/video.go:50` calls `v.RenderLoRes(mixedMode)`, silently dropping `page2`. This is the asymmetry (see doc 16 §5).

In hi-res, once `page2 = true` propagates to `hiResLineAddr`, every call to that function returns an address in `$4000`-`$5FFF` for the remainder of that frame. Software reads and writes to `$4000`+; the renderer reads the same slice. No additional memory is allocated; it is still `v.RAM` indexed differently.

### Real-World Analogy

A two-binder filing cabinet with identical tab dividers. A single switch (`$C055`) tells the renderer which binder to read from. In hi-res mode the renderer obeys the switch; in lo-res mode it is ignored.

## Section 6: Mixed Mode -- Scanlines 0-159 As Hi-Res, Scanlines 160-191 As Text

### What It Is

When `mixed=true`, `RenderHiRes` limits the graphics portion to the top 160 scanlines and delegates the bottom 32 scanlines to text rendering. The `maxLine` variable at `video/hires.go:61-64` implements this:

```go
maxLine := 192
if mixed {
    maxLine = 160 // 192 - 32 (4 text rows x 8 scanlines)
}
```

After the graphics loop finishes (`video/hires.go:66-69`), the mixed-mode tail at `video/hires.go:71-73` is:

```go
if mixed {
    v.renderTextRows(20, 24)
}
```

**Diagram 7: mixed-mode partition**

```text
  mixed = false (pure hi-res)          mixed = true (mixed mode)

  scanline  addr (page 1)              scanline  addr (page 1)
  --------  -----------                --------  -----------
      0     $2000  (HI-RES)                0     $2000  (HI-RES)
      1     $2400  (HI-RES)                1     $2400  (HI-RES)
      2     $2800  (HI-RES)                2     $2800  (HI-RES)
      ...   ...                            ...   ...
    159       ???  (HI-RES)              159       ???  (HI-RES)
    160       ???  (HI-RES)              160       --   (TEXT, row 20) <--!
    161       ???  (HI-RES)              161       --   (TEXT, row 20)
    ...       ...                         ...       ...
    191     $3FD0  (HI-RES)              191       --   (TEXT, row 23)

  maxLine = 192                        maxLine = 160
  no tail call                         tail: renderTextRows(20, 24)

  renderTextRows reads from $0400-$07FF (text page 1), NOT from
  $2000+. The text shown in the mixed-mode bottom strip is sourced
  from the text buffer, not from the hi-res buffer.
```

### Why It Matters

> The mixed-mode boundary at scanline 160 matches the lo-res boundary
> at lo-res row 40 (= scanline 160) -- the same 32-scanline text
> region at the bottom of the screen. Hi-res truncates the outer
> loop instead of guarding individual writes (lo-res does the
> opposite -- it iterates and guards). The end result is identical:
> nothing is written to scanlines 160..191 by the graphics path,
> then `renderTextRows(20, 24)` paints text from `$0400`-sourced
> bytes into those scanlines. Two completely independent memory
> regions (hi-res at `$2000`, text at `$0400`) cooperate to fill one
> screen.

The lo-res counterpart to the same tail call is at `video/lores.go:58-61`. Both call `renderTextRows(20, 24)` with identical arguments. The `renderTextRows` contract is at `video/video.go:60-62`: "renders a range of text rows [startRow, endRow)". Cross-ref doc 16 §6 and doc 08 §7.

Mixed mode is toggled by softswitches `$C052` (clear MixedMode) and `$C053` (set MixedMode) at `io/softswitches.go:85-90`.

### How the Code Works

The numerical correspondence is worth stating explicitly:
- 192 scanlines total. 4 text rows x 8 scanlines/row = 32 scanlines of text. 192 - 32 = 160.
- `renderTextRows(20, 24)` paints text rows 20, 21, 22, 23. Each text row is 8 scanlines tall (CharH=8). Rows 20..23 occupy scanlines 160..191. 20 x 8 = 160.
- The number 160 is hardcoded at `video/hires.go:63` with the comment `// 192 - 32 (4 text rows x 8 scanlines)`.

Unlike lo-res (which iterates all rows and uses an offset guard to suppress writes beyond row 40), hi-res simply stops the outer loop at `maxLine`. The bytes at scrambled addresses for scanlines 160..191 are NOT read in mixed mode. Then `renderTextRows` re-reads the text buffer and writes scanlines 160..191 via the text rendering path.

### Real-World Analogy

A stage with a hi-res photographic backdrop occupying the top five-sixths and a teleprompter in the bottom one-sixth. The photo wall has its own 8 KB film cell; the teleprompter has its own 1 KB ticker tape. The stage manager draws the photo wall first, stops at scanline 160, then unrolls the ticker tape across the bottom 32 rows.

## Section 7: End-to-End Render Trace -- From Softswitch Flip to Colored Pixel

This section traces a single concrete example through every layer. Byte `$03 = 0b_0000_0011` (two adjacent on-bits at bit 0 and bit 1) written to `RAM[$2000]`. For the dispatch wiring diagram, see §5 Diagram 6 (not redrawn here).

**Precondition.** Software has executed:
- `LDA $C050` -> `io/softswitches.go:79-80`: `s.TextMode = false`.
- `LDA $C052` -> `io/softswitches.go:85-86`: `s.MixedMode = false` (pure hi-res).
- `LDA $C054` -> `io/softswitches.go:91-92`: `s.Page2 = false` (page 1).
- `LDA $C057` -> `io/softswitches.go:100-101`: `s.HiRes = true`.

State: `TextMode=false`, `MixedMode=false`, `Page2=false`, `HiRes=true`.

**Step 1: Software writes a byte.** `STA $2000` with A=`$03`. `RAM[$2000] = $03`. This controls pixels px=0..6 on scanline 0 of page 1. Cross-ref `03.walkthrough_memory.md` for the RAM write path.

**Step 2: Frame boundary.** `main.go:374` calls `vid.Render(false, false, true, false)`. Cross-ref `08.walkthrough_video.md` §7 for the frame-render pipeline.

**Step 3: Dispatch.** `video/video.go:44-51`: `textMode=false` skips case 1; `hiRes=true` enters case 2; `v.RenderHiRes(page2=false, mixedMode=false)` runs.

**Step 4: RenderHiRes setup.** `mixed=false` so `maxLine=192` (`video/hires.go:61-64`). No tail call after the loop.

**Step 5: Outer loop, line=0.** `addr := hiResLineAddr(0, false)` (`video/hires.go:67`). Formula: `section=0, group=0, row=0` -> `$2000 + 0 + 0 + 0 = $2000`.

**Step 6: Inner loop, col=0.** `b := v.RAM[$2000] = $03` (`video/hires.go:80`).
- `palette = ($03 >> 7) & 1 = 0` -> Green/Purple palette (bit 7 is 0).
- `pixels = $03 & 0x7F = 0x03 = 0b_0000_0011`.

**Step 7: Bit loop.**

- bit=0, px=0, `thisPixel = (0x03 >> 0) & 1 = 1` (on):
  - Pass 1: bit < 6, right-neighbor = `(0x03 >> 1) & 1 = 1`. Neighbor on -> `colorIdx = 3` (White).
  - Pass 2: colorIdx already 3, skip.
  - `color = hiResColors[0][3] = (255,255,255)`.
  - `offset = (0*280 + 0) * 4 = 0`. Write `(255,255,255,0xFF)` to `v.Pixels[0..3]`.

- bit=1, px=1, `thisPixel = (0x03 >> 1) & 1 = 1` (on):
  - Pass 1: bit < 6, right-neighbor = `(0x03 >> 2) & 1 = 0`. Not white. `px%2 = 1` (odd) -> `colorIdx = 1` (Green).
  - Pass 2: colorIdx != 3; bit > 0, left-neighbor = `(0x03 >> 0) & 1 = 1`. Upgrade -> `colorIdx = 3` (White).
  - `color = hiResColors[0][3] = (255,255,255)`.
  - `offset = (0*280 + 1) * 4 = 4`. Write `(255,255,255,0xFF)` to `v.Pixels[4..7]`.

- bit=2..6, `thisPixel = 0`: `colorIdx = 0` (Black = (0,0,0,0xFF)) for each.

**Step 8: Inner loop continues.** col=1..39: `b := v.RAM[$2001..$2027]`, all zero by hypothesis -> all pixels Black on scanline 0.

**Step 9: Outer loop continues.** line=1..191: `addr = hiResLineAddr(line, false)` per the scramble. All bytes zero -> all pixels Black across all remaining scanlines.

**Step 10: Frame commit.** `main.go:377` uploads `v.Pixels` to SDL texture and presents. Cross-ref `18.walkthrough_main.md`.

**Observable result.** The leftmost two pixels of scanline 0 (px=0 and px=1) are White because the two on-bits in `$03` are adjacent and the white-merge rule fires in both directions. Pixels px=2..6 of scanline 0 are Black. The rest of the screen is Black. Byte `$03` produces a 2-pixel white dot at the top-left corner of the screen.

## Section 8: Design Decisions and Hardware Reality

**Q1: Why is bit 7 the palette-shift bit and not the 8th pixel?**

Hardware convention. The Apple II+'s video shift register clocked bits 0..6 out as pixels and gated bit 7 into the color-phase circuit (`video/hires.go:81-82`). There is no architectural reason bit 7 could not have been a 7th pixel; Wozniak chose to trade one bit per byte for double the artifact-color count. The emulator mirrors the hardware decoding exactly.

**Q2: Why approximate NTSC artifact color with a 2x4 lookup table?**

Simplification, the same flavor as doc 16's lo-res palette simplification. Real NTSC chroma comes from beating the 14 MHz dot clock against the 3.58 MHz subcarrier with YIQ encoding of dot pairs. Modeling that requires per-pixel filter-bank simulation -- roughly 100x more compute than the current neighbor heuristic. `08.walkthrough_video.md` line 707 lists "full NTSC color artifact simulation" as known future work.

**Q3: Why does the white-merge rule cross byte boundaries but the palette swap does not?**

The neighbor lookup at `video/hires.go:103-106` and `video/hires.go:123-125` reads neighbor pixel bits across byte boundaries. But `palette` is selected per-byte from bit 7 of the current byte (`video/hires.go:81`). Real hardware behaves the same way: the shift register's color-phase gate was updated when each new byte arrived, not on every bit. So a byte with bit 7=0 ending in "...11" followed by a byte with bit 7=1 starting "11..." renders the boundary pair as White (correct -- neighbor merge applies), but the pixels just before and after the boundary use different palettes. The emulator reproduces this discontinuity by construction: the byte loop walks col-by-col, reading `palette` from each byte fresh.

**Q4: Is the half-pixel shift emulated in geometry or only in palette?**

Only in palette. Real Apple II+ hi-res shifts the actual horizontal position of the 7-pixel run by half a 14 MHz dot-clock when bit 7 is set; that is what physically swapped the chroma phase on a composite TV. The emulator does NOT shift pixel positions in `v.Pixels`: every byte produces 7 pixels at exactly `col*7..col*7+6` (`video/hires.go:85`), and the framebuffer write at `video/hires.go:132-133` is `offset := (line*ScreenW + px) * 4` with no half-pixel adjustment. The palette swap (Green/Purple to Orange/Blue) stands in for the geometric shift. Visible consequence: at very high contrast, the apparent "fringe" between adjacent bytes with different bit-7 values is missing. This is a known divergence from real hardware behavior.

**Q5: What about the doc-comment table at `video/hires.go:14-19` that disagrees with the formula?**

It is a documentation bug in the source file. The comment table uses the text-mode stride convention by mistake: it treats `line += 1` as advancing the $80 stride (the convention from `textLineAddr`) when in hi-res `line += 1` actually advances the $400 stride. The result: the comment shows `Line 1 -> $2080`, `Line 7 -> $2380`, and `Line 8 -> $2400`, while the formula and `video/video_test.go:80-91` give Line 1 -> `$2400`, Line 7 -> `$3C00`, Line 8 -> `$2080`. Three of the four shown rows are wrong -- it is a structural stride mistake, not a row-label swap. The formula and test are authoritative; Diagram 3 in §3 uses them. Go comments are not executed, so runtime is unaffected. Do not use the comment table to derive addresses.

**Q6: Why is page 2 honored in hi-res but not lo-res?**

Adoption. Hi-res page 2 is heavily used by Apple II software: smooth scrolling, animated demos, and BASIC's `HGR2` command all write to `$4000`-`$5FFF` and then flip `$C055`. Lo-res page 2 (at `$0800`-`$0BFF`) is rarely used in shipped Apple II+ titles. The emulator implemented hi-res page 2 because real software depended on it; lo-res page 2 fell into the long tail. Doc 16 §5 covers the lo-res half of this asymmetry. `08.walkthrough_video.md` line 707 names text/lo-res page 2 as remaining future work.

**Q7: What happens if `RAM[$2000..$3FFF]` is uninitialized when hi-res mode is entered?**

Power-on RAM is zero-initialized (cross-ref `03.walkthrough_memory.md`), so a fresh entry into hi-res shows a black screen until software writes to the page. BASIC's `HGR` command clears the page to zeros before switching modes. Other software may flip modes first and write afterward, in which case the user briefly sees the previous frame's contents (since `v.Pixels` is not cleared between mode switches by `Render` -- see `video/video.go:36-52`, no clear-buffer call before the dispatch). The same risk exists in lo-res for the same reason.

## Section 9: Summary and Quick Reference

> Hi-res graphics is a 280x192 pixel display backed by an 8 KB
> per-page frame buffer (`$2000`-`$3FFF` for page 1, `$4000`-`$5FFF`
> for page 2). Each byte controls 7 horizontal pixels via bits 0-6
> (bit 0 = leftmost) plus a palette-select bit 7 that toggles between
> Green/Purple and Orange/Blue artifact-color pairs. The emulator
> approximates NTSC color artifacting with a per-pixel
> neighbor-and-parity heuristic that emits four colors per palette:
> Black (off), the parity-chosen artifact color (off neighbors), or
> White (any on-neighbor). The 192-row address scramble is a
> three-level interleave (`row%8`, `group`, `section`) related to but
> distinct from the 24-row text scramble. Mixed mode truncates
> graphics to scanline 159 and delegates the bottom 32 scanlines to
> `renderTextRows(20, 24)`, which sources text from the text page
> at `$0400`. Page 2 is fully threaded end-to-end, unlike lo-res
> where it is silently dropped.
