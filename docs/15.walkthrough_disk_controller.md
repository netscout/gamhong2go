## Section 0: Background -- What a Disk II Controller Card Does

### What It Is

The previous three docs walked the data stack bottom-up:
`12.walkthrough_disk_image.md` showed how 143360 bytes live on the host
filesystem; `13.walkthrough_disk_gcr.md` showed how those bytes encode into a
nibble stream; `14.walkthrough_disk_drive.md` showed how the mechanical and
magnetic state of each drive is modelled in the emulator. This doc walks the
final layer -- the controller card that connects all of that to the CPU.

A real Disk II interface card is a small PCB that plugs into an Apple II slot
(slot 6 is canonical). On the card are:

- A **256-byte PROM** at `$C600-$C6FF` (the slot-6 single-slot ROM window)
  holding the boot-and-RWTS-shim code.
- A **16-address softswitch window** at `$C0E0-$C0EF` (slot 6 lands here per
  the slot-wiring convention documented in `04.walkthrough_bus.md` §0).
- **Four stepper coil latches** (phase 0..3) that wire out to the drive's
  stepper motor -- covered in `14.walkthrough_disk_drive.md` §3.
- **Two Q flip-flops** (Q6, Q7) that form a 2-bit mode selector.
- An **8-bit data register** (the `latch` field) shifted in from the flux head
  via a serial-to-parallel register.
- A **one-byte write register** that gets clocked out to the head on write.
- **No MFM, no index mark, no format-aware logic.** The card is GCR-naive; all
  sector framing lives in software (the RWTS layer). See `dos33_boot_journey.md`
  for the 6502-level view.

**What this code emulates**: everything above except the physical flux-to-TTL
conversion and the mechanical drive internals. Drive mechanics live in
`14.walkthrough_disk_drive.md`. The GCR nibble stream that the emulated head
"reads" was prebaked by `gcr.go` (`13.walkthrough_disk_gcr.md`).

**Scope boundary** -- what this doc does NOT cover:

- **Disk image file formats** -- `12.walkthrough_disk_image.md`. Mount
  delegates to `LoadImage`; this doc treats images as opaque.
- **GCR encoding / nibble stream layout** -- `13.walkthrough_disk_gcr.md`.
  The byte stream `readDataLatch` advances through is opaque here.
- **Drive mechanical state** (halfTrack, stepper physics, `phaseOn`/`phaseOff`,
  lazy nibble cache) -- `14.walkthrough_disk_drive.md`. This doc calls those
  methods and shows the bus-to-drive dispatch, but does not re-walk them.
- **Bus shim body at `$C0E0-$C0EF`** -- fully walked in
  `14.walkthrough_disk_drive.md` §7. This doc re-cites the shim's `Strobe`
  call but does not re-walk the $C0ED / Q7=1 special-case branches.
- **RWTS higher-level logic** (track seeks, retry counts, DOS 3.3 file
  system) -- `dos33_boot_journey.md` user-side doc. §8 cross-links rather than
  disassembles.
- **16-sector vs 13-sector format distinction** -- only 16-sector is supported.
- **WOZ / .nib variable-rate nibble streams** -- not implemented (see
  `12.walkthrough_disk_image.md` §0 scope call-out).
- **2 KB expansion ROM at $C800-$CFFF** -- that is a slot-EXPANSION mechanism
  for cards that need more than 256 bytes of code. Disk II does not use it; this
  emulator does not implement it.

**Terms this doc OWNS** -- defined here for the whole series:

| Term | One-sentence definition | Expanded in |
|------|------------------------|-------------|
| **latch / data register** | `c.latch uint8` -- the byte the CPU sees at `$C0EC` in READ modes | §5 |
| **Q6 / Q7** | Two flip-flops selecting one of four controller modes (READ data, READ status, WRITE load, WRITE run) | §4, §5 |
| **BPL *-3 pacing / bit-7 pacing** | Returning `c.latch & 0x7F` when steps == 0, making RWTS's wait-for-byte loop spin | §5 |
| **cyclesPerNibble** | `32` -- CPU cycles per nibble at Apple II+ clock | §5 |
| **write register / writeReg** | Staging byte loaded via `$C0ED` in Q7=1 mode, clocked to the head in WRITE RUN | §6 |
| **boot PROM / slot-6 PROM / DISK2.rom** | The 256-byte ROM at `$C600-$C6FF` the CPU jumps to on boot | §7 |
| **tracer / Tracer** | Opt-in interface for debug logging of disk activity | §9 |

The terms **track**, **sector**, **logical sector**, and **sector order** are
owned by `12.walkthrough_disk_image.md` §0. The terms **nibble**, **nibble
stream**, **address field**, and **6-and-2 GCR** are owned by
`13.walkthrough_disk_gcr.md`. The terms **halfTrack**, **phase / coil**,
**motor / motorOn**, and **dirty flag** are owned by
`14.walkthrough_disk_drive.md`.

### Real-World Analogy

A cartridge-tape controller in an old mainframe terminal. The drive is a
mechanical reel deck; the controller card is the small board that converts "tell
the CPU what byte is under the head right now" into a memory-mapped register plus
a handful of control lines. The card does not know what a file is, does not know
how records are framed; it knows "current flux bit" and "write this bit on the
next rising edge". All higher-level structure lives in software.

## Section 1: The `Controller` Struct -- Field Groupings

### What It Is

`disk/controller.go:27-38` defines the `Controller` struct. Eight fields span
four conceptual groups: drive references, flip-flops, data path, and injection.
Reading by group rather than declaration order aligns with the section layout
that follows.

**Diagram 1: `Controller` struct field groupings** (`disk/controller.go:27-38`)

```text
                     struct Controller
   +-------------------------------------------------+
   |  DRIVE REFERENCES                               |
   |    drives   [2]drive   -- per-drive state       |
   |    selected int        -- 0 or 1 (DRIVE1/DRIVE2)|
   +-------------------------------------------------+
   |  FLIP-FLOPS (Q6/Q7 mode selector)               |
   |    q6       bool       -- data vs status/write  |
   |    q7       bool       -- read vs write side    |
   +-------------------------------------------------+
   |  DATA PATH (the byte pipeline)                  |
   |    latch    uint8      -- $C0EC read value      |
   |    writeReg uint8      -- $C0ED write staging   |
   |    lastCycle uint64    -- pacing anchor          |
   +-------------------------------------------------+
   |  INJECTION (caller-supplied)                    |
   |    cyclePtr *uint64    -- MONOTONIC CPU cycles  |
   |    tracer   Tracer     -- nil = silent           |
   +-------------------------------------------------+
```

Per-field notes (sourced from inline struct comments):

- `drives [2]drive` -- per-drive state; indexed 0 or 1 (`disk/controller.go:28`).
- `selected int` -- `0` or `1`; which drive the current softswitch access
  targets. Flipped by `$C0EA`/`$C0EB` strobes (`disk/controller.go:29`).
- `q6, q7 bool` -- the two flip-flops. See §5's matrix (`disk/controller.go:31`).
- `latch uint8` -- data register exposed at `$C0EC` reads. Updated by the
  cycle-paced `readDataLatch` (`disk/controller.go:32`).
- `writeReg uint8` -- the "next byte to write"; latched by `$C0ED` in Q7=1
  mode (see `14.walkthrough_disk_drive.md` §7 for the shim's special case)
  (`disk/controller.go:33`).
- `lastCycle uint64` -- `*cyclePtr` value at the last latch advance. Used by
  `readDataLatch` to compute delta (`disk/controller.go:34`).
- `cyclePtr *uint64` -- pointer to the host's CPU cycle counter. MUST be
  monotonically increasing. See the tricky-wording block below for the L15-13
  trap (`disk/controller.go:36`).
- `tracer Tracer` -- nil by default. Full coverage in §9
  (`disk/controller.go:37`).

**Constants alongside the struct**: `cyclesPerNibble uint64 = 32`
(`disk/controller.go:16`) and `numDrives = 2` (`disk/controller.go:20`). The
`numDrives` constant is used for bounds-checking in every public drive-index
API.

### Why It Matters

**The monotonic-diskCycle contract** is the single most load-bearing piece of
wiring between `disk/` and `main.go`. The `NewController` doc comment at
`disk/controller.go:40-44` is the authoritative spec -- quoted verbatim:

> `cyclePtr` must point to a monotonically increasing CPU cycle counter (NOT a
> frame-relative counter that resets each frame). Use a separate `diskCycle`
> variable in `main.go`; do NOT share the frame-relative `frameCycle` variable
> used by the speaker, because that resets to 0 each frame and would cause
> uint64 underflow in the delta calculation.

The emulator declares `diskCycle` separately (`main.go:90`) and increments both
counters after each CPU step (`main.go:368-369`). `frameCycle` resets to 0 each
frame (`main.go:361`); `diskCycle` never resets. If the controller shared
`frameCycle`, `delta = now - c.lastCycle` would underflow at the frame boundary
(now = small, lastCycle = large from the prior frame), causing `nibblePos` to
jump wildly. The separate variable is not an optimisation -- it is a correctness
requirement.

**Why the tracer lives in the struct**: a nil `tracer` field is ALL tracing costs
in a production build -- a single pointer comparison at each call site.

### How the Code Works

`NewController(cyclePtr *uint64)` (`disk/controller.go:45-47`) stores the
cycle pointer and returns a zeroed struct. All fields default to zero/nil/false.
The controller is inert until `Mount` or `Swap` loads an image, and until
`SetTracer` (`disk/controller.go:49-54`) optionally wires a logger.

### Real-World Analogy

A small control panel on the back of a tape deck. Two knobs labelled Q6 and Q7
pick one of four modes (READ DATA / READ STATUS / WRITE LOAD / WRITE RUN). One
slot accepts the tape reel (the drive ref). A window displays the last byte
under the head (the `latch`). A small indicator light (the `tracer`) is off by
default; an optional connector on the side accepts an external logger board.

## Section 2: Threading Model and the `Switches` Shim Call Path

### What It Is

The controller is SINGLE-GOROUTINE -- same threading model as the speaker
package covered in `11.walkthrough_speaker.md` §2. The package-level comment at
`disk/controller.go:1-6` states this verbatim:

```
// Package disk emulates the Apple Disk II controller card in slot 6.
//
// Threading model: SINGLE GOROUTINE. Same assumption as speaker.go;
// see that file's header for the full argument. All Read/Write calls
// arrive on the main goroutine via the bus. flush-on-Close also runs on
// the main goroutine. No mutexes are required.
```

### Why It Matters

The Apple II CPU stepper, the SDL event poller, and the `Swap`/`Eject` entry
points all run on the main goroutine in sequence within a single main-loop
iteration (`main.go:270-374`: `for running {` through `vid.Render(...)`). This is
what makes the latch, write register, and flush paths mutex-free. The audio
callback (`speaker.go`) runs on an SDL thread but does NOT touch
`disk.Controller`.

### How the Code Works

The bus maps `$C0E0-$C0EF` to `disk.NewSwitches(dc)` inside the
`installDiskCard` closure at `main.go:235` (lazy-install mechanics covered in
§7). On any
CPU access in that range, the bus dispatches to `Switches.Read(addr)` or
`Switches.Write(addr, v)` (the full shim body is walked in
`14.walkthrough_disk_drive.md` §7). The shim forwards to `c.Strobe(addr)` with
one exception:

- `$C0ED` Read in Q7=1 mode: sets `c.q6 = true` and returns 0 WITHOUT calling
  `Strobe` (`disk/device.go:14-18`).
- `$C0ED` Write in Q7=1 mode: calls `c.Q6WriteReg(v)`, sets `c.q6 = true`, and
  returns WITHOUT calling `Strobe` (`disk/device.go:24-29`).

Everything else forwards to `Strobe` and returns whatever `Strobe` returns.

The `$C0ED` Q7=1 special case in the shim is the ONE place the bus call path
bypasses `Strobe`. When reading this doc, "the bus hit `$C0Ex`" can be read as
"`Strobe` ran with offset `0xX`" everywhere except when the offset is `0xD`
AND Q7=1.

### Real-World Analogy

A receptionist who logs every phone call (`Strobe`) except one specific
extension that is a direct-dial voicemail deposit (`$C0ED` in Q7=1). Every
other extension routes through the log; the direct-dial bypasses it.

## Section 3: The 16-Way `Strobe` Dispatch Table (`$C0E0-$C0EF`)

### What It Is

`Strobe` (`disk/controller.go:296-377`) is the authoritative 16-way dispatch
for every softswitch access in the `$C0E0-$C0EF` window. Each of the 16 offsets
triggers a distinct side effect. There is no mirroring; every offset `0x00..0x0F`
is unique.

The signature (`disk/controller.go:296-299`):

```go
// Strobe handles a softswitch access at addr in [$C0E0..$C0EF].
// Returns the data-register value for read accesses.
func (c *Controller) Strobe(addr uint16) uint8 {
    offset := addr & 0x0F // 0..15
```

### Why It Matters

**Diagram 2: `$C0E0-$C0EF` 16-way strobe dispatch**

```text
  addr      offset  case                 side effect                          walked in
  --------  ------  -------------------  -----------------------------------  ---------
  $C0E0     0x00    PHASE0OFF            phaseOff(0) on selected drive        §4
  $C0E1     0x01    PHASE0ON             phaseOn(0) on selected drive         §4
  $C0E2     0x02    PHASE1OFF            phaseOff(1)                          §4
  $C0E3     0x03    PHASE1ON             phaseOn(1)                           §4
  $C0E4     0x04    PHASE2OFF            phaseOff(2)                          §4
  $C0E5     0x05    PHASE2ON             phaseOn(2)                           §4
  $C0E6     0x06    PHASE3OFF            phaseOff(3)                          §4
  $C0E7     0x07    PHASE3ON             phaseOn(3)                           §4
  $C0E8     0x08    MOTOROFF             motorOn=false + flushAll()           §4
  $C0E9     0x09    MOTORON              motorOn=true                         §4
  $C0EA     0x0A    DRIVE1 select        selected=0 (motor state unchanged)   §4
  $C0EB     0x0B    DRIVE2 select        selected=1 (motor state unchanged)   §4
  $C0EC     0x0C    Q6L (data register)  q6LAccess() -- 4 modes via Q6/Q7    §5, §6
  $C0ED     0x0D    Q6H                  q6=true (write-load / status mode)   §5
  $C0EE     0x0E    Q7L                  q7=false (read side)                 §5
  $C0EF     0x0F    Q7H                  q7=true  (write side)                §5
```

Notable call-outs:

- **`$C0E8` (MOTOROFF)** is the only offset with a side effect beyond drives and
  flip-flops: it calls `c.flushAll()`. Full walk in §4.
- **`$C0EA` / `$C0EB`** flip `c.selected` but do NOT touch `motorOn`
  (`disk/controller.go:341-345`). The comment is explicit: "re-route subsequent
  strobes; do NOT change motor state."
- **`$C0EC`** (Q6L) is the only offset that returns a non-zero value (via
  `q6LAccess`). All others fall through to `return 0` at
  `disk/controller.go:376`.
- **`$C0ED`** (Q6H) sets `c.q6 = true`. The `if c.q7 { }` block at
  `disk/controller.go:357-359` is intentionally empty -- write-register latching
  happens via the shim's Q7=1 special case, not here.
- **`$C0EE`** sets `c.q7 = false` (enter read side, `disk/controller.go:362-367`);
  **`$C0EF`** sets `c.q7 = true` (enter write side, `disk/controller.go:369-374`).
  Trace events fire only on transitions (the `oldQ7` guard).

### How the Code Works

The 16-address window is a consequence of how Apple II slots are wired, not a
choice the controller makes. Every slot gets a dedicated 16-address softswitch
block at `$C080 + slot*0x10`; slot 6 lands on `$C0E0`. The Disk II card uses all
16 for distinct functions because the address lines are free. Some cards use only
a few; the Disk II uses every one.

### Real-World Analogy

A jukebox with 16 buttons labelled `00` through `0F`. Some pairs are "off" and
"on" for the same feature (`00/01` for phase 0, `02/03` for phase 1, etc.); some
are distinct selectors (`0A` picks player A, `0B` picks player B); one is a
read-window (`0C` tells you what record is playing); and three more (`0D/0E/0F`)
choose listening modes.

## Section 4: Phase Strobes, Motor On/Off, Drive Select (offsets `0x00-0x0B`)

### What It Is

The first twelve cases of the `Strobe` switch handle the "mechanical" half of
the card: phase strobes (head positioning), motor on/off (spindle), and drive
select. The Q6/Q7 half -- the data and write paths -- is §5.

### Why It Matters

**Phase strobes** (`disk/controller.go:301-325`) forward to `phaseOn`/`phaseOff`
on the selected drive. For each offset `0x00..0x07`, the case body follows a
two-line pattern: call `c.tracePhase(phaseIdx, on)` BEFORE the state change
(so the trace captures the pre-change half-track), then call
`c.drives[c.selected].phaseOn(idx)` or `.phaseOff(idx)`. Only the SELECTED drive
is affected; the other drive's `phases` field is untouched until `selected` flips
via `$C0EA`/`$C0EB`. The stepper physics of `phaseOn`/`phaseOff` are walked in
`14.walkthrough_disk_drive.md` §3.

**MOTORON** (`disk/controller.go:335-339`) sets `c.drives[c.selected].motorOn =
true` and emits a `TraceModeChange` event.

**MOTOROFF** (`disk/controller.go:327-333`) does two things:

```go
case 0x08: // MOTOROFF
    c.drives[c.selected].motorOn = false
    if c.tracer != nil {
        c.tracer.TraceModeChange(*c.cyclePtr, c.selected, "MOTOROFF")
    }
    // Flush dirty tracks on motor-off to bound data loss.
    c.flushAll()
```

`flushAll` is where dirty tracks get written back to the image file in normal
operation. Not only at `Close()` -- at every MOTOROFF. This is the reason a
"normal" DOS 3.3 SAVE persists to the `.dsk` file without the user doing
anything special: when BASIC gets the prompt back, DOS drops the motor; MOTOROFF
fires `flushAll`; dirty tracks hit disk via the atomic tmp+rename dance (see
`12.walkthrough_disk_image.md` §6). `Close()` at `disk/controller.go:73-76` is
just `c.flushAll()` again -- a backstop for unclean shutdown, not the primary
persistence path.

### How the Code Works

**`flushAll`** (`disk/controller.go:78-94`) iterates both drives with a
`flushed map[*diskImage]bool{}` dedup (note the lowercase type name --
`diskImage` is package-private; see `12.walkthrough_disk_image.md` §2) so an
image shared by both drives is flushed only once (L12-7 in
`12.walkthrough_disk_image.md` §6.2). Flush
failures are logged to stderr but never returned -- a MOTOROFF strobe must not
panic or stall the CPU.

**Motor strobes affect the selected drive only.** To stop the other drive, the
CPU must flip `selected` via `$C0EA`/`$C0EB` first, then strobe MOTOROFF. This
is why Diagram 2 annotates "motor state unchanged" for DRIVE1/DRIVE2.

### Real-World Analogy

A CNC router's emergency-retract button. Pressing it does two things at once:
lifts the cutter off the stock (motor off) and triggers a routine that writes out
the current tool path so the operator can resume (flush).

## Section 5: Q6/Q7 Four-Mode Matrix + `readDataLatch` + BPL *-3 Pacing

### What It Is

This is the densest section of the doc, and the section that owns the terms
**latch / data register**, **Q6 / Q7**, **BPL *-3 pacing**, and
**cyclesPerNibble**. It covers the `q6LAccess` function and the `readDataLatch`
function it calls in READ DATA mode. The **BPL *-3 pacing claim is the single
load-bearing claim in the whole series.**

### Why It Matters

**L15-4: `cyclesPerNibble = 32`** (`disk/controller.go:16`). At 1.023 MHz Apple
II+ clock, 32 cycles = 31.3 microseconds per nibble. 16 sectors per track * 396
nibbles per sector envelope + 48 head-gap = 6384 nibbles per track (see
`13.walkthrough_disk_gcr.md` §7). 6384 * 31.3 microseconds = 200 ms per
revolution. The Disk II spins at 300 RPM = 200 ms per revolution. The constant
is not a guess -- it is calibrated to real hardware rotation speed.

**L15-3: the Q6/Q7 four-mode matrix.** The doc comment at
`disk/controller.go:379-385` is the authoritative spec:

```go
// q6LAccess implements the $C0EC data-register access.
// Behaviour depends on the Q7/Q6 mode:
//
//   Q7=0, Q6=0  READ data   advance nibble stream with cycle pacing
//   Q7=0, Q6=1  READ status return WP in bit 7 (motor-on gated)
//   Q7=1, Q6=0  WRITE load  (load mode active; Q6L returns current latch)
//   Q7=1, Q6=1  WRITE run   clock writeReg into nibble stream
```

**Diagram 3: Q6/Q7 four-mode matrix**

```text
               Q6=0                         Q6=1
           +-----------------+-----------------+
    Q7=0   |  READ DATA      |  READ STATUS    |
           |  advance latch  |  bit 7 = WP &&  |
           |  via cycle pace |  motorOn        |
           |  BPL *-3 paced  |  (no pacing)    |
           +-----------------+-----------------+
    Q7=1   |  WRITE LOAD     |  WRITE RUN      |
           |  latch shown,   |  clock writeReg |
           |  no advance     |  into nibble[.] |
           |                 |  set dirty[t]   |
           +-----------------+-----------------+

  Q6 set by:   $C0ED (Q6H, c.q6 = true)
  Q6 clear by: NEVER cleared by softswitch in this emulator. Real Disk II
               hardware clears Q6 on $C0EC; here q6LAccess handles the
               behavioral outcome without toggling the flag (see note below).
  Q7 set by:   $C0EF (Q7H, c.q7 = true)
  Q7 clear by: $C0EE (Q7L, c.q7 = false)
```

A clarifying note: in Disk II hardware documentation `$C0EC` is called "Q6 Low"
because it clears Q6 in the real chip. In this emulator hitting `$C0EC` runs
`q6LAccess` (the data-register read); `$C0ED` (Q6H) sets `c.q6 = true`. The
behavioural outcome matches real hardware; the naming diverges from the
schematic.

### How the Code Works

**READ STATUS branch** (Q7=0, Q6=1, `disk/controller.go:389-396`):

```go
if !c.q7 && c.q6 {
    // READ status: return WP in bit 7, motor-on gated.
    // Bit-7 pacing rule for BPL *-3 does not apply here.
    if d.motorOn && d.writeProt {
        return 0x80
    }
    return 0x00
}
```

Returns `0x80` only when the motor is on AND the disk is write-protected. The
motor-on gate matches what RWTS observes under normal operation. This path is NOT
paced; BPL *-3 is a READ DATA feature.

**WRITE RUN branch** (Q7=1, Q6=1): full walk is §6 (`disk/controller.go:398-413`).

**READ DATA / WRITE LOAD branch** (Q6=0, `disk/controller.go:415-421`):

```go
if !c.q7 && !c.q6 {
    return c.readDataLatch(d)
}
// Q7=1, Q6=0 (WRITE load): just return current latch without advancing.
return c.latch
```

WRITE LOAD returns the latch without advancing. The latch is a shared register;
write mode does not zero it.

**`readDataLatch` full walk** (`disk/controller.go:424-473`):

Guard (`disk/controller.go:427-436`): if motor is off, no image, or nibble
buffer empty, return `0xFF`. Chose `0xFF` over `0x00` -- all legal GCR nibbles
have bit 7 set so `0xFF` looks like "not a recognisable nibble" rather than valid
data.

Cycle math (`disk/controller.go:438-441`):

```go
now := *c.cyclePtr
delta := now - c.lastCycle
steps := delta / cyclesPerNibble
rem := delta - steps*cyclesPerNibble
```

The `rem` retains the sub-nibble-time remainder for phase preservation below.

**L15-5: BPL *-3 pacing** (`disk/controller.go:443-447`) -- verbatim:

```go
if steps == 0 {
    // Not enough time elapsed for a new nibble.
    // RWTS's BPL *-3 wait-for-byte loop relies on seeing bit 7 = 0 here.
    return c.latch & 0x7F
}
```

RWTS's "wait for a nibble" loop is three bytes of 6502: `LDA $C0EC; BPL *-3`.
The `BPL` ("branch on plus", i.e. branch if bit 7 is clear) jumps 3 bytes back
to the `LDA` as long as the byte just read has bit 7 = 0. All legal GCR nibbles
have bit 7 set (see `13.walkthrough_disk_gcr.md` §1). The emulator exploits
this: when `readDataLatch` is called before `cyclesPerNibble` (32) cycles have
elapsed, it returns `c.latch & 0x7F` -- same value as before, but with bit 7
forcibly cleared. RWTS sees "not ready, spin again" and the loop spins. After 32
cycles elapse, `readDataLatch` advances `nibblePos`, loads a fresh nibble (bit 7
set by construction), and returns it. RWTS sees "byte arrived" and falls through
to processing.

This is the reason the controller needs `cyclePtr` at all. Without it, the
emulator would have to either (a) hand out a fresh nibble on every `$C0EC`
access -- RWTS would race through the track at CPU speed, not disk speed, and the
sector framing would break -- or (b) tick a timer in a separate goroutine -- the
single-goroutine threading model rules that out. The `cyclePtr -> delta -> steps
-> latch & 0x7F` path turns the single-goroutine emulator into a cycle-accurate
Disk II without a timer.

**L15-6: modulo-clamp** (`disk/controller.go:449-455`):

```go
nLen := len(nibs)
if int(steps) > nLen {
    // Jump is larger than one revolution; just keep relative position.
    steps = steps % uint64(nLen)
}
```

If `delta` is enormous (emulator startup, long idle, test fixtures that advance
the cycle counter by billions), `steps` would jump `nibblePos` many revolutions
forward. The modulo-clamp collapses it to a within-one-revolution advance. This
is the safety net the hot-swap threading comment (walked in §7) depends on.

**L15-7: sub-nibble phase preservation** (`disk/controller.go:457-459`):

```go
d.nibblePos = (d.nibblePos + int(steps)) % nLen
c.latch = nibs[d.nibblePos]
c.lastCycle = now - rem // preserve sub-nibble phase
```

Subtracting `rem` from `now` pretends the read happened at the exact nibble
boundary. Without it, fractional cycles accumulate: a CPU polling every 31
cycles instead of 32 would drift to 62 cycles per nibble -- enough to break
RWTS timing over one revolution.

`d.lastReadAt = nowFn()` (`disk/controller.go:460`) stamps wall-clock for the
activity indicator (owned by `14.walkthrough_disk_drive.md` §5). Tracer
emission at `disk/controller.go:462-470` is covered in §9.

**Diagram 4: cycle-paced nibble advance + BPL *-3 pacing timeline**

```text
  CPU cycle stream  ....................................................
                    t0           t0+10  t0+20  t0+32  t0+40  t0+64
                    |             |      |      |      |      |
                    v             v      v      v      v      v
                  first          read   read   read   read   read
                  read           #2     #3     #4     #5     #6
                  (primes
                   latch)

  cyclesPerNibble = 32; suppose last latch advance was at t0.

  read #2 at t0+10:
     delta=10, steps=0, rem=10
     return c.latch & 0x7F     <-- BIT 7 CLEAR (not ready)
     RWTS BPL *-3: bit 7=0, branch back, read again.

  read #3 at t0+20:
     delta=20, steps=0, rem=20
     return c.latch & 0x7F     <-- BIT 7 CLEAR (still not ready)

  read #4 at t0+32:
     delta=32, steps=1, rem=0
     nibblePos += 1, c.latch = nibs[nibblePos]   <-- NEW NIBBLE
     c.lastCycle = (t0+32) - 0 = t0+32
     return c.latch            <-- bit 7 SET
     RWTS BPL *-3: bit 7=1, falls through to processing.

  read #5 at t0+40:
     delta=8, steps=0, rem=8
     return c.latch & 0x7F     <-- BIT 7 CLEAR again (paced)

  read #6 at t0+64:
     delta=32, steps=1, rem=0
     c.latch = next nibble; bit 7 set.

  Net effect: the CPU sees a new byte at most every 32 cycles, regardless
  of how fast it polls $C0EC. In between, bit 7 is clear so the BPL *-3
  loop spins.
```

### Real-World Analogy

A barista at a slow espresso machine. The espresso takes 32 seconds to pour.
Customers (the CPU) keep asking "is it ready?" every few seconds. The barista
answers "not yet, bit-7 clear" (returns `latch & 0x7F`). When 32 seconds elapse,
the next "is it ready?" gets the cup (bit 7 set). The barista resets their timer
to the exact moment the espresso finished, not to the moment the customer last
asked -- if they reset to "last asked" the timer would drift and the next shot
would be late.

## Section 6: The Write-Run Path (`writeReg` -> nibble stream + dirty flag)

### What It Is

The Q7=1, Q6=1 branch of `q6LAccess` at `disk/controller.go:398-413` is the
write path. It owns the **write register / writeReg** term and sets the only
dirty flag in the whole package.

### Why It Matters

**L15-8: the WRITE run path** -- verbatim (`disk/controller.go:398-413`):

```go
if c.q7 && c.q6 {
    // WRITE run: clock writeReg into current nibble position.
    if d.motorOn && !d.writeProt && d.image != nil {
        track := d.halfTrack / 2
        nibs := d.trackData(d.image.order)
        if len(nibs) > 0 {
            d.nibbles[track][d.nibblePos] = c.writeReg
            d.dirty[track] = true
            d.nibblePos = (d.nibblePos + 1) % len(nibs)
        }
        now := *c.cyclePtr
        c.lastCycle = now
        d.lastWriteAt = nowFn()
    }
    return c.latch
}
```

Three guards before any write: `motorOn`, NOT `writeProt`, `image != nil`. Fail
any of them and the whole `if` body is skipped; the CPU still gets `c.latch` back
(stale read-side value). RWTS checks write-protect via the READ STATUS path
BEFORE trying a write; the guard here is a safety net for mis-sequenced code.

Track derivation: `track := d.halfTrack / 2` -- same integer-divide rule as
`trackData` (see `14.walkthrough_disk_drive.md` §2). Odd half-tracks write to
the even-below track's buffer.

Lazy cache materialisation via `trackData` (`disk/controller.go:402`): if the
track has never been read, `trackData` calls `EncodeTrack` first (see
`14.walkthrough_disk_drive.md` §4). A write to a previously-unread track still
materialises the full 6384-nibble buffer and writes into it.

The manual +1 advance (`disk/controller.go:406`): writes are NOT cycle-paced.
Every `$C0EC` access in Q7=1/Q6=1 mode advances `nibblePos` by exactly 1. The
cycle anchor `c.lastCycle = now` is updated (not `now - rem`) so if the CPU
drops back to read mode, the next delta starts from the last write instant
exactly. Writes have no sub-nibble phase to preserve; the CPU dictates write
timing via hand-tuned 6502 code.

`d.dirty[track] = true` (`disk/controller.go:405`) is the ONLY site that sets
the dirty flag. The flag is consumed by `img.flush` during MOTOROFF (§4) and
`Close()`. `d.lastWriteAt = nowFn()` (`disk/controller.go:410`) stamps the
wall-clock timestamp for the write-activity indicator; ownership in
`14.walkthrough_disk_drive.md` §5.

### How the Code Works

**`Q6WriteReg` -- the staging latch** (`disk/controller.go:494-499`):

```go
// Q6WriteReg latches v into the write register (called on $C0ED write in Q7=1 mode).
func (c *Controller) Q6WriteReg(v uint8) {
    if c.q7 {
        c.writeReg = v
    }
}
```

Called from `Switches.Write` at `disk/device.go:25-29` when the address is
`$C0ED` and `q7` is true. The `if c.q7` guard is defence-in-depth; the shim
already checks `c.q7` before calling. `writeReg` is not zeroed after the
clock-out; the same byte stays there until the next `$C0ED` write.

The write side does not go through `readDataLatch`. It lives inside `q6LAccess`
directly and does its own +1 advance. RWTS's write loop self-paces at one byte
per 32 CPU cycles (hand-tuned 6502 code); the emulator trusts the CPU's timing
rather than rate-limiting on its own.

Wire sequence: CPU `STA $C0EF` (q7=true) -> `STA $C0ED, v` (Q6WriteReg -> writeReg=v)
-> `STA $C0EC` (WRITE RUN: nibs[nibblePos]=v, dirty[track]=true, nibblePos++) ->
repeat per byte -> `STA $C0EE` (q7=false) -> `STA $C0E8` (MOTOROFF -> flushAll).

### Real-World Analogy

A telegraph key with a paper-tape recorder. The operator (CPU) first loads a
character onto the key (`$C0ED` writes to `writeReg`), then presses "send"
(`$C0EC` in WRITE RUN). Each press advances the tape by one character slot. The
operator is responsible for pacing; there is no timer inside the tape mechanism.

## Section 7: Mount / Swap / Eject + Threading Contract + PROM Lazy Install

### What It Is

The lifecycle methods that manage image loading, hot-swap, and the slot-6 PROM
wiring. This section owns the **boot PROM / slot-6 PROM / DISK2.rom** term.

### Why It Matters

**Mount** (`disk/controller.go:56-71`) bounds-checks `driveIdx`, delegates to
`LoadImage` (see `12.walkthrough_disk_image.md` §3), and sets `image`,
`writeProt`, and `label`. The `deriveLabel(path)` call at
`disk/controller.go:68` is the label setter; the caching rationale is owned by
`14.walkthrough_disk_drive.md` §6.

**Close** (`disk/controller.go:73-76`) is one line: `c.flushAll()`. It is a
safety net for unclean shutdown; normal persistence is MOTOROFF in §4.

**Swap** (`disk/controller.go:139-251`) is the meatiest method in the file after
`Strobe`/`q6LAccess`. It proceeds in phases:

1. Bounds-check `driveIdx`; log a warning (not an error) if the motor is on.
2. Flush the outgoing image (logged on error, not fatal).
3. Clear all image-bound per-drive state: `image`, `writeProt`, `nibblePos`,
   `lastReadAt`, `lastWriteAt`, `label`, `nibbles[*]`, `dirty[*]`.
   Preserved: `halfTrack`, `phases`, `motorOn` (mechanical state, as on real
   hardware).
4. Clear controller-level `latch` and `writeReg` IF this drive is the currently
   selected drive (`disk/controller.go:223-226`). Do NOT clear `q6`/`q7` --
   those are flip-flops on the card, CPU-owned. Do NOT reset `c.lastCycle` -- see
   the threading contract below.
5. If `path == ""`, return (eject-only path).
6. Load new image via `LoadImage`; set `image`, `writeProt`, `label`.

**L15-14: Swap threading contract** -- quoted verbatim from
`disk/controller.go:152-167`:

> Threading contract (v3): the main loop calls sdl.PollEvent -> handles
> DROPFILE -> then runs the CPU step, so Swap and readDataLatch never execute
> concurrently; no mutex is needed for the latch/writeReg clear. Swap MUST be
> called on the SDL main goroutine (consistent with the package-level
> single-goroutine invariant at disk/controller.go:3). SDL drop events and
> keyboard events are polled on that goroutine; the audio callback (speaker.go)
> never touches disk.Controller.
>
> c.lastCycle is intentionally NOT reset. The next readDataLatch call will
> compute delta = now - c.lastCycle; if that delta is huge (drive was
> deselected for many seconds, or this is the first read after a long idle),
> the steps = delta / cyclesPerNibble computation is clamped by the
> modulo-wrap at disk/controller.go:295 (steps = steps % uint64(nLen)), so
> nibblePos wraps cleanly within one revolution regardless of gap size. That
> clamp -- not any "global pacing" notion -- is the actual safety net.

**Narrator note about drifted line reference**: the threading comment above cites
`disk/controller.go:295` as the location of the modulo-wrap clamp. The current
clamp is at `disk/controller.go:452-455` (verified in §5 above). The internal
line number is stale -- a consequence of code refactoring since the comment was
written. The behaviour described is correct; only the cited line number has
drifted. Flagged for future cleanup.

**Eject** (`disk/controller.go:253-258`) is a readability-only wrapper for
`Swap(driveIdx, "")`, used by `handleDiskEjectKey` for Ctrl+1 / Ctrl+2.

**Ctrl+1 / Ctrl+2 eject wiring** (`main.go:793-814`): `handleDiskEjectKey`
checks `!dc.HasDisk(driveIdx)` and logs "already empty" if true. Returns `true`
to consume the key, preventing the character from reaching the BASIC prompt.

### How the Code Works

**L15-10: the PROM is 256 bytes, NOT 2 KB.** This is the most common
reader trap. The IIe slot-expansion ROM window at `$C800-$CFFF` is 2 KB -- that
is for cards that need more ROM than 256 bytes. The Disk II uses the simpler
**single-slot ROM** at `$C600-$C6FF`, exactly 256 bytes. This emulator does not
implement the `$C800-$CFFF` slot-expansion mechanism; Disk II does not need it.

Verification:
- `main.go:222`: `memory.LoadROM("roms/DISK2.rom", 0xC600)` -- loads at `$C600`.
- `main.go:232`: `b.Map(prom.Base, prom.End(), prom)` -- `prom.End()` returns
  `Base + Size - 1 = 0xC6FF` for a 256-byte file.
- `main.go:237`: the success log names both the size and the address range.
- Confirmed: `roms/DISK2.rom` is 256 bytes.

**L15-11: idempotent lazy install.** The `installDiskCard` closure at
`main.go:216-241` guards on `diskCardInstalled` to short-circuit repeat calls.
Inside, it loads the PROM first (`memory.LoadROM("roms/DISK2.rom", 0xC600)`);
on failure it logs via `promFailed` (rate-limit: verbose on first failure, terse
on subsequent) and returns WITHOUT mapping softswitches. On success it maps the
PROM (`b.Map(prom.Base, prom.End(), prom)`), then the softswitches
(`b.Map(0xC0E0, 0xC0EF, disk.NewSwitches(dc))`), then sets
`diskCardInstalled = true`. PROM-first ordering ensures the card is either fully
installed or fully absent -- no half-installed state (PROM blank, softswitches
live).

The gate at `main.go:245-247` only calls `installDiskCard()` at startup if
`-disk1` or `-disk2` was given. Without disk flags, the PROM region is unmapped
(open bus) and the CPU boots Applesoft normally. `handleDropFile`
(`main.go:740-766`) calls `installCard()` lazily at `main.go:755`: a user who
launched without disk flags can drag-drop a `.dsk` mid-session and get the card
installed on the fly.

**L15-12: rate-limited failure handling.** Three consecutive drops with a missing
`DISK2.rom` produce one verbose line (`%v (card not installed)`) plus two terse
lines (`still missing -- install failed on prior attempt`). On success,
`promFailed` is reset so a later failure fires the verbose line again.

**Ctrl+R after mid-session install**: the success log at `main.go:764` tells the
user to "press Ctrl+R to reboot". The Apple II firmware's slot scan runs during
CPU reset. If the PROM is installed mid-session, it exists at `$C600` but no
code has jumped into it yet -- Applesoft keeps running. Pressing Ctrl+R fires a
reset; the firmware finds slot 6, jumps to `$C600`, and the disk boots.

**Diagram 5: PROM lazy install state machine**

```text
  startup:
     no -disk flag       -->  installDiskCard NOT called; prom unmapped (open bus)
     -disk1 or -disk2    -->  installDiskCard()
                               |
                               v
                           LoadROM "roms/DISK2.rom"  --FAIL-->  stderr verbose;
                               |                               promFailed=true; return
                               v
                           b.Map prom ($C600-$C6FF, 256 bytes)
                               |
                               v
                           b.Map softswitches ($C0E0-$C0EF)
                               |
                               v
                           diskCardInstalled = true

  drag-drop:
     handleDropFile --> installCard()
                        |
                        v
                     diskCardInstalled?
                      yes -> no-op (idempotent)
                      no  -> same sequence as above
                             on success: user presses Ctrl+R to reboot
```

### Real-World Analogy

Installing a printer driver on a running OS. The first time you plug the printer
in, the OS offers to install the driver (first `installCard()` call); subsequent
plug-ins are no-ops (idempotent). If the driver installer fails, the OS logs it
once and does not spam subsequent attempts. And the printer does not actually
print until you restart the relevant service (Ctrl+R to reboot).

## Section 8: End-to-End Boot Trace (Emulator-Side)

### What It Is

A high-level walk from CPU reset to the DOS prompt, emulator-side. This section
does NOT disassemble the 256-byte PROM -- see `dos33_boot_journey.md` for the
6502-level detail. The goal is to connect §3's dispatch table, §5's BPL *-3
pacing, §4's MOTOROFF flush, and §7's PROM wiring into a single narrative.

### How the Code Works

**Diagram 6: boot sequence (high-level, emulator-side)**

```text
  CPU reset
       |
       v
  Apple II firmware: slot scan ($FFFC/D reset vector)
       |  slot 6 PROM signature match
       v
  JMP $C600  (prom.Base; mapped by installDiskCard, main.go:232)
       |
       v
  DISK II PROM (256 bytes at $C600-$C6FF):
    $C0EA DRIVE1 select (§4)
    $C0E9 MOTORON (§4)
    LDA $C0EC / BPL *-3  <-- BPL *-3 paced latch reads (§5)
    JMP $0801 once track 0 sector 0 loaded into $0800
    (Q7 remains false from zero-value controller construction;
     boot is read-only, so the PROM never touches $C0EE/$C0EF.)
       |
       v
  boot0 at $0801: phase strobes (§4), more $C0EC reads (§5)
    load RWTS at $B700 -- see dos33_boot_journey.md
       |
       v
  DOS 3.3 resident loaded
       |
       v
  $C0E8 MOTOROFF --> c.flushAll() (no-op; boot is read-only) (§4)
       |
       v
  BASIC prompt ]
```

The emulator does not run the PROM "specially". It is 256 bytes of 6502 at
`$C600-$C6FF`, executed by the same CPU emulator that runs Applesoft. Every
`$C0EC` access routes through the same `Strobe` -> `q6LAccess` ->
`readDataLatch` path. The "magic" is that the Apple PROM was designed to use
those addresses in a way that matches what the emulator models. There is no
PROM-detection code in `disk/controller.go`.

### Real-World Analogy

An old PC BIOS with a boot ROM for a SCSI controller. The BIOS scanned slots for
a signature byte, jumped to the ROM, and the ROM did the rest. The hardware did
not "know" it was booting SCSI versus IDE.

## Section 9: Tracing Disk Activity (`tracer.go`)

The Tracer interface is an opt-in debug facility. By default `c.tracer` is nil
and tracing costs nothing beyond a pointer comparison at each call site. Wire a
non-nil implementation via `SetTracer` (`disk/controller.go:49-54`) to enable
logging.

**L15-16: four methods** (`disk/tracer.go:12-30`):

```go
type Tracer interface {
    TraceNibbleRead(cycle uint64, drive, halfTrack, nibblePos int, value uint8)
    TracePhaseStrobe(cycle uint64, drive, phase int, on bool, oldHT, newHT int, phases [4]bool)
    TraceModeChange(cycle uint64, drive int, event string)
    TraceAddressField(cycle uint64, drive, halfTrack, nibblePos int, vol, track, sector uint8)
}
```

- **TraceNibbleRead** (`disk/tracer.go:12-17`): fires on every `$C0EC` read
  that actually advances the latch (steps > 0 in `readDataLatch`). Does NOT fire
  on BPL *-3 paced reads (steps == 0), so trace volume matches real nibble rate,
  not CPU poll rate. Rate-limited via `maxNibbles` in the `stderrTracer`
  implementation.
- **TracePhaseStrobe** (`disk/tracer.go:19-22`): fires on every `$C0E0-$C0E7`
  access via the `tracePhase` helper. Called BEFORE the state change, so `oldHT`
  is the current half-track; `newHT` is the predicted value after the step (may
  clamp at 0 or 69).
- **TraceModeChange** (`disk/tracer.go:24-25`): fires on MOTORON, MOTOROFF,
  Q6=1, Q7=0, and Q7=1. Q6L resets are NOT traced -- that is the data-register
  read, not a mode change.
- **TraceAddressField** (`disk/tracer.go:27-30`): fires when a complete `D5 AA
  96 <vol> <trk> <sec> <chk>` address field is detected with a valid XOR
  checksum. Used to confirm the disk is framing correctly. One per sector, low
  rate -- unbounded.

**L15-15: nil-default zero overhead.** Every call site is guarded
(`disk/controller.go:329, 337, 353, 365, 372, 463, 468, 502-504`). Example:

```go
func (c *Controller) tracePhase(phase int, on bool) {
    if c.tracer == nil {
        return
    }
    ...
```

Production builds wire no tracer; the only cost is the nil-pointer comparison.

**`stderrTracer` -- the only shipped implementation** (`disk/tracer.go:32-78`):
`NewStderrTracer(w io.Writer, maxNibbles int) Tracer` (`disk/tracer.go:40-44`)
wraps any `io.Writer` (stderr from `main.go`). `maxNibbles` caps the
`TraceNibbleRead` line count (0 = unlimited). The rate limit is a running
counter, not a time window. A boot triggers tens of thousands of nibble reads;
capping at 200 shows the first 200 and silently drops the rest. `drive+1` is
the 1-based user-facing index. Phase, Mode, and AddressField methods
(`disk/tracer.go:55-78`) are unbounded -- they fire much less frequently.

**`checkAddressFieldTrace`** (`disk/controller.go:475-492`) -- the ACTIVE
address-field trace site. Called from `readDataLatch` at
`disk/controller.go:467-470`. Uses a closure `at(offset)` that handles
wrap-around via modulo:

```go
at := func(offset int) uint8 { return nibs[(pos+offset+n)%n] }
```

Checks for `D5 AA 96` at positions -2, -1, 0 from the current `nibblePos`. If
matched, decodes the 4 odd/even pairs (vol, track, sector, checksum) and verifies
`chk == vol^track^sector` (the `decodeOddEven` function is from `gcr.go`; see
`13.walkthrough_disk_gcr.md` §4). On success, emits `TraceAddressField`.

**L15-17: `traceAddressField` is dead code.** `disk/controller.go:539-548`
defines a lowercase method:

```go
func (c *Controller) traceAddressField(d *drive, nibs []uint8, pos int, vol, track, sector uint8) {
    if c.tracer == nil {
        return
    }
    c.tracer.TraceAddressField(*c.cyclePtr, c.selected, d.halfTrack, pos,
        vol, track, sector)
}
```

This method is NOT called anywhere in the package. The active site is
`checkAddressFieldTrace` at `disk/controller.go:475-492`, which calls
`c.tracer.TraceAddressField` directly. The lowercase helper is a leftover from an
earlier refactor -- it is callable dead code that would work if wired, but no
caller wires it. When reading the source, follow `checkAddressFieldTrace`, not
this lowercase helper. The dead method is flagged here as a future-cleanup target.

**CLI wiring** (`main.go:52-53`, `main.go:197-199`):
- `-disktrace` flag (bool, default false): enables tracing.
- `-disktracen` flag (int, default 200): caps nibble lines.
- At startup: `if *diskTrace { dc.SetTracer(disk.NewStderrTracer(os.Stderr, *diskTraceN)) }`.
- `-disktracen 0` = unlimited (per `NewStderrTracer` contract).

**Frequently asked questions**:

**Q: What is the difference between Q6L ($C0EC) and Q6H ($C0ED)?**
A: `$C0EC` runs `q6LAccess` (returns the latch per the Q6/Q7 matrix). `$C0ED`
sets `c.q6 = true`; in Q7=1 mode via the shim it also latches `writeReg`.
Reading `$C0EC` returns a value; reading `$C0ED` returns 0.

**Q: Why does the cycle-paced read return `latch & 0x7F` instead of 0?**
A: RWTS's `LDA $C0EC; BPL *-3` loop branches while bit 7 is clear. Returning 0
also works, but `latch & 0x7F` preserves the low 7 bits so debuggers see stable
partial data rather than an opaque zero.

**Q: Why is `c.lastCycle` not reset on hot-swap?**
A: The modulo-clamp in `readDataLatch` (§5 L15-6) collapses any huge delta to a
within-one-revolution advance, so resetting `lastCycle` would save no bug and
risks desynchronising the cycle math.

**Q: What is the difference between `checkAddressFieldTrace` and `traceAddressField`?**
A: `checkAddressFieldTrace` at `disk/controller.go:475-492` is the active path.
`traceAddressField` at `disk/controller.go:539-548` is dead code (§9 L15-17).
