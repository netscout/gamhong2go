## Section 0: Background -- What a Drive Represents

### What It Is

The previous two docs walked the _data_: `12.walkthrough_disk_image.md` showed
how 143360 bytes live on the host filesystem; `13.walkthrough_disk_gcr.md`
showed how those bytes encode into a nibble stream. This doc walks the
_mechanism_ -- the software model of the physical Disk II drive.

Real Disk II hardware is deliberately dumb. The drive contains a 4-phase
stepper motor (head positioning), a spindle motor (~300 RPM), and a flux
amplifier. No sector framing. No checksums. All intelligence lives in the
controller card. In this emulator, `disk/drive.go` (98 LOC) holds the per-drive
mechanical and magnetic state the controller reads and writes.

**Scope boundary** -- what this doc does NOT cover:

- **Q6 / Q7 state machine** -- `15.walkthrough_disk_controller.md` §4.
- **Cycle-paced `readDataLatch`** -- `15.walkthrough_disk_controller.md` §5.
- **Boot PROM** -- `15.walkthrough_disk_controller.md` §8.
- **GCR encoding internals** -- `13.walkthrough_disk_gcr.md`. `EncodeTrack` is opaque here.
- **Disk image file formats** -- `12.walkthrough_disk_image.md`. `*diskImage` is opaque here.
- **Quarter-tracking** -- not emulated; see §2.
- **Tracer interface** -- `15.walkthrough_disk_controller.md` §9.

**Terms this doc OWNS** -- defined here for the whole series:

| Term | One-sentence definition | Expanded in |
|------|------------------------|-------------|
| **halfTrack** | Integer 0..69; head position; `track = halfTrack/2`; odd values sit between real tracks | §2 |
| **phase / coil** | One of four stepper-motor coils (0..3); energising adjacent coils drags the head half a track | §3 |
| **motor / motorOn** | Per-drive spindle state; flipped by `$C0E8`/`$C0E9` strobes via the controller | §1, §6 |
| **dirty flag** | Per-track boolean set on each write nibble; read by the flush path in `12.walkthrough_disk_image.md` §6 | §1, §4, §6 |

The terms **track**, **sector**, **logical sector**, and **sector order** are
owned by `12.walkthrough_disk_image.md` §0. The terms **nibble**, **nibble
stream**, and **EncodeTrack** are owned by `13.walkthrough_disk_gcr.md` §1 / §5.

### Real-World Analogy

A turntable: motor spins the platter (`motorOn`), an arm positions the
cartridge in half-click steps (`halfTrack`) driven by a solenoid (phases).
Sector interleaving and GCR encoding belong to the controller, not the drive.

## Section 2: The `halfTrack` Model (0..69, `track = halfTrack/2`, No Quarter-Tracking)

### What It Is

The Disk II head resolves 70 distinct positions -- 35 "on-track" and 35
"between-track". The emulator models this as a plain integer `halfTrack`.

`disk/gcr.go:47-52` defines the boundary constant:

```go
const (
    tracksPerDisk = 35
    // maxHalfTrack is the highest legal halfTrack index. 35 tracks ->
    // halfTracks 0..69 (70 positions total); index 70 would map to
    // track 35, out of bounds for nibbles[tracksPerDisk].
    maxHalfTrack    = 2*tracksPerDisk - 1
    ...
)
```

**Diagram 2: halfTrack number line**

```text
  halfTrack:  0    1    2    3    4    5  ...  66   67   68   69
              |    |    |    |    |    |        |    |    |    |
  track:      0    0    1    1    2    2  ...  33   33   34   34
              ^         ^         ^            ^         ^
              even=real even=real even=real   even=real even=real

  halfTrack 1: head is between tracks 0 and 1 -> returns track 0's buf
  halfTrack 69: head is beyond track 34 (clamped)

  Clamp at boundaries:
    decrement from 0    -> pinned at 0    (disk/drive.go:48-50)
    increment past 69   -> pinned at 69   (disk/drive.go:51-53)
```

### Why It Matters

The `track = halfTrack/2` bridge is critical: an off-by-one returns a
neighboring track's nibble buffer -- silent data corruption.

### How the Code Works

`disk/drive.go:92`: `t := d.halfTrack / 2`. Integer division truncates toward
zero: halfTrack 68 -> track 34, halfTrack 69 -> track 34. Odd half-tracks map
to the same buffer as the even below.

> Odd half-tracks are not a separate "half data stream" in this
> emulator. They share the even-below track's nibble buffer. A real
> Disk II head at halfTrack=1 reads a mixture of track 0 and track 1
> flux with reduced signal quality -- the emulator simplifies by
> returning track 0's clean signal. This is one of the deliberate
> fidelity trade-offs; the quarter-track mechanism that advanced
> copy-protection schemes used is not modelled.

**Quarter-tracking NOT emulated.** `activePhase()` returns -1 for multiple
coils; `phaseOn` only steps when `prev >= 0`. `halfTrack` is `int` (not
`uint8`) because the `halfTrack < 0` guard at `disk/drive.go:48-50` requires it.

### Real-World Analogy

An elevator with 35 floors and 70 stops. An odd stop is between floors;
this emulator shows the lower floor's contents.

## Section 3: Stepper-Motor Physics (4 Coils, Adjacent-Coil Step, Opposite-Coil No-Op)

### What It Is

Four coils at 90-degree intervals surround a spiral cam. An adjacent coil drags
the head half a track; the opposite coil is ambiguous and does nothing.

**Diagram 3: 4-coil stepper motor (top-down view)**

```text
              coil 1
                |
    coil 0 --- CAM --- coil 2
                |
              coil 3

  diff = (next - prev + 4) % 4

    prev=0, next=1  diff=1  -> halfTrack++   (forward)
    prev=1, next=2  diff=1  -> halfTrack++   (forward)
    prev=2, next=3  diff=1  -> halfTrack++   (forward)
    prev=3, next=0  diff=1  -> halfTrack++   (forward, wraps mod 4)

    prev=0, next=3  diff=3  -> halfTrack--   (backward)
    prev=3, next=2  diff=3  -> halfTrack--   (backward)
    prev=2, next=1  diff=3  -> halfTrack--   (backward)
    prev=1, next=0  diff=3  -> halfTrack--   (backward)

    prev=0, next=2  diff=2  -> NO-OP         (opposite coil)
    prev=1, next=3  diff=2  -> NO-OP         (opposite coil)
    prev=2, next=0  diff=2  -> NO-OP         (opposite coil)
    prev=3, next=1  diff=2  -> NO-OP         (opposite coil)
```

### Why It Matters

> The `(next - prev + 4) % 4` trick sidesteps Go's sign-of-dividend
> modulo rule: `-3 % 4 == -3` in Go, not `1`. Adding 4 first shifts
> the domain non-negative, so a backward step like prev=3, next=0
> gives `(0 - 3 + 4) % 4 == 1 % 4 == 1` -- the correct forward
> distance -- while the true backward step prev=0, next=3 gives
> `(3 - 0 + 4) % 4 == 7 % 4 == 3`.

### How the Code Works

**`stepPhase`** (`disk/drive.go:38-54`) -- the diff dispatch and clamp:

```go
func (d *drive) stepPhase(prev, next int) {
    diff := (next - prev + 4) % 4
    switch diff {
    case 1:
        d.halfTrack++
    case 3:
        d.halfTrack--
    // diff == 2 means opposite coil; no clean step, ignore.
    }
    if d.halfTrack < 0 {
        d.halfTrack = 0
    }
    if d.halfTrack > maxHalfTrack {
        d.halfTrack = maxHalfTrack
    }
}
```

`diff = 2` has no `case` -- the switch does nothing; the clamp leaves
`halfTrack` unchanged. `diff = 0` cannot reach `stepPhase` in practice
(the guard in `phaseOn` below prevents it).

**`activePhase`** (`disk/drive.go:56-69`): returns the single-on coil index, or
-1 if none or multiple coils are on (quarter-track blocker).

**`phaseOn`** (`disk/drive.go:71-79`): captures prev single-coil state,
energises the new coil, steps if `prev >= 0 && prev != phase`.
`d.phases[phase] = true` runs BEFORE `stepPhase` (matches real-hardware order).

**`phaseOff`** (`disk/drive.go:81-84`): clears the flag only; cam stays put.

### Real-World Analogy

A combination lock with four tumblers: "0" to "1" (forward), "0" to "3"
(backward), "0" to "2" (ambiguous, no movement).

## Section 4: Lazy Nibble Cache (Per-Track Materialisation)

### What It Is

`nibbles [tracksPerDisk][]uint8` at `disk/drive.go:12` is a 35-element array
of inner slices. Each inner slice starts `nil`; the first `trackData` call for
a given track allocates the buffer via `EncodeTrack`.

### Why It Matters

Pre-encoding all 35 tracks at Mount would allocate ~223 KB per drive (35 x 6384
bytes; see `13.walkthrough_disk_gcr.md` §7) regardless of actual use. A cold
boot touches 6-8 tracks; lazy allocation keeps memory proportional to usage.

> The cache is write-through. When a write lands via the Q6/Q7=1
> WRITE RUN path, the controller does `d.nibbles[track][d.nibblePos]
> = c.writeReg; d.dirty[track] = true` (see
> `15.walkthrough_disk_controller.md` §6). The in-memory nibble
> buffer IS the authoritative record until MOTOROFF triggers a
> flush (see `12.walkthrough_disk_image.md` §6). This is why the
> cache is not just a performance optimisation -- it also carries
> the not-yet-flushed user data. An invalidation that discarded a
> dirty-but-not-flushed track would lose user work.

### How the Code Works

`trackData` is the sole materialisation site (`disk/drive.go:86-98`):

```go
func (d *drive) trackData(order SectorOrder) []uint8 {
    if d.image == nil {
        return nil
    }
    t := d.halfTrack / 2
    if d.nibbles[t] == nil {
        sectors := d.image.trackSectors(t, order)
        d.nibbles[t] = EncodeTrack(sectors, 254, t, order)
    }
    return d.nibbles[t]
}
```

The nil guard defends against an empty slot; the controller adds a second guard
at `disk/controller.go:428-431`. `EncodeTrack(sectors, 254, t, order)`: vol
byte hardcoded `254` (DOS 3.3 standard); all four args are governed by
`13.walkthrough_disk_gcr.md` §5. Read path: `disk/controller.go:433`; write
path: `disk/controller.go:402`. Swap resets all caches to nil/false
(`disk/controller.go:205-208`); see §6.

## Section 5: Activity Timestamps -- Wall-Clock, Not Cycle-Based

### What It Is

Two `time.Time` fields at `disk/drive.go:26-27` record the wall-clock instant
at which the most recent nibble passed the head, driving the title-bar
disk-activity indicator.

### Why It Matters

F12 turbo mode runs emulated cycles ~10x faster than wall-clock. A cycle-delta
indicator would misbehave -- too brief in turbo, or too persistent at normal
speed. The struct comment at `disk/drive.go:16-25` is the authoritative
specification for both the wall-clock choice and the goroutine access contract:

> Activity tracking for the host UI window-title indicator.
> Stamped with nowFn() each time a real nibble passes the head.
> Read by HadRecentRead/HadRecentWrite against a wall-clock window
> so the indicator stays visible regardless of turbo/normal speed.
> Zero value (time.Time{}) means "never had activity".
>
> Single-goroutine access only (emulator is single-goroutine outside
> the SDL audio callback, which does not touch these fields). If a
> future refactor adds goroutines here, these reads/writes become
> racy and must be protected.

General rule: UI-layer timers are always wall-clock. See also
`11.walkthrough_speaker.md` §4.3 for the same choice in speaker frame pacing.

### How the Code Works

**500 ms window** -- `disk/controller.go:96-101`:
`const recentActivityWindow = 500 * time.Millisecond`. The comment: "500 ms is
well above the perceptual threshold for a single blink (~100 ms) and short
enough that a cleanly-finished read fades quickly."

**Injection seam** -- `nowFn` at `disk/controller.go:22-24` defaults to
`time.Now`. Tests override it without `time.Sleep`.

**Stamp sites**: `disk/controller.go:460` stamps `d.lastReadAt` at the end of
a successful nibble advance (READ data, Q6=0, Q7=0); `disk/controller.go:410`
stamps `d.lastWriteAt` after a WRITE RUN commit (Q6=1, Q7=1). READ status and
WRITE load do NOT stamp -- only paths moving a real nibble count.

**Consumers** -- `HadRecentRead` / `HadRecentWrite` at `disk/controller.go:106-128`.
`IsZero()` returns false immediately. Swap resets both
(`disk/controller.go:202-203`).

## Section 6: Cached `label` + Mount / Swap / Eject Lifecycle (Drive-Side View)

### What It Is

`label string` at `disk/drive.go:32` holds the pre-computed short display name.
The comment at `disk/drive.go:29-32`:

> label is the cached display name for UI (title bar). Set by the
> controller in Mount/Swap/Eject -- never written from the CPU-facing paths.
> Empty string when no image is mounted.

### Why It Matters + How the Code Works

**Label caching**: `filepath.Base` + `filepath.Ext` allocate on every call.
Caching keeps the ~1 Hz title-bar refresh to a pointer deref + string read.
`deriveLabel` at `disk/controller.go:287-294` returns basename minus extension:
`foo.dsk` -> `foo`. `DriveLabel(driveIdx)` at `disk/controller.go:273-282`
is the consumer; invalidation happens only at Mount / Swap / Eject.

**Hot-swap fidelity**: real hardware preserves drive mechanism state across a
disk swap; the emulator must match or programs seeking during a swap crash.

**L14-7: Hot-swap preservation rules.** The authoritative source is the `Swap`
doc comment at `disk/controller.go:143-150`:

> Real-hardware fidelity: halfTrack (head position), phases, and
> motorOn are preserved (those are physical/mechanical -- on real
> hardware, changing floppies doesn't move the head or stop the
> spindle). Per-image state (nibble cache, nibblePos, dirty flags,
> activity timestamps, writeProt) resets. Controller-level in-flight
> state for THIS drive (c.latch, c.writeReg) is also cleared when the
> drive being swapped is the currently selected drive -- those
> represent a nibble or write byte derived from the old image and
> would corrupt the new image if left intact.

**Diagram 4: Hot-swap state-preservation table**

```text
  +--------------------------------+---------------------------+------------------------+
  | Field                          | After Swap                | Source cite            |
  +--------------------------------+---------------------------+------------------------+
  | d.halfTrack                    | KEEP                      | disk/drive.go:9        |
  | d.phases[0..3]                 | KEEP                      | disk/drive.go:8        |
  | d.motorOn                      | KEEP                      | disk/drive.go:10       |
  +--------------------------------+---------------------------+------------------------+

  | d.dirty[0..34]                 | RESET -> false            | controller.go:205-208  |

  +--------------------------------+---------------------------+------------------------+
  | c.latch                        | RESET -> 0 (selected only)| controller.go:224      |

```

**The `c.lastCycle` intentional-no-reset.** The comment at
`disk/controller.go:160-166`:

> c.lastCycle is intentionally NOT reset. The next readDataLatch
> call will compute delta = now - c.lastCycle; if that delta is huge
> (drive was deselected for many seconds, or this is the first read
> after a long idle), the steps = delta / cyclesPerNibble computation
> is clamped by the modulo-wrap at disk/controller.go:295 (steps =
> steps % uint64(nLen)), so nibblePos wraps cleanly within one
> revolution regardless of gap size. That clamp -- not any "global
> pacing" notion -- is the actual safety net.

Note: the internal line reference `disk/controller.go:295` in that comment has
drifted due to a later refactor. The modulo-wrap clamp is now at
`disk/controller.go:452-455`. The mechanism is unchanged.

The drive-state reset code at `disk/controller.go:195-208` sets all Magnetic
and Activity fields to their zero values exactly as the table shows.

**Mount vs Swap**: `Mount` is "drive was empty, put a disk in". `Swap` is
"drive had a disk; replace or eject" and adds a flush-first step at
`disk/controller.go:189-193`. **Eject** (`disk/controller.go:253-258`) is a
readability-only wrapper -- `Swap(driveIdx, "")` with the empty-path branch
leaving `d.image == nil`. See `12.walkthrough_disk_image.md` §6 for the flush
path.

### Real-World Analogy

A cassette-tape Walkman: the tape (image, nibbles, dirty, writeProt, label)
goes in and out; the motor (`motorOn`), the playhead position (`halfTrack`,
`phases`), and the mode knob (`q6`, `q7`) stay where they were.

## Section 7: `device.go` -- The `Switches` Shim at $C0E0-$C0EF

`disk/device.go` (31 LOC) adapts `*Controller` to the `bus.Device` interface.
It is the bridge from the 6502 address bus to the drive-facing methods in §§1-6.
This section drops the quadrant headers and walks the two methods directly.

**Structural parallel.** Three other softswitch-style `bus.Device` shims exist in the emulator:
`io.SoftSwitches` ($C000-$C07F; `05.walkthrough_io.md`),
`languageCard.Switches` ($C080-$C08F; `10.walkthrough_languagecard.md` §6),
`speaker.Device` ($C030; `11.walkthrough_speaker.md` §2). All four hold a
pointer to the stateful object and forward accesses into it.

**Struct and constructor** (`disk/device.go:1-10`): the struct comment says
"Map AFTER io.SoftSwitches so this device wins the address-decode race
(bus last-mapping-wins; see bus.go)" -- that mapping-order line is load-bearing;
see `04.walkthrough_bus.md`. The Write method note at `disk/device.go:22-23`:
"all 16 addresses are chip-select strobes" -- the hardware latches the address
decode line, not the data bus. `v` is discarded for all 16 offsets except the
special case below. `Strobe` handles the full dispatch
(`15.walkthrough_disk_controller.md` §3).

**L14-8: The $C0ED / Q7=1 special case (both Read and Write).**

**Diagram 5: $C0ED / Q7=1 special-case flow**

```text
  Bus Read($C0ED)                        Bus Write($C0ED, v)
       |                                        |
       v                                        v
  Switches.Read(addr)                    Switches.Write(addr, v)
       |                                        |
  addr&0x0F == 0x0D && s.c.q7 ?         addr&0x0F == 0x0D && s.c.q7 ?
       |                                        |
    YES   |   NO                           YES      |   NO
     v         v                            v             v
  q6=true   Strobe(addr)             Q6WriteReg(v)   Strobe(addr)
  return 0  (return result)          q6=true         (return)
  (no Strobe)                        return
                                     (no Strobe)

  All other 15 addresses, and $C0ED when q7==false, forward to Strobe.
```

**Read path** (`disk/device.go:12-20`):

```go
func (s *Switches) Read(addr uint16) uint8 {
    // $C0ED write in Q7=1 mode loads writeReg; on read Q6H just strobes.
    if addr&0x0F == 0x0D && s.c.q7 {
        s.c.q6 = true
        return 0
    }
    return s.c.Strobe(addr)
}
```

When q7=1, the shim sets `q6=true` and returns 0 without calling Strobe.
In write mode $C0ED is Q6H -- a flip-flop set, no data to return.

**Write path** (`disk/device.go:22-31`):

```go
func (s *Switches) Write(addr uint16, v uint8) {
    if addr&0x0F == 0x0D && s.c.q7 {
        s.c.Q6WriteReg(v)
        s.c.q6 = true
        return
    }
    s.c.Strobe(addr)
}
```

This is the one access in $C0E0-$C0EF where `v` is meaningful. `Q6WriteReg(v)`
at `disk/controller.go:494-499` latches `v` into `writeReg`. The next $C0EC
access while Q6=1 and Q7=1 commits that byte to the nibble buffer (covered in
`15.walkthrough_disk_controller.md` §6). Without this special case, `Strobe`
would discard `v`.

## Section 8: Design Decisions and Hardware Reality

**Q1 -- Why does `halfTrack` go up to 69 and not 70?**

`70 / 2 = 35` is out of bounds for `nibbles[tracksPerDisk]`. `maxHalfTrack`
at `disk/gcr.go:49-52` documents this; the clamp at `disk/drive.go:48-53`
enforces it.

**Q2 -- Why is quarter-tracking not emulated?**

`activePhase()` returns -1 for multiple coils; `phaseOn` only steps when
`prev >= 0`. Simultaneous coils block any step. Quarter-track support would
require partial-flux signal degradation modelling.

**Q3 -- Why is the `diff == 2` opposite-coil case a no-op?**

A 180-degree cam rotation is physically direction-ambiguous; real Disk II drives
also do not commit a step in this state (the cam axis is mechanically unstable
under an opposite-coil pulse). The emulator matches the hardware: no `case 2:`
at `disk/drive.go:41-46`.

**Q4 -- Why is the nibble cache lazy instead of pre-encoded at Mount?**

Pre-encoding allocates ~223 KB per drive regardless of actual track usage.
Lazy allocation at `disk/drive.go:92-97` keeps memory proportional to visited tracks.

**Q5 -- Why are activity timestamps wall-clock and not cycle-based?** (load-bearing)

F12 turbo runs cycles ~10x faster than wall-clock. A cycle-delta indicator
would fade before the user sees it. Wall-clock keeps the 500 ms window
consistent. See `disk/drive.go:16-25` and `disk/controller.go:96-101`.

**Q6 -- Why cache the drive label instead of recomputing it each refresh?**

`filepath.Base` + `filepath.Ext` allocate on every call. Caching in
`drive.label` (`disk/drive.go:29-32`) makes the ~1 Hz title-bar refresh a
string read. Invalidation happens only at Mount / Swap / Eject.

**Q7 -- Why does hot-swap preserve mechanical state but reset magnetic state?** (load-bearing)

Hardware fidelity: swapping floppies on real hardware does not move the head or
stop the spindle. `halfTrack`, `phases`, and `motorOn` are mechanical attributes
of the drive mechanism. The cartridge (image, nibbles, dirty, writeProt, label,
stamps) is what changed. See `disk/controller.go:143-150` (quoted in §6). The
`c.lastCycle` intentional-no-reset relies on the modulo-wrap at
`disk/controller.go:452-455` as the safety net.

**Q8 -- Why does `$C0ED` have a special case in both shim paths?** (load-bearing)

It is the one $C0Ex softswitch where the data byte carries information.
`Strobe(0xC0ED)` discards `v`; the shim at `disk/device.go:15-17` (Read) and
`disk/device.go:24-29` (Write) routes writes to `Q6WriteReg(v)`. See
`15.walkthrough_disk_controller.md` §6 for the write-run path.

## Section 9: Summary / What Is Next / Quick Reference

> A drive in this emulator is 98 lines of Go modelling a 4-coil
> stepper motor, a half-track head position (0..69), a lazy per-track
> GCR nibble cache, and wall-clock activity timestamps. The four
> methods `stepPhase`, `phaseOn`, `phaseOff`, and `trackData` cover
> everything the controller needs to know about the physical side
> of the Disk II. Hot-swap preserves the mechanical state (head
> position, stepper coils, motor spin) and resets the magnetic state
> (image, nibbles, dirty flags, write-protect, label, activity
> timestamps) -- the same split a real-hardware floppy swap produces.
> A thin 31-line `Switches` shim (`device.go`) at $C0E0-$C0EF forwards
> every bus access to the controller's `Strobe` method, with the one
> special case that `$C0ED` in write mode latches the data byte into
> `writeReg` instead of merely flipping a flip-flop.
