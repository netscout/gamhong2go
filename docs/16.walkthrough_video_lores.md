## Section 0: Background -- What 40x48 Lo-Res Graphics Was on the Apple II+

### What It Is

The Apple II+ "GR" mode is what BASIC enters when you type the `GR` statement. The user sees a 40-column by 48-row grid of colored squares. Each square is one of 16 Apple II palette colors. The grid is formed from the same 1 KB text-screen buffer at `$0400`-`$07FF` that text mode reads -- no new memory is allocated, no separate frame buffer. The `GRAPHICS` softswitch (`$C050`) merely changes *how* the video circuitry interprets the bytes already in that buffer.

Text mode sees each byte as a character code; lo-res mode sees it as two vertically stacked 7x4-pixel color blocks, one per nibble. Doubling the rows from 24 to 48 costs nothing in memory -- the top and bottom halves of each text cell become two separate colored blocks.

The `video/lores.go` source comment at `video/lores.go:24-31` summarizes these facts: 40x48 lo-res screen, low nibble = top block color, high nibble = bottom block color, each block 7x4 pixels, mixed mode renders the bottom 4 text rows as text instead.

### Why It Matters

Lo-res sits in the middle of the Apple II+ mode taxonomy:

```text
  textMode=true               -> text       (40x24 chars)
  textMode=false, hiRes=false -> lo-res     (40x48 color blocks)   <-- this doc
  textMode=false, hiRes=true  -> hi-res     (280x192 pixels)
  mixedMode=true              -> graphics top + text bottom (any graphics mode)
```

The dispatch is handled by `Render()` at `video/video.go:44-51` (covered in `08.walkthrough_video.md` §7). Lo-res is the `default` branch -- it fires when neither `textMode` nor `hiRes` is true. At power-on, `TextMode=true` (see `io/softswitches.go:56`), so the machine starts in text mode. Lo-res is only reached after software reads `$C050` to clear `TextMode`, with `HiRes` still false (its zero-value default).

A mosaic-tile wall. Each tile slot in the 40x24 grid can hold either a character stencil (text mode) or a pair of stacked colored tiles (lo-res mode). The wall itself -- the 1 KB of RAM at `$0400`-`$07FF` -- never changes. Only the interpretation rule changes when you flip the `GRAPHICS` lever.

## Section 1: The 40x24 Text-Mode Buffer Seen As 40x48 Two-Color Bytes

### What It Is

The lo-res screen is backed by the same text-mode buffer. There is no separate page, no copy. The same 960 bytes (40 x 24) of text cells become 1,920 colored blocks (40 x 48) because each byte carries two nibbles, each naming a color.

The geometry constants shared between text and lo-res are declared at `video/video.go:4-11`:

```go
const (
    TextCols = 40
    TextRows = 24
    CharW    = 7   // pixels per character width
    CharH    = 8   // pixels per character height
    ScreenW  = TextCols * CharW // 280 pixels
    ScreenH  = TextRows * CharH // 192 pixels
)
```

### Why It Matters

The hardware video circuitry has one screen-memory scanner. The `GRAPHICS`/`TEXT` softswitch picks the interpretation path downstream of the scanner, not a different scanner. Both modes issue the same 960 reads from `$0400`-`$07FF` per frame.

The outer loop at `video/lores.go:38-45` iterates 24 text rows and 40 columns -- exactly matching `renderTextRows()` in `video/video.go`. The only difference is what the inner loop does with the byte it fetches at `video/lores.go:42`:

```go
b := v.RAM[baseAddr+uint16(col)]
```

`v.RAM` is the same 64 KB slice the CPU writes to (`video/video.go:21`: "Direct reference to main RAM"). No copy. Software mutations between `Render` calls are seen in the next frame (L16-7).

### How the Code Works

The geometry doubling is expressed in a single line at `video/lores.go:46`:

```go
loResRow := row * 2
```

Each text row (0-23) produces two lo-res rows (0-1, 2-3, ..., 46-47). The top block is painted at `row*CharH` (y=0, 8, 16, ...) and the bottom block at `row*CharH+4`. Two stacked 4-scanline blocks fill the same 8 scanlines as one text character.

**Diagram 1: Same RAM, two interpretations**

```text
  Same RAM ($0400-$07FF, 1024 bytes -- 960 used, 64 wasted)

  Text mode interpretation:         Lo-res mode interpretation:
  40 cols x 24 rows                 40 cols x 24 rows
  each byte = one character         each byte = TWO colored blocks

  col:   0    1    2   ...  39      col:  0   1   2  ...  39
       +----+----+----+-...+----+       +---+---+---+-...+---+
  r 0  | 'H'| 'I'| '!'|... |    |  r 0 |t=2|t=5|t=0|... |t=A|  top nibble
       +----+----+----+-...+----+       |b=7|b=3|b=0|... |b=1|  bot nibble
  r 1  |    |    |    |... |    |       +---+---+---+-...+---+
       +----+----+----+-...+----+  r 1  |t=...                |
       ...                              +---+---+---+-...+---+
  r 23 |    |    |    |... |    |       ...
       +----+----+----+-...+----+  r 23 ...

  Text: 24 rows x 8 scanlines x 7 px    Lo-res: 48 rows x 4 scanlines x 7 px
          = 192 scanlines tall                   = 192 scanlines tall
          (60 Hz refresh)                        (same 60 Hz, same raster)
```

### Real-World Analogy

A dual-purpose printing stencil. The paper (RAM) is the same. Flip one lever and the stencil traces letter outlines; flip the other and the same holes punch out two-color tile patterns. You never re-print the paper to switch modes.

## Section 2: The 16-Color Lo-Res Palette

### What It Is

The file opens with the palette table at `video/lores.go:3-22`: a package-level `var loResColors = [16][3]uint8` prefaced by the comment "Apple II lo-res palette -- 16 colors. Each entry is [R, G, B]. These match the NTSC artifact colors."

### Why It Matters

The table is indexed *directly* by the 4-bit color nibble -- no remap. `loResColors[b & 0x0F]` returns the RGB triple for the top block; `loResColors[(b >> 4) & 0x0F]` does the same for the bottom block. If you read a text-mode ASCII byte as lo-res (say, capital 'A' = `$41`), the two nibbles `0x1` and `0x4` index palette slots 1 (Magenta) and 4 (Dark Green) -- exactly what an Apple II+ shows if you write 'A' to text-page memory and flip to GR without clearing.

Alpha is not stored in the table. It is filled separately at `video/lores.go:72` inside `fillBlock` (`v.Pixels[offset+3] = 0xFF`).

### How the Code Works

`loResColors` is a fixed array, not a slice; 16 entries, each a 3-byte RGB triple. Index 0 is Black, index 15 is White. The values approximate the NTSC chroma phases the Apple II hardware produced on a composite TV.

**Diagram 2: Palette table (loResColors[0..15], RGB from lores.go:6-21)**

```text
  idx  name            R    G    B      idx  name            R    G    B
  ---  --------------  ---  ---  ---    ---  --------------  ---  ---  ---
   0   Black             0    0    0     8   Brown           136   85    0
   1   Magenta (Deep Red)221  0   51     9   Orange          255  102    0
   2   Dark Blue          0    0  153    10  Grey 2          170  170  170
   3   Purple (Violet)  221   34  221    11  Pink            255  153  136
   4   Dark Green         0  119   34    12  Green (Light)    17  221    0
   5   Grey 1            85   85   85    13  Yellow          255  255    0
   6   Medium Blue       34   34  255    14  Aquamarine       68  255  153
   7   Light Blue       102  170  255    15  White           255  255  255
```

The 16 RGB values in the table above are verbatim from `video/lores.go:6-21`.

### Real-World Analogy

A 16-tile paint-chip fan. Each tile has a printed label: "0 Black", "1 Magenta", and so on. Wherever the lo-res code needs a color, it holds up a 4-bit nibble and reads the matching fan tile's RGB values.

## Section 3: The Headline Exhibit -- Two Color Nibbles Per Byte

### What It Is

Each byte in the text-page buffer encodes two vertically stacked color blocks. The byte is split into two 4-bit nibbles; each nibble indexes the `loResColors` table. The result is two independent colors filling the top and bottom halves of one text-cell slot.

The two unpack lines at `video/lores.go:43-44` are the heart of the renderer:

```go
topColor := b & 0x0F
botColor := (b >> 4) & 0x0F
```

### Why It Matters -- CRITICAL Correction

> It is tempting to guess that the high nibble (bits 7..4) names the top
> block and the low nibble (bits 3..0) names the bottom -- because "higher
> bits" feels like "higher position on screen". **That is backward.** The
> code pairing is:
>
> `low nibble -> top block (scanlines 0..3 within the cell)`
> `high nibble -> bottom block (scanlines 4..7 within the cell)`
>
> Verified at `video/lores.go:43-54`. This convention matches real Apple II
> hardware and the code comment at `video/lores.go:26-27`. Readers who try
> to reverse-engineer colors from memory dumps without looking at hardware
> docs always guess wrong first -- this call-out is the same warning real
> Apple II programmers needed in 1978.

### How the Code Works

**Worked example: byte `$2A` at RAM address `$0400` (row 0, col 0)**

```text
  $2A = 0b_0010_1010

  topColor = 0x2A & 0x0F = 0x0A = 10  -> Grey 2   (170, 170, 170)
  botColor = (0x2A >> 4) & 0x0F = 0x02 = 2 -> Dark Blue  (0, 0, 153)
```

Block size: 7 pixels wide (`CharW=7`, one text-cell width) by 4 scanlines tall (half of `CharH=8`). Two blocks stacked = 8 scanlines = the same vertical real estate as one text character.

The two `fillBlock` calls at `video/lores.go:47-54` paint those blocks:

```go
if loResRow < maxLoResRow {
    v.fillBlock(col, row*CharH, CharW, 4, loResColors[topColor])
}
if loResRow+1 < maxLoResRow {
    v.fillBlock(col, row*CharH+4, CharW, 4, loResColors[botColor])
}
```

Top block starts at `(col*7, row*8)` in the 280x192 `v.Pixels` buffer. Bottom block starts at `(col*7, row*8 + 4)`. Pixel buffer is RGBA, 4 bytes per pixel.

**Diagram 3: Byte-to-block expansion, one cell worked end-to-end**

```text
  One text-cell byte at RAM[$0400]          One on-screen cell
  (row 0, col 0 after textLineAddr)         (col 0, row 0 of the
                                            40x24 grid)

    bit  7 6 5 4 3 2 1 0                    +-------+
    val  0 0 1 0 1 0 1 0  = $2A             |       |  4 scanlines
         \____/ \_____/                     | top   |  color = low
         high=2   low=A                     | block |  nibble = $A
         (bot)    (top)                     |       |  = Grey 2
                                            +-------+  ---------
                                            |       |  4 scanlines
                                            | bot   |  color = high
                                            | block |  nibble = $2
                                            |       |  = Dark Blue
                                            +-------+
                                            7 px wide (CharW)

  Pixel buffer writes (lores.go:49 / lores.go:53):
    fillBlock(col=0, py=0, w=7, h=4, color=loResColors[0xA])   // top
    fillBlock(col=0, py=4, w=7, h=4, color=loResColors[0x2])   // bot
```

> If you ever start wondering "wait -- should the high nibble go on top,
> or on the bottom?", the answer in this emulator is **always and exactly**:
> high nibble = bottom block (later in vertical scanline order), low nibble =
> top block. The pattern is the same for all 40 columns and all 24 rows.
> Reading the code at `video/lores.go:43-44` settles it: the low bits are
> extracted first and filled first, at the smaller `py` coordinate.

### Real-World Analogy

A double-decker bus token. Each token (byte) is a rectangular chip stamped with two halves; the left half (low nibble) tells you the top-floor seat color, the right half (high nibble) tells you the bottom-floor seat color. The conductor (render loop) visits each seat in turn.

## Section 4: Screen-to-Memory Address Scrambling (Shared with Text Mode)

### What It Is

`RenderLoRes` calls `textLineAddr(row)` at `video/lores.go:39` to find the base address of each text row:

```go
baseAddr := textLineAddr(row)
```

This is the same function text mode uses. It is defined at `video/video.go:115-117`:

```go
func textLineAddr(row int) uint16 {
    return 0x0400 + uint16(row%8)*0x80 + uint16(row/8)*0x28
}
```

### Why It Matters

The underlying byte layout for lo-res is exactly the text layout. The scramble was chosen once for text mode and is inherited for free by lo-res. This is also why `textLineAddr` lives in `video/video.go`, not in either `chargen.go` or `lores.go` -- it is a package-shared helper.

For a full 24-row table and the hardware wiring rationale, see `08.walkthrough_video.md` §5 or `06.walkthrough_main_phase3.md` §4 (both reprint the formula and a complete address table; `video/video.go:104-114` carries the doc comment). This doc does not re-derive the scramble; it only shows the call site.

### How the Code Works

Formula breakdown:
- `row % 8` picks one of 8 "super-rows" (0-7). Each super-row starts `$80` bytes after the previous.
- `row / 8` picks one of 3 "thirds" (0-2). Each third starts `$28` (= 40) bytes after the previous.
- Their sum added to `$0400` is the base address of the row's 40-byte strip.

**Diagram 4: Formula sanity check (three rows)**

```text
  baseAddr(row) = $0400 + (row % 8) * $80 + (row / 8) * $28

  row  0: $0400 + 0*$80 + 0*$28 = $0400
  row  8: $0400 + 0*$80 + 1*$28 = $0428
  row 16: $0400 + 0*$80 + 2*$28 = $0450   -- used in §3 example

  Full 24-row table: see 08.walkthrough_video.md §5 (Diagram 5) or
  06.walkthrough_main_phase3.md §4 (Diagram 4).
```

### Real-World Analogy

A shared street-address system across two cities that happen to use identical postal codes. Text mode delivers letters to those addresses; lo-res delivers colored-tile bundles. The mailroom (`textLineAddr`) does not care which product is being delivered -- it decodes the row number into a box number.

## Section 5: Page 1, Page 2, and the Unimplemented Lo-Res Page Switch

### What It Is

On real Apple II+ hardware, `$C054` / `$C055` select page 1 (`$0400`-`$07FF`) or page 2 (`$0800`-`$0BFF`) for both text and lo-res. In this emulator, `RenderLoRes` does not honor the `Page2` softswitch. The function signature at `video/lores.go:32` has no `page2` parameter:

```go
func (v *Video) RenderLoRes(mixed bool)
```

### Why It Matters

The dispatch at `video/video.go:44-51` shows the asymmetry directly:

```go
case hiRes:
    v.RenderHiRes(page2, mixedMode)   // page2 threaded through
default:
    v.RenderLoRes(mixedMode)          // page2 dropped here
```

Hi-res gets `page2`; lo-res does not. `docs/08.walkthrough_video.md:707` already names "text page 2 at `$0800`-`$0BFF` explicit support" as genuinely future work.

**Diagram 5: Dispatch wiring -- where page2 is dropped**

```text
  main.go:374
    vid.Render(sw.TextMode, sw.MixedMode, sw.HiRes, sw.Page2)
                                                       |
                                                       v
  video.go:36-52                                      page2
    func (v *Video) Render(textMode, mixedMode,        |
                           hiRes, page2 bool) {        |
                                                       v
      switch {                              text mode: ignored (doc 08)
      case textMode: v.RenderText()         ----------> no page2 param
      case hiRes:    v.RenderHiRes(page2, mixedMode)   <- threaded
      default:       v.RenderLoRes(mixedMode)          <- DROPPED HERE
      }                                                  (known gap)
    }
```

### How the Code Works

The `Page2` bool IS maintained in `io/softswitches.go:91-96` (cases `$C054`/`$C055`) and IS passed through `main.go:374` into `Render()`. The signal simply stops at the lo-res branch. `textLineAddr` has no `page2` parameter either -- the base `$0400` is hardcoded. Software that writes lo-res data to `$0800`-`$0BFF` and flips `$C055` sees nothing change on screen.

> The `Page2` softswitch is not broken -- it is fully wired at the I/O layer
> (`io/softswitches.go:91-96`), fully passed through the main loop
> (`main.go:374`), and fully honored by the hi-res renderer
> (`hires.go:22-34, :60-67`). What is missing is one extra parameter on
> `RenderLoRes` and one extra branch in `textLineAddr` that would add
> `$0400` or `$0800` as the base address. The data path to do this already
> exists; the interpretation layer for lo-res just ignores the signal today.
> Doc 08 §9 lists this as "genuinely future work" (`docs/08.walkthrough_video.md:707`).

### Real-World Analogy

A letter with two possible return addresses printed on it. The postal service reads the "from" field; text and hi-res clerks read it correctly. The lo-res clerk has a rubber stamp that always says "return to $0400" and stamps over the form without reading.

## Section 6: Mixed Mode -- Rows 0-19 As Graphics, Rows 20-23 As Text

### What It Is

When `mixed=true`, the bottom 4 text rows (rows 20-23, corresponding to lo-res rows 40-47) are rendered as text characters rather than colored blocks. Two mechanisms cooperate:

1. `maxLoResRow` is clamped to 40 (`video/lores.go:33-36`), suppressing `fillBlock` calls for lo-res rows 40-47.
2. A tail call to `renderTextRows(20, 24)` re-reads the same 4 rows from RAM and renders them as characters (`video/lores.go:58-61`).

### Why It Matters

The row boundary is hardcoded at text row 20 (`renderTextRows(20, 24)`) and not derived from `maxLoResRow` or `CharH`. Mixed mode always uses exactly 4 text rows at the bottom -- the same convention `08.walkthrough_video.md` §4 describes for hi-res mixed mode. `renderTextRows` is defined at `video/video.go:62`; `05.walkthrough_io.md` §3d covers the `$C052`/`$C053` mixed-mode toggle.

### How the Code Works

The outer loop (`video/lores.go:38`) still iterates all 24 text rows. When `mixed=true`, `maxLoResRow=40` (`video/lores.go:35`) prevents the two `fillBlock` calls for text rows 20-23. The bytes at those rows ARE still fetched from RAM -- the guards at `video/lores.go:48` and `video/lores.go:52` suppress the pixel writes but do not skip the fetch. After the loop, the tail at `video/lores.go:58-61` fires:

```go
if mixed {
    v.renderTextRows(20, 24)
}
```

`renderTextRows(20, 24)` re-reads the same four rows' worth of RAM bytes through `CharGenROM` and paints characters. The same RAM, interpreted twice -- first as lo-res (suppressed), then as text (drawn).

**Diagram 6: Mixed-mode row partition**

```text
  mixed = false (pure lo-res)           mixed = true (mixed mode)

  text   lo-res    screen rows          text   lo-res   screen rows
  row    rows      (scanlines)          row    rows     (scanlines)
  ---    ------    -----------          ---    ------   -----------
   0      0,1       0-7   (lores)        0      0,1      0-7   (lores)
   1      2,3       8-15  (lores)        1      2,3      8-15  (lores)
   2      4,5      16-23  (lores)        2      4,5     16-23  (lores)
   ...    ...      ...                   ...    ...     ...
  19     38,39    152-159 (lores)       19     38,39   152-159 (lores)
  20     40,41    160-167 (lores)       20     --      160-167 (TEXT)  <-- !
  21     42,43    168-175 (lores)       21     --      168-175 (TEXT)
  22     44,45    176-183 (lores)       22     --      176-183 (TEXT)
  23     46,47    184-191 (lores)       23     --      184-191 (TEXT)

  maxLoResRow = 48                      maxLoResRow = 40
  no tail call                          tail: renderTextRows(20, 24)
```

> In mixed mode, the bottom 4 text rows are rendered **by the text
> renderer** (`renderTextRows`), not by filling with a background color and
> not by blanking the rest. The `maxLoResRow=40` clamp silences the graphics
> writes for rows 40-47; then the tail call re-reads the same 4 rows' worth
> of RAM bytes through `CharGenROM` and paints characters. The same RAM,
> interpreted twice -- first as lo-res (suppressed), then as text (drawn).

### Real-World Analogy

A hybrid stage curtain. The top 40 rows drop a painted color-tile backdrop; the bottom 8 rows lift a text scroll instead. Both halves use the same curtain hardware; the `mixed` lever decides which half does which job.

## Section 7: End-to-End Render Trace -- From Softswitch Flip to Colored Pixel

This section stitches lo-res into the rest of the emulator with a single concrete worked example. We follow byte `$2A` written to `$0400` all the way to a colored pixel in the SDL window.

**1. Precondition.** Software has executed:
- `LDA $C050` -- clears `TextMode` (`io/softswitches.go:79-80`)
- `LDA $C052` -- clears `MixedMode` (`io/softswitches.go:85-86`; irrelevant to this worked example but completes the softswitch snapshot)
- `LDA $C056` -- clears `HiRes` (`io/softswitches.go:97-98`)

Resulting state: `TextMode=false`, `MixedMode=false`, `HiRes=false`, `Page2=false`.

**2. Software writes a byte.** `STA $0400` with A=`$2A`. `RAM[$0400] = $2A`. See `03.walkthrough_memory.md` for the RAM `.Write` path.

**3. Frame boundary.** `main.go:374` runs `vid.Render(false, false, false, false)`. See `08.walkthrough_video.md` §7 for the full frame-loop pipeline.

**4. Dispatch.** `video/video.go:44-51`: `textMode=false` skips case 1; `hiRes=false` skips case 2; `default` branch runs `v.RenderLoRes(false)`.

**5. RenderLoRes setup.** `mixed=false` so `maxLoResRow=48` (`video/lores.go:33-36`).

**6. Outer loop, row=0.** `baseAddr := textLineAddr(0) = $0400` (`video/video.go:116`).

**7. Inner loop, col=0.** `b := v.RAM[$0400] = $2A` (`video/lores.go:42`).
- `topColor = 0x2A & 0x0F = 0x0A = 10` -- Grey 2 (170, 170, 170).
- `botColor = (0x2A >> 4) & 0x0F = 0x02 = 2` -- Dark Blue (0, 0, 153).
- `loResRow = 0 * 2 = 0`.

**8. Top-block fillBlock.** `loResRow=0 < maxLoResRow=48`, so `v.fillBlock(0, 0*CharH, CharW, 4, loResColors[10])` (`video/lores.go:49`).
- Inner loops `y=0..3`, `x=0..6`: 28 pixels written as (170, 170, 170, 255).

**9. Bottom-block fillBlock.** `loResRow+1=1 < maxLoResRow`, so `v.fillBlock(0, 0*CharH+4, CharW, 4, loResColors[2])` (`video/lores.go:53`).
- Pixels `(x=0..6, y=4..7)` become (0, 0, 153, 255).

**10. Loop continues.** Cols 1-39, then rows 1-23 fill the rest of the 40x48 grid.

**11. Frame commit.** `main.go` uploads `v.Pixels` to the SDL texture and calls `SDL_RenderCopy`. See `08.walkthrough_video.md` §7 or `18.walkthrough_main.md`.

**12. Observable result.** The top-left text cell (col 0, row 0) shows a Grey 2 rectangle on top and a Dark Blue rectangle on bottom -- exactly the bit pattern of `$2A` expanded through `loResColors`.

For the dispatch diagram see §5 Diagram 5 above; it is not repeated here. This trace intentionally skips the full 6502 `STA` microinstruction cost, the PPU-vs-CPU cycle interleave, and SDL-side compositing. Those concerns live in `01.walkthrough_cpu_go.md` / `02.walkthrough_cpu_test_go.md` (CPU) and `08.walkthrough_video.md` / `18.walkthrough_main.md` (main loop).

## Section 8: Design Decisions and Hardware Reality

**Q1. Why does the low nibble go on top and the high nibble on the bottom?**

This matches Apple II hardware convention. The video circuit scans each text-cell byte twice per frame -- once for the top half-scanline pair, once for the bottom -- and gates which nibble it uses with a row-parity signal. The emulator mirrors the hardware ordering at `video/lores.go:43-54` rather than picking an "arbitrary-but-obvious" high=top layout. The §3 "CRITICAL correction" call-out is the same warning real Apple II programmers encountered when reading memory dumps for the first time.

**Q2. Why are all 16 palette colors hand-coded as RGB triples instead of derived from an NTSC simulation?**

Simplification. Accurate NTSC artifact color requires a per-pixel colorburst-phase model. The emulator approximates by picking 16 representative RGB values; the source comment at `video/lores.go:3-4` states that these "match the NTSC artifact colors." This is the same flavor of simplification doc 08 describes for hi-res.

**Q3. Why does `RenderLoRes` not accept a `page2` parameter?**

Known gap. The `Page2` softswitch is wired end-to-end (`io/softswitches.go:91-96` -> `main.go:374` -> `video/video.go:36`). `RenderHiRes` honors it (`video/hires.go:22-34`). `RenderLoRes` does not because no software title tested to date has relied on lo-res page 2. Adding it is a one-parameter threading change plus a base-address branch in `textLineAddr`. `docs/08.walkthrough_video.md:707` explicitly names this as future work.

**Q4. Why does `renderTextRows(20, 24)` live at the tail of `RenderLoRes` instead of being orchestrated by `Render()`?**

Locality. The "in mixed mode, the bottom 4 rows are text" rule is a property of the graphics renderer, not the dispatcher. Both `RenderLoRes` and `RenderHiRes` own the decision internally (`video/lores.go:58-61`, `video/hires.go:71-73`). This keeps `Render()` as a pure mode dispatcher. See `08.walkthrough_video.md` §7.

**Q5. Why does `fillBlock` bounds-check both `y < ScreenH` and `x < ScreenW`?**

Defensive. With `ScreenW=280`, `ScreenH=192`, `col <= 39`, `row <= 23`, `CharW=7`, and the bottom block's offset-plus-height of 4+4=8 scanlines (equal to `CharH`), both bounds (`col*CharW+w <= 280`, `row*CharH+8 <= 192`) are mathematically unreachable. The code at `video/lores.go:66-74` retains the checks because removing them would create latent fragility if any constant ever changed, and the per-frame cost is negligible.

**Q6. Could lo-res and text modes share a single rendering function?**

No. The per-byte interpretation is different: nibble-to-color vs. bitmap-row-to-pixels means different inner loops. They do share the outer loop structure (`textLineAddr`, `TextCols` iteration), and that sharing is captured by calling the same `textLineAddr` helper. Code factoring beyond that would obscure rather than clarify.

**Q7. What happens if a frame starts with garbage in `$0400`-`$07FF`?**

Normal. On power-on, RAM is zero-initialized (see `03.walkthrough_memory.md`), so a pure lo-res screen renders as all-Black (palette index 0). Software that runs `HOME` before flipping to GR fills the buffer with spaces (`$A0 = 0b1010_0000`): `topColor = 0x0` = Black, `botColor = 0xA` = Grey 2. That produces alternating Black/Grey-2 rows across the screen, not the solid-black GR screen BASIC's `GR` command produces (which clears the buffer differently). This is a known quirk, not a bug.

## Section 9: Summary / Quick Reference

> Lo-res graphics is a 40x48 colored-block display produced by
> reinterpreting the same 960 bytes of text-screen RAM (`$0400`-`$07FF`).
> Each byte holds two 4-bit color nibbles -- low nibble for the top block,
> high nibble for the bottom -- indexing into a fixed 16-entry Apple II
> palette. The row address formula is shared verbatim with text mode. Mixed
> mode clamps graphics rendering to lo-res rows 0..39 and delegates the
> bottom 4 text rows to `renderTextRows(20, 24)`. Lo-res page 2 is a known
> gap.
