# Educational Walkthrough: From Keypress to Pixel -- The End-to-End Input/Display Pipeline

> This walkthrough is a *cross-cutting* document. Unlike the other walkthroughs, which each focus on one file or one package, this one follows a single piece of data -- one byte representing one keystroke -- across **every layer** of the emulator: SDL event loop, I/O softswitches, the bus, the CPU, the firmware ROM (via the language card overlay), screen RAM, the character generator, the video renderer, the SDL texture, and finally the pixels the user sees. Read this once you are comfortable with walkthroughs `03` (memory), `04` (bus), `05` (I/O), `07` (chargen), `08` (video), and `10` (language card). It does not introduce new mechanics -- it stitches the existing ones into a single end-to-end story.

---

## Section 0: The Big Picture -- Three Stages, Two Shared Buffers

### What It Is

A complete keystroke-to-pixel round trip crosses three roughly independent stages. They never call each other directly; they communicate only through **two shared memory locations**.

```text
  STAGE 1 -- INPUT          STAGE 2 -- ROM ON CPU         STAGE 3 -- RENDERER
  (SDL -> kbd register)     (kbd register -> screen RAM)  (screen RAM -> pixels)
  +-----------------+       +-----------------------+     +------------------+
  | SDL KeyboardEvt |       | ROM keyboard poll     |     | vid.Render() at  |
  | main.go event   | ----> | at $C000, COUT        | --> | 60 Hz from main  |
  | sw.PressKey()   |       | writes to $0400+      |     | CharGenROM ->    |
  +-----------------+       +-----------------------+     | SDL texture      |
        $C000 reg                 screen RAM              +------------------+
```

| Producer            | Shared state              | Consumer            |
|---------------------|---------------------------|---------------------|
| SDL (Stage 1)       | `$C000` keyboard register | CPU / ROM (Stage 2) |
| CPU / ROM (Stage 2) | `$0400-$07FF` screen RAM  | Renderer (Stage 3)  |

### Why It Matters

This decoupling is the single most important architectural fact about the Apple II -- and the emulator preserves it faithfully. On the real hardware:

- The keyboard chip latches data into a register and waits; the CPU has to come ask.
- The CPU writes a byte to DRAM and walks away; nobody is "notified."
- The video circuitry scans DRAM 60 times a second and generates an NTSC signal regardless of what the CPU is doing.

Nobody hands off events. Everyone reads the same shared state at their own pace. This walkthrough's job is to make that pattern concrete by following one byte all the way through.

### Real-World Analogy

A factory with three departments separated by conveyor belts. The receiving dock (SDL) puts boxes onto conveyor 1, which feeds a register. The assembly floor (CPU/ROM) takes boxes from conveyor 1 and places finished goods onto conveyor 2 (screen RAM). The shipping department (renderer) takes from conveyor 2 and trucks the goods out (to the monitor). No department phones another. They only interact by adding to or removing from the belts.

## Section 1: Stage 1 -- SDL Captures the Key and Pokes the Keyboard Register

### What It Is

SDL2 provides an event-driven keyboard model. The emulator's main loop polls SDL for keyboard events each host frame and translates them into the Apple II's flat 7-bit ASCII byte, which it deposits into the `io.SoftSwitches` keyboard register at `$C000`.

### Why It Matters

Stage 1 is purely a translator. It converts a modern multi-modifier keyboard event (Sym + Mod + Type) into the one byte the real Apple II keyboard chip would have latched. After this stage, nothing downstream cares that the input came from SDL -- the rest of the pipeline runs as if a real keyboard chip had done the latching.

### How the Code Works

**Step 1 -- SDL fires a KeyboardEvent.** `main.go:289`:

```go
case *sdl.KeyboardEvent:
    switch e.Type {
    case sdl.KEYDOWN:
        ...
        if key := sdlKeyToApple(e); key != 0 {
            sw.PressKey(key)
        }
```

For our worked example (user pressing Shift+A), `e.Keysym.Sym = sdl.K_a` and `e.Keysym.Mod & sdl.KMOD_SHIFT != 0`.

**Step 2 -- `sdlKeyToApple` translates SDL -> Apple ASCII.** `main.go:417`:

```go
func sdlKeyToApple(e *sdl.KeyboardEvent) uint8 {
    sym := e.Keysym.Sym
    mod := e.Keysym.Mod

    if mod&sdl.KMOD_CTRL != 0 {
        if sym >= sdl.K_a && sym <= sdl.K_z {
            return uint8(sym-sdl.K_a) + 1   // Ctrl+A=1, Ctrl+B=2, ...
        }
    }
    // Special keys: Return, Backspace, Delete, Tab, Escape ...
    // Printable ASCII characters with shift handling
    ...
}
```

With Shift held and `K_a` pressed, the function returns `0x41` (`'A'`).

**Step 3 -- `sw.PressKey(0x41)` deposits the byte and raises the strobe flag.** `io/softswitches.go:177`:

```go
func (s *SoftSwitches) PressKey(key uint8) {
    s.KeyData = key & 0x7F   // 0x41
    s.KeyReady = true
}
```

After this returns, `SoftSwitches` holds:

```text
  KeyData  = 0x41   (the 'A')
  KeyReady = true   (the strobe bit -- "a key is waiting")
```

**The CPU has not yet been told anything.** SDL has done its job; the data is sitting in the keyboard register waiting for software to poll it. This is exactly how the real Apple II works -- the keyboard hardware latches the key and a single strobe bit; the CPU has to come ask.

### Real-World Analogy

Think of a hotel concierge desk with a tiny mailbox. A guest drops off a note (the keystroke), and a small flag pops up on top of the box (the strobe). The mailbox doesn't ring a bell or send an email. The next staff member who happens to walk past the desk has to look at the flag, take the note, and lower the flag.

## Section 2: Stage 2 -- The Firmware ROM Polls the Register and Writes the Screen

### What It Is

The Apple II+ firmware ROM at `$D000-$FFFF` contains the Monitor, Applesoft BASIC, and the `KEYIN` / `COUT` routines that form the standard input/output loop. Once a program is waiting for input (the `]` prompt in Applesoft, for example), the ROM sits in a tight loop reading `$C000` and checking bit 7. When the strobe goes high, the ROM accepts the key, clears the strobe, then echoes the character to the screen via the `COUT` routine -- which ultimately stores a byte into screen RAM at `$0400-$07FF`.

### Why It Matters

Stage 2 is where the CPU actually participates. Everything from the bus routing to the language card overlay to the screen-encoding convention shows up in this stage. It is also where the emulator gets its biggest payoff for architectural faithfulness: because the LC, bus, and softswitch layers all behave like the real hardware, the *unmodified* original Apple II firmware ROM image runs without patching and drives this stage end to end.

### How the Code Works

**Step 4 -- CPU reads `$C000`.** Somewhere inside the Monitor's `KEYIN` loop (around `$FD1B` in the standard Apple II+ ROM), the CPU executes `LDA $C000`. From the CPU's point of view this is an ordinary absolute load -- it has no idea $C000 is magic. The bus routes the read:

```text
  CPU: c.read($C000)
   -> bus.Read($C000)
   -> walks mappings in reverse (last-mapping-wins)
   -> hits io.SoftSwitches at $C000-$C0FF
   -> SoftSwitches.Read($C000)
```

`io/softswitches.go:67`:

```go
case 0xC000:
    val := s.KeyData          // 0x41
    if s.KeyReady {
        val |= 0x80           // strobe bit on
    }
    return val                // returns 0xC1
```

Register A is loaded with `$C1` (= `0x41 | 0x80`). The 6502's N (negative) flag is automatically set because bit 7 is high.

**Step 5 -- ROM tests the strobe and clears it.** The Monitor's `KEYIN` routine (at `$FD1B` in the standard II+ ROM) is a tight wait loop:

```asm
KEYIN:  LDA  $C000      ; sample keyboard
        BPL  KEYIN      ; loop while bit 7 CLEAR (no key)
        STA  $C010      ; clear strobe (the stored byte is ignored)
        RTS             ; A still holds $C1
```

`BPL` (branch if positive = bit 7 clear) loops back while no key is waiting. The moment `KeyReady` is true, the `$C000` read returns `$C1`, bit 7 is set, `BPL` is *not* taken, and the routine falls through. `STA $C010` then clears the strobe -- the byte the CPU "writes" is irrelevant because softswitches are address-strobed, not data-latched. In the emulator, both reads *and* writes to `$C010` clear the strobe; `SoftSwitches.Write` just calls `Read` (`io/softswitches.go:171-174`).

`io/softswitches.go:73`:

```go
case 0xC010:
    s.KeyReady = false
    return s.KeyData & 0x7F
```

`KeyReady` is now false, so subsequent reads of `$C000` will return `$41` without the high bit -- preventing the loop from accepting a phantom second 'A'.

**Step 6 -- ROM echoes the character to screen RAM via `COUT`.** Applesoft and the Monitor both route character output through `COUT` (around `$FDED`). `COUT` computes the screen address from the current cursor row/column (using the interleaved row formula -- see `06.walkthrough_main_phase3.md` Section 4 and `08.walkthrough_video.md` Section 5) and stores the character. Suppose the cursor is at row 0, column 1 -- the target address is `$0401`. The CPU executes the equivalent of:

```asm
  STA $0401      ; A = $C1
```

The write goes:

```text
  CPU: c.write($0401, 0xC1)
   -> bus.Write($0401, 0xC1)
   -> walks mappings in reverse
   -> hits memory.RAM at $0000-$BFFF
   -> RAM.Write($0401, 0xC1)
   -> ram[0x0401] = 0xC1
```

**A critical detail**: the byte stored is `$C1`, not `$41`. The keyboard register already delivered the byte with bit 7 set (the strobe), the ROM passes it through to `COUT` more or less unchanged, and the Apple II's screen encoding interprets `$80-$FF` as **normal display** (see `07.walkthrough_chargen.md` Section 3). The same high bit that meant "strobe" on the keyboard side conveniently means "normal mode" on the screen side. That coincidence is a Wozniak shortcut, not magic -- the keyboard delivers bytes pre-formatted for the screen.

**At this point the renderer is unaware.** ROM has done its job; the data is sitting in screen RAM waiting for the next video frame. CPU and renderer never call each other -- they share screen RAM and nothing else.

### Real-World Analogy

A receptionist (the ROM) sitting at a desk reading the same paperback novel over and over. Every few seconds she glances up at the concierge mailbox flag (`$C000` bit 7). When the flag is up, she walks over, takes the note, lowers the flag (`$C010`), reads the message, and writes the message on the building's whiteboard (`$0400+`). She then sits back down and resumes reading. She has no idea where the note came from. She just knows: flag up -> grab note -> write on whiteboard.

## Section 3: Stage 3 -- The Renderer Scans Screen RAM and Paints Pixels

### What It Is

The main loop calls `vid.Render` once per host frame (60 fps). `RenderText` walks all 24 rows and 40 columns of screen memory, calls `CharGenROM` for each cell on each of the 8 scanlines, expands the 7-bit pixel pattern into RGBA pixels in the `Pixels` buffer, then hands the buffer to SDL for display.

### Why It Matters

This stage is what makes the byte in screen RAM visible. Without it, the user's keystroke would be silently buffered forever. The 60 Hz cadence is deliberate -- the same as the real NTSC video refresh rate -- and is the reason a key pressed *now* shows up on screen within roughly 16-17 ms even though no event fired to notify the renderer.

### How the Code Works

**Step 7 -- main loop invokes the renderer.** `main.go:374`:

```go
vid.Render(sw.TextMode, sw.MixedMode, sw.HiRes, sw.Page2)
```

`sw.TextMode` is true by default, so `Render` dispatches to `RenderText` -> `renderTextRows` (`video/video.go:62-102`).

**Step 8 -- iterate row, column, scanline.** For row 0, `textLineAddr(0)` returns `$0400`. The inner loop walks `col = 0..39`. At `col = 1`:

```go
screenByte := v.RAM[baseAddr+uint16(col)]    // RAM[$0401] = 0xC1
```

For each of 8 scanlines, the renderer asks the character generator for that scanline's pixel pattern:

```go
pixels, inverse := CharGenROM(screenByte, scanline)
```

**Step 9 -- `CharGenROM` decodes the screen byte and looks up the glyph row.** Reusing the trace from `07.walkthrough_chargen.md` Section 4:

```text
  screenByte = 0xC1, scanline = 0

  Step a: $C1 >= $80 -> default case
          charIndex = $C1 & $7F = $41 (65)
          inverse   = false

  Step b: row = 0, in 0..7 -> OK

  Step c: pixels = charGen[65*8 + 0] = charGen[520] = 0x08
```

`CharGenROM` returns `(0x08, false)` -- the top peak of the letter 'A'.

**Step 10 -- expand 7 bits into 7 RGBA pixels.** `video/video.go:77-98`:

```go
for px := 0; px < CharW; px++ {
    lit := (pixels>>uint(px))&1 != 0   // bit 0 = leftmost
    if inverse { lit = !lit }
    offset := (py*ScreenW + col*CharW + px) * 4
    if lit {
        v.Pixels[offset+0] = ColorOn[0]   // phosphor green
        ...
    } else {
        v.Pixels[offset+0] = ColorOff[0]  // black
        ...
    }
}
```

For scanline 0 of our 'A' (`pixels = 0x08`, binary `0001000`), only `px=3` (bit 3) lights up. Six black pixels, one green pixel, six black -- the single dot at the top of the letter. Scanlines 1-6 fill in the rest of the glyph; scanline 7 is the blank descender.

**Step 11 -- upload to SDL and present.** After all 960 character cells (24 rows x 40 columns) have been expanded across 8 scanlines each -- that is 7,680 `CharGenROM` calls and 53,760 RGBA pixel writes per frame -- `main.go:377-380`:

```go
texture.Update(nil, unsafe.Pointer(&vid.Pixels[0]), int(video.ScreenW)*4)
renderer.Clear()
renderer.Copy(texture, nil, nil)
renderer.Present()
```

`Present` hands the texture to SDL, SDL hands it to the GPU, the GPU paints the window, the monitor shows it. The user sees an 'A'.

### Real-World Analogy

A scanner running on a fixed schedule. Sixty times a second, it walks the whiteboard from top to bottom, copies every cell onto a piece of paper, hands the paper to the courier (SDL), and the courier hands it to the printer (monitor). The scanner doesn't know what changed on the whiteboard, and it doesn't need to -- it just copies everything every time. Whatever the receptionist wrote will show up on the next pass.

## Section 5: Why The Decoupling Matters

Three independent stages, two pieces of shared state. Each stage runs at its own pace:

| Stage     | Runs when                                              | Cadence            |
|-----------|--------------------------------------------------------|--------------------|
| Stage 1   | An SDL key event is dequeued                           | event-driven       |
| Stage 2   | The CPU happens to execute `LDA $C000` in its main loop | ~1 MHz polling     |
| Stage 3   | The main loop hits the 60 Hz render tick               | 60 Hz              |

Several emergent properties fall out of this decoupling:

1. **Type-ahead works for free.** If the user types two characters before the ROM polls `$C000`, the second one overwrites `KeyData` and the first one is lost -- exactly like the real Apple II, which had a one-byte type-ahead buffer (the keyboard register itself).

2. **The renderer cannot "miss" a change.** It doesn't react to events; it re-scans the whole screen 60 times a second. Whatever the CPU last wrote will appear on the next frame.

3. **The CPU can stall without breaking input.** Even if the CPU is busy in a long delay loop, SDL keystrokes still land in `KeyData` and wait. They'll be picked up the next time the ROM polls.

4. **The renderer can fall behind without breaking the CPU.** A slow host can render at 30 Hz instead of 60 -- the CPU never notices. Screen RAM is the source of truth; the renderer's pace is decorative.

This is the same architectural pattern the real Apple II used in 1977 because hardware was cheap and inter-component synchronization was expensive. The emulator inherits the same elegance.

## Section 7: Summary

> Pressing a key on the host keyboard produces a single byte (`0x41` for Shift+A) that crosses three independent stages and lands as 56 pixels on screen. SDL puts the byte into the `$C000` keyboard register and raises a strobe bit. The Apple II+ firmware ROM -- running on the emulated 6502, reachable through the language card overlay -- polls `$C000` in a tight loop, accepts the key, clears the strobe at `$C010`, and stores the byte (now `$C1`) into screen RAM at the cursor's address. Up to 16.67 ms later, the main loop's 60 Hz tick calls `vid.Render`, which iterates screen RAM, asks `CharGenROM` for the glyph row, expands each 7-bit pattern into RGBA pixels, and hands the frame buffer to SDL. The user sees an 'A'.

**The architectural takeaway**: the three stages are decoupled, communicating only through `$C000` (keyboard register) and `$0400-$07FF` (screen RAM). No stage calls another. No event is propagated. Every stage just reads or writes shared memory at its own cadence. This is the Apple II's original design from 1977, preserved unchanged in this emulator.

## Appendix A: 6502 CPU Register Cheat Sheet

Stage 2 leans heavily on three 6502 instructions and one register. If you ever lose the thread of the assembly snippets in Section 2, this appendix is the refresher.

### The Five Registers

The 6502 has only a handful of registers, all 8-bit except the 16-bit `PC`:

| Reg   | Name             | Purpose                                                                                  |
|-------|------------------|------------------------------------------------------------------------------------------|
| **A** | Accumulator      | The main working register. Nearly every load, store, arithmetic, and bit operation flows through A. |
| X, Y  | Index registers  | Used for array indexing and counting loops.                                              |
| SP    | Stack pointer    | Points to the next free byte on the stack ($0100-$01FF).                                 |
| PC    | Program counter  | 16-bit. Address of the next instruction to execute.                                      |
| P     | Status flags     | N (negative), V (overflow), Z (zero), C (carry), I (interrupt disable), D (decimal), B (break). |

### The Three Instructions That Matter for Stage 2

| Mnemonic   | Effect                                              | Touches A? | Sets N/Z? |
|------------|-----------------------------------------------------|------------|-----------|
| `LDA addr` | Reads byte from `addr`, **loads** into A.           | yes        | yes       |
| `STA addr` | **Writes** A's current value out to `addr`.         | no         | no        |
| `BPL addr` | Branches to `addr` if N flag is clear (bit 7 = 0).  | no         | no        |

Two implications matter throughout Section 2:

1. **`STA` does not change A.** It takes whatever is already in A and writes that byte to memory. After `STA`, A still holds the same value it had before. This is the whole reason `STA $C010` can clear the strobe while leaving the keyboard byte intact in A for the next instruction (`STA $0401` inside `COUT`).

2. **`BPL` does not touch A.** It only peeks at the N flag (set by the *previous* load). After `BPL`, A is unchanged regardless of whether the branch was taken.

### The KEYIN Loop in Terms of the Cheat Sheet

```asm
KEYIN:  LDA  $C000      ; reads $C000 (synthesized byte), loads $C1 into A.
                        ; N flag := bit 7 of A = 1.
        BPL  KEYIN      ; tests N flag. N=1, so branch NOT taken. A unchanged ($C1).
        STA  $C010      ; writes A ($C1) to $C010. Side effect: KeyReady=false.
                        ; A unchanged ($C1).
        RTS             ; returns to caller. A still $C1. Ready for COUT.
```

Across the four instructions, A is loaded once and never modified again. That single byte then travels from KEYIN's caller all the way to `STA $0401` inside `COUT`, where it finally lands in screen RAM.

## Appendix B: The Strobe Bit Is Synthesized, Not Stored

Section 2 talks about "the strobe bit" as if it lives somewhere as an actual bit. It does not. Bit 7 at address `$C000` is **manufactured on demand** every time the CPU reads, and "clearing the strobe" never mutates a bit -- it flips a separate Go `bool`. Understanding this is the difference between memorizing the protocol and actually grasping why `STA $C010` is safe.

### Where the State Actually Lives

Inside `io.SoftSwitches`, the keyboard occupies two completely separate fields:

```go
type SoftSwitches struct {
    KeyData  uint8 // last key pressed (bit 7 = strobe)  ← only bits 0-6 used
    KeyReady bool  // true when a new key is available    ← this is "the strobe"
    ...
}
```

- `KeyData` holds the 7-bit ASCII byte. Bit 7 is always zero (forced by the `& 0x7F` in `PressKey`).
- `KeyReady` is a Go bool that tracks whether the byte in `KeyData` has been acknowledged yet.

Neither of these is "bit 7 of `$C000`." That bit exists only at the moment the bus delivers a synthesized byte to the CPU.

### The Synthesis on Read

`io/softswitches.go:67-72`:

```go
case 0xC000:
    val := s.KeyData          // 0x41 — only bits 0-6 ever populated
    if s.KeyReady {
        val |= 0x80           // glue the strobe bit on top
    }
    return val                // 0xC1 — the byte the CPU receives
```

The byte `$C1` is *constructed* by ORing `0x80` onto `KeyData` if and only if `KeyReady` is true. It never exists in storage. It exists only as a transient value on the bus during one CPU read cycle.

### Diagram B1: Two Fields, One Synthesized Byte

```text
  Inside SoftSwitches (Go struct):
  +-----------------------------+
  | KeyData  uint8  =  0x41     |   ← only 7 bits used
  | KeyReady bool   =  true     |   ← the "strobe" lives here
  +-----------------------------+
                |
                | LDA $C000 triggers a synthesis:
                v
  +-----------------------------+
  |   val := KeyData            |   = 0x41
  |   if KeyReady {             |
  |       val |= 0x80           |   = 0xC1  (strobe bit glued on top)
  |   }                         |
  |   return val                |
  +-----------------------------+
                |
                v
            A = 0xC1   ← the byte the CPU sees
```

### Why `STA $C010` Doesn't Re-Arm the Strobe

When the CPU executes `STA $C010` with A=`$C1`:

1. CPU emits a write cycle: address `$C010`, data byte `$C1`.
2. Bus routes the write to `SoftSwitches.Write($C010, 0xC1)`.
3. `SoftSwitches.Write` (`io/softswitches.go:171-174`) **never reads the `val` parameter**. It just calls `Read(addr)` for the side effect:

```go
func (s *SoftSwitches) Write(addr uint16, val uint8) {
    s.Read(addr)            // val is named but never used
}
```

4. `Read($C010)` runs `s.KeyReady = false` and returns `KeyData & 0x7F` (= `0x41`). The return value is also discarded for a write.
5. The `0xC1` the CPU put on the bus evaporates. Nothing latches it. Nothing inspects it.

This is the "address-strobed, not data-latched" pattern from `10.walkthrough_languagecard.md` Section 6. The softswitch reacts to the *act* of being addressed at `$C010`, not to the byte that happened to be on the bus during that write.

### Diagram B2: Same Address, Different Accesses, Same Side Effect

```text
  CPU instruction       What CPU puts on bus      What softswitch does      Effect on A
  --------------------  ------------------------  ------------------------  ------------
  LDA $C010             reads $C010               returns KeyData & 0x7F    A := 0x41
                                                  sets KeyReady = false      (loaded)
                                                                            (strobe cleared)

  STA $C010 (A=0xC1)    writes 0xC1 to $C010      sets KeyReady = false      unchanged
                                                  ignores the 0xC1            (still 0xC1)
                                                                            (strobe cleared)

  STA $C010 (A=0x00)    writes 0x00 to $C010      sets KeyReady = false      unchanged
                                                  ignores the 0x00            (still 0x00)
                                                                            (strobe cleared)
```

Same address, three different access patterns, three different bytes on the bus -- same observable side effect every time. **Only the address matters.** That is precisely why the ROM convention `STA $C010` (instead of `LDA $C010`) is the right call: it clears the strobe without disturbing A, so the keyboard byte stays alive in A until `COUT` stores it to screen RAM.

### The Byte's Three Lives

The same byte `$C1` plays three different roles in its short life. Bit 7 is reinterpreted at each stage:

| Stage                       | Where the byte is              | What bit 7 means there         |
|-----------------------------|--------------------------------|--------------------------------|
| 1. Just emerged from `$C000` | On the bus, delivered to A    | **Strobe**: "a key is waiting" |
| 2. Sitting inside register A | CPU internal storage          | **Nothing** -- just bit 7 of a number |
| 3. Stored at `$0401`         | Screen RAM, read by renderer  | **Normal display mode** (vs inverse/flashing -- see `07.walkthrough_chargen.md` §3) |

The strobe bit is cleared *out of band* through `KeyReady`, not by mutating the byte in A. That is what allows the same byte to flow through all three stages unchanged, with bit 7 happening to mean the right thing at each step. Wozniak designed it this way so the keyboard could feed the screen directly with no bit-twiddling in between.

### The One-Line Summary

There is no "strobe bit" stored anywhere. There is a Go bool `KeyReady`, and the softswitch read handler ORs `0x80` onto the manufactured byte when that bool is true. "Clearing the strobe" flips the bool. `STA $C010` is safe because the softswitch never looks at what was written -- the address itself is the entire signal.

## Appendix C: How KEYIN and COUT Are Connected -- JSR/RTS and the Stack

Section 2 walks `KEYIN` and `COUT` as if they form one continuous chain: read a key, then echo it. But neither subroutine knows the other exists. They are two independent tools in the firmware ROM, and a *third* routine -- usually `GETLN` -- is the one that calls both in sequence. This appendix unpacks how that linkage works, and clears up the common misconception that `RTS` somehow advances PC into the next routine.

### KEYIN and COUT Are Two Separate ROM Subroutines

Both live in the Apple II+ firmware ROM, but at different addresses and with no direct connection:

| Routine | ROM address | Job                                              |
|---------|-------------|--------------------------------------------------|
| KEYIN   | `$FD1B`     | Wait for a key, return it in A.                  |
| COUT    | `$FDED`     | Take the byte in A, write it to the screen.     |

`KEYIN`'s `RTS` does **not** flow into `COUT`. It returns to whichever instruction called `KEYIN` -- and *that* instruction's neighbor is what runs next.

### How `RTS` Actually Works -- It's a Stack Pop

`RTS` (ReTurn from Subroutine) pops a return address from the stack and loads it into PC. It is the partner of `JSR` (Jump to SubRoutine), which pushed that address on the way in. PC does not "increase by some amount" -- PC is restored to whatever the caller's stack frame says.

Concrete example with addresses pinned down:

```asm
  Caller (GETLN, in ROM):                Subroutine (KEYIN, in ROM):
  $FD75   JSR  KEYIN          ┐           $FD1B   LDA  $C000
  $FD78   JSR  COUT           │           $FD1E   BPL  $FD1B
  $FD7B   ...                 │           $FD20   STA  $C010
                              │           $FD23   RTS
                              │
                              └── PC returns here ($FD78) after KEYIN's RTS
```

The dance, step by step:

1. CPU executes `JSR KEYIN` at `$FD75`. It pushes the return address (`$FD77` -- one less than the next instruction, for arcane 6502 reasons) onto the stack, then sets PC = `$FD1B`.
2. KEYIN runs its wait loop and reaches `RTS` at `$FD23`.
3. `RTS` pops `$FD77` from the stack, adds 1 to get `$FD78`, and loads PC = `$FD78`.
4. CPU now executes the instruction at `$FD78`, which happens to be `JSR COUT`.

The reason `COUT` runs after `KEYIN` is **not** because `RTS` knows about `COUT`. It is because the caller (GETLN) deliberately wrote `JSR COUT` as the very next instruction after `JSR KEYIN`.

### Diagram C1: The Stack During the JSR/RTS Dance

```text
  Step 1: Before JSR KEYIN at $FD75
  Stack:  [ ... ]                          PC = $FD75

  Step 2: JSR KEYIN executes
  Stack:  [ ..., 0xFD, 0x77 ]              PC = $FD1B
                  ^^^^^^^^^^
                  return addr ($FD77) pushed onto stack

  Step 3: KEYIN runs its loop and reaches RTS at $FD23
  Stack:  [ ..., 0xFD, 0x77 ]              PC = $FD23
  Register A = $C1                         (the key, ready for the next step)

  Step 4: RTS executes
  Stack:  [ ... ]                          PC = $FD78
                                                  ^
                                                  back to the instruction
                                                  after JSR KEYIN

  Step 5: JSR COUT executes at $FD78
  Stack:  [ ..., 0xFD, 0x7B ]              PC = $FDED
                  ^^^^^^^^^^
                  new return addr ($FD7B) pushed
  Register A = $C1                         (still alive, COUT will use it)
```

The stack is the bookkeeping. `JSR` pushes; `RTS` pops. The CPU has no idea what the subroutine "means" -- only the caller knows that calling `KEYIN` produces a key in A and that the natural next step is to call `COUT`.

### Who Is the Caller? GETLN.

On the Apple II, the routine that links `KEYIN` and `COUT` together is `GETLN` (Get a Line of input), at around `$FD6A` in the Monitor ROM. Roughly:

```asm
GETLN:  LDX  #$00            ; X = character count
NXTCHR: JSR  KEYIN           ; ──► wait for next key; returns A = key ($C1 for 'A')
        ; (some checks for Enter, backspace, etc.)
        JSR  COUT            ; ──► echo the key to the screen
                             ;     COUT eventually does STA $0401 (or wherever
                             ;     the cursor is in screen RAM).
        STA  INPUT_BUF,X     ; save the key in an input buffer
        INX
        CMP  #$8D            ; was it Enter? (Apple II Enter = $8D, not $0D)
        BNE  NXTCHR          ; no -> loop for another key
        RTS                  ; yes -> return to whoever called GETLN
```

`GETLN` itself is called by Applesoft BASIC's main input loop (when displaying the `]` prompt) or by the Monitor's command parser (when displaying `*`). So the full call tree for one keystroke is:

```text
  Applesoft polling loop  (in ROM)
       |
       | JSR GETLN
       v
  GETLN  (in ROM, ~$FD6A)
       |
       |   loop:
       |   JSR KEYIN     ──► KEYIN waits for key, RTS returns A=$C1 to GETLN
       |   JSR COUT      ──► COUT writes $C1 to screen RAM, RTS returns to GETLN
       |   save A in input buffer
       |   check for Enter
       |   branch back to loop OR fall through
       |
       | RTS
       v
  back to Applesoft polling loop
```

Three nested levels of `JSR`/`RTS`, three independent stack frames. None of these routines "know" about the others by name -- they only know what's on the stack and what's in the registers.

### How COUT Picks the Destination -- Cursor Variables and `STA (BASL),Y`

In Section 2 Step 6, the doc says COUT does `STA $0401` to write 'A' at row 0, column 1. That literal `STA $0401` does **not** appear anywhere in the ROM -- COUT does not know the cursor is at column 1 when it is assembled. The actual instruction inside COUT is `STA (BASL),Y`, an indirect-indexed store, and the address `$0401` is computed at run time from the cursor state. Three zero-page variables hold that state.

**The cursor state in zero page**

| Addr  | Name     | Meaning                                                |
|-------|----------|--------------------------------------------------------|
| `$24` | **CH**   | Cursor column (0..39). "Character Horizontal."         |
| `$25` | **CV**   | Cursor row (0..23). "Character Vertical."              |
| `$28` | **BASL** | Low byte of the base address of the current text row.  |
| `$29` | **BASH** | High byte of that base address.                        |

`BASL`/`BASH` together form a 16-bit pointer to the start of whichever text row the cursor is currently on. Crucially, it is **not recomputed on every store** -- it is updated only when the cursor moves to a new row.

**Where `BASL`/`BASH` come from -- the VTAB routine**

When the cursor moves vertically (newline, scroll, explicit positioning), the Monitor calls **VTAB** (around `$FC22`). VTAB takes `CV`, runs the row interleaving formula (same math as `textLineAddr` in `video/video.go:115-116` -- see `06.walkthrough_main_phase3.md` §4), and stores the result in `BASL`/`BASH`.

For our example with the cursor on row 0:

```text
  CV = 0
  VTAB computes textLineAddr(0) = $0400
  VTAB stores BASL = $00, BASH = $04
```

`BASL`/`BASH` now stays put as long as the cursor stays on row 0.

**The store inside COUT1**

COUT1 (at `$FDF0`, the routine that COUT at `$FDED` jumps through indirectly) reduces, for a printable character, to:

```asm
COUT1:  CMP  #$A0        ; printable ($A0+)?
        BCS  STORADV     ; yes -> store and advance
        ; ... handle CR ($8D), BS ($88), BELL ($87), LF ($8A) ...

STORADV:
        LDY  CH          ; Y = cursor column = 1
        STA  (BASL),Y    ; <-- THE store. Address = (BASL/BASH) + Y.
        INC  CH          ; advance cursor right
        LDA  CH
        CMP  #$28        ; column == 40?
        BCC  DONE        ; no -> done
        JSR  CR_LF       ; yes -> wrap: CH=0, CV++, VTAB
DONE:   RTS
```

The pivotal instruction is `STA (BASL),Y` -- opcode `$91`, addressing mode "zero-page indirect, indexed by Y." The CPU resolves it like this:

```text
  Read 16-bit pointer from zero page:
       low byte  = ram[$28] = BASL = $00
       high byte = ram[$29] = BASH = $04
       pointer   = $0400

  Add Y:
       effective address = pointer + Y = $0400 + 1 = $0401

  Write A ($C1) to $0401.
```

That is where the `STA $0401` in the Section 2 trace actually comes from -- not a literal absolute store, but `STA (BASL),Y` with BASL/BASH and Y arranged so the effective address resolves to `$0401`.

**Diagram C2: Cursor state -> effective address**

```text
  Zero page:                      Screen RAM:

   $24  CH    = 0x01     -----+
                              |
   $25  CV    = 0x00          |
                              |
   $28  BASL  = 0x00  ---+    |
   $29  BASH  = 0x04  ---+    |    $0400 +---------+
                         |    |          | row 0   |
                         |    |    $0401 | col 1 --+---<-- STA writes $C1 here
                         |    |    $0402 | col 2   |
                         |    |          |  ...    |
                         |    |    $0427 | col 39  |
                         |    |    $0428 |  ...    |  (row 8 -- interleaved!)
                         |    |          +---------+
                         |    |
                         |    | CPU executes STA (BASL),Y with Y = CH = 1:
                         |    |   pointer = ram[$28..$29] = $0400
                         |    |   eff_addr = pointer + Y = $0401
                         |    v
                         +--> effective address = $0401
```

**Why the indirection? Two reasons**

1. **Speed.** The row-interleave math is expensive, but the cursor moves vertically far less often than horizontally. Caching `textLineAddr(CV)` in `BASL`/`BASH` means COUT does only a fast pointer-plus-Y per character, instead of recomputing the row address each store.

2. **Programmability.** Applesoft and Monitor commands (`HTAB`, `VTAB`, etc.) move the cursor by writing directly to `CH`, `CV`, and `BASL`/`BASH`. They all funnel through this same pointer-plus-column mechanism, so cursor positioning is a uniform interface.

**The cursor advance after the store**

Once the byte is in screen RAM, the same routine advances the cursor:

```asm
        INC  CH          ; column++
        LDA  CH
        CMP  #$28        ; column == 40?
        BCC  DONE
        JSR  CR_LF       ; wrap to next row
```

If the just-stored character was column 39, the wrap path runs: `CH = 0`, `CV++`, VTAB recomputes BASL/BASH for the new row. If `CV` would have exceeded 23 (last row), a scroll routine copies all rows up one and clears the bottom -- still pure RAM writes, still invisible to the renderer until the next 60 Hz tick.

**One subtlety -- the CSW vector**

`$FDED` (the public "COUT" entry point) is not COUT1 itself. It is:

```asm
$FDED:  JMP  (CSWL)      ; CSWL/CSWH = $36/$37 -- "Character SWitch" vector
```

By default the vector points to `COUT1` at `$FDF0`. But DOS 3.3 and ProDOS hook `$36/$37` to redirect output -- e.g., to a printer firmware on slot 1. `PR#1` in Applesoft is essentially a `CSWL`/`CSWH` overwrite. For our keystroke flow, with no I/O hooks installed, the vector still points to COUT1, and the cursor-driven `STA (BASL),Y` happens as described.

**The one-sentence answer**

`STA $0401` is what the indirect-indexed instruction `STA (BASL),Y` resolves to when `BASL`/`BASH` = `$0400` (the cached `textLineAddr(0)` for the cursor's current row) and `Y = CH = 1` (cursor column 1). The three zero-page slots -- `CH`, `CV`, `BASL`/`BASH` -- together encode "where the next character goes," and they are maintained by COUT and VTAB across every keystroke.

### Why This Matters for the Walkthrough

In Section 2 Step 6, the doc says:

> JSR COUT  →  STA $0401  with A=$C1

That `JSR COUT` is executed by **GETLN** (or some similar caller), not by `KEYIN` itself. The architectural picture is:

- `KEYIN` is a tool: "wait for a key, give it to me in A."
- `COUT` is a tool: "take what's in A, paint it on the screen."
- `GETLN` is the recipe that uses both tools in order to produce its higher-level behavior ("read a line, echoing each key as you go").

This is the same separation-of-concerns idea you see everywhere in the codebase: small, focused units, glued together by higher-level orchestrators. The 6502 ROM uses the stack as its glue.

### Real-World Analogy

`KEYIN` is a doorbell receiver: it watches for the bell, then hands you the visitor's name card. `COUT` is a sign-writer: hand it a name, it writes that name on the welcome board. Neither one talks to the other. The hotel concierge (`GETLN`) is the one who picks up the name card from the doorbell receiver and walks it over to the sign-writer. The doorbell receiver doesn't know there's a sign-writer; the sign-writer doesn't know where its input came from. The concierge orchestrates them.

### The One-Line Summary

`RTS` does not point to `COUT`. `RTS` pops the return address that `JSR KEYIN` pushed, so PC returns to the instruction right after `JSR KEYIN` in the caller's code. That caller -- typically `GETLN` -- happens to have written `JSR COUT` as the very next instruction. The sequencing is the caller's choice; `KEYIN` and `COUT` are unrelated subroutines that share only the convention that the keystroke travels through register A from one to the other.

## Appendix D: From Screen RAM to Monitor Pixels -- The Post-COUT Journey

Section 3 is intentionally brief because the full mechanics of `vid.Render` deserve their own treatment. This appendix follows our byte (`$C1` sitting at `$0401`) all the way to a glowing green pixel on the user's monitor: through the 60 Hz render tick, the four-deep nested loop, the `Pixels` RGBA buffer, the SDL texture upload, the GPU draw call, the back-buffer swap, and finally the OS compositor.

### What Happens Immediately After `STA $0401`?

Nothing visible. The CPU continues executing the next instruction (inside `GETLN`, e.g. `STA INPUT_BUF,X`). The renderer is asleep, unaware that screen memory changed. The byte just sits in DRAM:

```text
  ram[0x0401] = 0xC1     ← passive; no notification fires
```

The byte will remain invisible for up to one host frame (~16.67 ms at 60 fps). During that interval the CPU may execute thousands more instructions. Eventually the main Go loop hits its render tick and the byte gets noticed.

### Step D1: The 60 Hz Render Tick

`main.go:362-380` is the heart of the main loop. Once per host frame, after running the CPU for `cyclesPerFrame` (= 17,050) cycles, it calls:

```go
vid.Render(sw.TextMode, sw.MixedMode, sw.HiRes, sw.Page2)
texture.Update(nil, unsafe.Pointer(&vid.Pixels[0]), int(video.ScreenW)*4)
renderer.Clear()
renderer.Copy(texture, nil, nil)
renderer.Present()
```

`sw.TextMode` is true at the Applesoft prompt, so `Render` dispatches to the text path. The entry-point is `video/video.go:36-52`:

```go
func (v *Video) Render(textMode, mixedMode, hiRes, page2 bool) {
    v.flashCounter++                       // (1) advance flash timer
    if v.flashCounter >= 16 {
        v.flashCounter = 0
        v.FlashState = !v.FlashState       // toggle every 16 frames
    }
    switch {
    case textMode:
        v.RenderText()                     // (2) dispatch to text renderer
    ...
    }
}
```

The flash counter is the only piece of state that survives across frames; everything else in text rendering is recomputed from scratch each tick.

### Step D2: The Four-Deep Nested Loop

`RenderText` calls `renderTextRows(0, 24)`. The inner work (`video/video.go:62-102`) is:

```go
for row := 0; row < 24; row++ {                       // 1) every text row
    baseAddr := textLineAddr(row)                     //    $0400, $0480, $0500, ...

    for col := 0; col < 40; col++ {                   // 2) every column
        screenByte := v.RAM[baseAddr+uint16(col)]     //    e.g. RAM[$0401] = 0xC1

        for scanline := 0; scanline < 8; scanline++ { // 3) every scanline of cell
            pixels, inverse := CharGenROM(screenByte, scanline)

            if screenByte >= 0x40 && screenByte < 0x80 && v.FlashState {
                inverse = true                        //    flash override
            }

            py := row*8 + scanline                    //    pixel-row in screen
            for px := 0; px < 7; px++ {               // 4) every pixel in cell row
                lit := (pixels>>uint(px))&1 != 0      //    bit 0 = leftmost!
                if inverse {
                    lit = !lit
                }
                offset := (py*280 + col*7 + px) * 4
                if lit {
                    v.Pixels[offset+0..3] = ColorOn   //    {0x33, 0xFF, 0x33, 0xFF}
                } else {
                    v.Pixels[offset+0..3] = ColorOff  //    {0x00, 0x00, 0x00, 0xFF}
                }
            }
        }
    }
}
```

Iteration count per frame:

| Level         | Iterations | Cumulative |
|---------------|-----------:|-----------:|
| rows          |         24 |         24 |
| × cols        |         40 |        960 |
| × scanlines   |          8 |      7,680 |
| × pixels      |          7 |     53,760 |

Every frame: 960 reads from screen RAM, 7,680 `CharGenROM` calls, 53,760 four-byte writes into `v.Pixels`. The renderer does not track "what changed" -- it just regenerates everything 60 times a second. Modern CPUs handle this comfortably in well under 1 ms.

For a line-by-line decipher of the four loops -- including the "scanline = horizontal stripe" visualization, the bit-shift walk that explains why bit 0 is the leftmost pixel, and a worked example of the 'A' crossbar at scanline 4 -- see `08.walkthrough_video.md` §6 ("Layer 4 -- Pixel loop" and the "What 'scanline' actually means visually" subsection that precedes it).

### Step D3: Zooming In on the 'A' at Row 0, Col 1

The cell at `$0401` is visited when `row = 0`, `col = 1`. The inner two loops walk all 8 scanlines and all 7 pixel columns.

**The eight glyph rows for 'A'** come back from `CharGenROM(0xC1, scanline)` (see `07.walkthrough_chargen.md` §4 for the decode logic):

| scanline | `pixels` | binary    | shape (`#` = lit) |
|---------:|:--------:|:---------:|:------------------|
| 0        | `0x08`   | `0001000` | `...#...` (peak)  |
| 1        | `0x14`   | `0010100` | `..#.#..`         |
| 2        | `0x22`   | `0100010` | `.#...#.`         |
| 3        | `0x22`   | `0100010` | `.#...#.`         |
| 4        | `0x3E`   | `0111110` | `.#####.` (crossbar) |
| 5        | `0x22`   | `0100010` | `.#...#.`         |
| 6        | `0x22`   | `0100010` | `.#...#.`         |
| 7        | `0x00`   | `0000000` | `.......` (descender blank) |

**The flash check is a no-op for our byte.** `$C1` is not in the `$40-$7F` range, so `inverse` stays false regardless of `FlashState`. If we had stored `$41` (just bit 7 missing), the flash branch would fire every other ~270 ms, and the 'A' would visibly blink.

**Bit-to-pixel expansion for scanline 0** (`pixels = 0x08`):

```text
  px = 0 → bit 0 of 0x08 = 0 → lit = false → ColorOff (black)
  px = 1 → bit 1 of 0x08 = 0 → lit = false → ColorOff
  px = 2 → bit 2 of 0x08 = 0 → lit = false → ColorOff
  px = 3 → bit 3 of 0x08 = 1 → lit = true  → ColorOn  (green!)
  px = 4 → bit 4 of 0x08 = 0 → lit = false → ColorOff
  px = 5 → bit 5 of 0x08 = 0 → lit = false → ColorOff
  px = 6 → bit 6 of 0x08 = 0 → lit = false → ColorOff
```

**Bit 0 is the leftmost pixel, not the rightmost** -- the opposite of the usual binary convention. So the lit pixel is at column 3 of the cell, the apex of the 'A'.

### Step D4: The `v.Pixels` RGBA Buffer

`v.Pixels` is a flat `[]uint8` of length `280 * 192 * 4 = 215,040` bytes, allocated once at `video/video.go:31`:

```go
Pixels: make([]uint8, ScreenW*ScreenH*4),
```

The layout is row-major RGBA:

```text
  v.Pixels layout (280 px wide, 192 px tall, RGBA = 4 bytes/pixel):
  +-------------------------------------------------------------+
  | Row 0:   [R G B A][R G B A][R G B A] ... [R G B A]          |  280 px = 1,120 bytes
  | Row 1:   [R G B A][R G B A][R G B A] ... [R G B A]          |
  |  ...                                                        |
  | Row 191: [R G B A][R G B A][R G B A] ... [R G B A]          |
  +-------------------------------------------------------------+
                              total = 280 * 192 * 4 = 215,040 bytes
```

The offset for pixel `(px_abs, py)` is:

```go
offset := (py*ScreenW + col*CharW + px) * 4
        = (py*280     + col*7    + px) * 4
```

For our 'A' apex pixel (`row=0`, `col=1`, `scanline=0`, `px=3`):

```text
  py     = 0*8 + 0 = 0
  px_abs = 1*7 + 3 = 10
  offset = (0*280 + 10) * 4 = 40

  v.Pixels[40..43] = {0x33, 0xFF, 0x33, 0xFF}   ← phosphor green
```

### Step D5: GPU Upload via `texture.Update`

Back in `main.go:377`:

```go
texture.Update(nil, unsafe.Pointer(&vid.Pixels[0]), int(video.ScreenW)*4)
```

`texture` was created at `main.go:163-167` as a streaming SDL texture sized 280x192 in `PIXELFORMAT_RGBA32` -- exactly matching `v.Pixels`. `texture.Update` is essentially a `memcpy` from system RAM (`v.Pixels`) into VRAM (the GPU's local memory). The arguments:

- `nil` -- update the whole texture (no sub-rectangle).
- `unsafe.Pointer(&vid.Pixels[0])` -- source pointer in system RAM.
- `int(video.ScreenW)*4 = 1120` -- pitch (bytes per source row); tells SDL how to step through `v.Pixels`.

After this returns, the GPU has a 280x192 texture matching the current frame.

### Step D6: Draw to the Back Buffer

```go
renderer.Clear()
renderer.Copy(texture, nil, nil)
```

- `Clear` paints the back buffer with the renderer's default color. Mostly a safety move -- the next `Copy` overdraws the whole area.
- `Copy(texture, srcRect, dstRect)` schedules a GPU draw call: stretch our 280x192 texture across the entire SDL window. Because the texture is much smaller than the window (it could be 840x624 or whatever the user chose), the GPU upscales it. The hint set at `main.go:161`:

```go
sdl.SetHint(sdl.HINT_RENDER_SCALE_QUALITY, "0")
```

selects **nearest-neighbor** scaling -- each emulator pixel becomes a sharp rectangle, no bilinear blurring. That's why the Apple II text looks crisp and chunky regardless of how big the host window is.

At this point the back buffer holds the new frame; the user's monitor is still showing the *previous* frame.

### Step D7: Swap Back Buffer to Front

```go
renderer.Present()
```

This is the buffer swap. The back buffer (the one we just drew) becomes the new front buffer; the old front buffer becomes the new back buffer (and will get cleared/overdrawn next frame).

Vsync is **disabled** in this emulator -- see the comment at `main.go:149-151`:

> No RENDERER_PRESENTVSYNC: we use time.Sleep-based pacing in the main loop as the single frame cap. VSync + manual cap cause speed drift on non-60 Hz displays (e.g. 120 Hz ProMotion, 59.94 Hz NTSC).

So `Present` returns immediately rather than blocking until the next display refresh, and the OS compositor decides when to actually push the frame to the display hardware.

### Step D8: From SDL to Your Eyes

The remaining stages are out of our control:

```text
  renderer.Present()
       |
       v
  OS compositor (Quartz / DWM / Mutter)
       |  combines our window with any other on-screen windows
       v
  GPU framebuffer
       |  scanned out over HDMI / DisplayPort / etc.
       v
  Monitor electronics
       |  drive the LCD or OLED pixels
       v
  Photons -> user's eyes -> retina -> visual cortex
```

End-to-end latency from `STA $0401` to "user sees the 'A'": roughly one host frame (~16.67 ms) plus one display refresh (~16.67 ms), so 17-33 ms typical. On the real 1977 Apple II it was essentially zero because the CRT was scanning DRAM live -- the byte became electrons within microseconds of the store. In the emulator the 60 Hz polling cadence is the price of running on a modern GPU stack.

### Diagram D2: The Full Post-COUT Journey

```text
  CPU: STA $0401, A=$C1
       |
       v  (write to RAM, no notification fires)
  ram[0x0401] = 0xC1
       |
       |  ... up to 16.67 ms pass ...
       v
  main loop's render tick (60 Hz)
       |
       v
  vid.Render(textMode=true, ...)
       |  flashCounter++ -> maybe toggle FlashState
       v
  RenderText -> renderTextRows(0, 24)
       |
       |  for row=0..23:
       |    for col=0..39:
       |      screenByte = ram[textLineAddr(row) + col]
       |      for scanline=0..7:
       |        (pixels, inverse) = CharGenROM(screenByte, scanline)
       |        if screenByte in $40-$7F and FlashState: inverse=true
       |        for px=0..6:
       |          lit = bit px of pixels         (bit 0 = LEFT)
       |          if inverse: lit = !lit
       |          v.Pixels[(py*280 + col*7 + px)*4 .. +4] = ColorOn or ColorOff
       v
  v.Pixels: 280 x 192 x 4 = 215,040 bytes, full RGBA snapshot
       |
       v
  texture.Update(...)        --> memcpy system RAM into VRAM
       |
       v
  renderer.Clear()
  renderer.Copy(texture, ...) --> GPU draws texture upscaled
                                   nearest-neighbor
       |
       v
  renderer.Present()         --> swap back buffer -> front buffer
       |
       v
  OS compositor -> GPU framebuffer -> monitor -> photons
       |
       v
  User sees the 'A'
```

### Key Takeaways

1. **The renderer is a polling system, not event-driven.** Writing to screen RAM doesn't trigger anything. The next 60 Hz tick will pick it up.
2. **The whole screen is recomputed every frame.** No diffing, no dirty rectangles, no "only update what changed." Modern hardware is more than fast enough to brute-force it.
3. **Bit 0 is the leftmost pixel** -- the opposite of standard binary convention. This is the single most common trap when reading the rendering loop.
4. **`v.Pixels` is a complete RGBA framebuffer**, the same layout SDL expects. The renderer produces a tiny bitmap image (280x192) each frame.
5. **The GPU upscales nearest-neighbor.** That preserves the chunky pixel aesthetic regardless of window size.
6. **`Present` doesn't immediately put pixels on the monitor** -- it hands the back buffer to the OS compositor, which eventually drives the display hardware.

### The One-Line Summary

After `STA $0401`, the byte sleeps in DRAM until the next 60 Hz render tick. `vid.Render` then walks all 960 screen cells, calls `CharGenROM` for each of the 7,680 cell-scanlines, expands every 7-bit glyph row into 7 RGBA pixels in `v.Pixels`, and hands the resulting 280x192 frame buffer to SDL. SDL uploads it to a GPU texture, draws the texture upscaled with nearest-neighbor filtering, and swaps the back buffer to the front. The OS compositor and GPU push the result to the monitor, and the user finally sees the 'A' -- about 17-33 ms after the CPU stored the byte.
