## Section 0: Background -- What a `.dsk` File Actually Is

### What It Is

When you pass `-disk1 foo.dsk` on the command line, the emulator opens a file from the host filesystem. That file is not a disk image in the sense of a forensic sector-by-sector dump with headers and checksums. It is a flat, sequential byte stream: 35 concentric rings of sectors, one after another, with no framing or metadata at all. For the user-level perspective on what a `.dsk` file contains from a DOS 3.3 standpoint, see `docs/dos33_user_guide.md`. This walkthrough is about how the emulator loads and manages that file.

The geometry the emulator enforces is fixed and inherited directly from the Apple Disk II hardware:

- **35 tracks** -- the spinning platter has 35 concentric rings of magnetic flux. The innermost ring is track 0; the outermost is track 34.
- **16 sectors per track** -- each ring is divided into 16 addressable blocks, numbered 0 through 15.
- **256 bytes per sector** -- each block holds exactly 256 bytes of user data.

The three constants are declared together in `disk/gcr.go:47-54`:

```go
const (
    tracksPerDisk = 35
    // maxHalfTrack is the highest legal halfTrack index. 35 tracks ->
    // halfTracks 0..69 (70 positions total); index 70 would map to
    // track 35, out of bounds for nibbles[tracksPerDisk].
    maxHalfTrack    = 2*tracksPerDisk - 1
    sectorsPerTrack = 16
    bytesPerSector  = 256
    ...
)
```

Their product -- 35 x 16 x 256 -- is the only legal file size. `disk/image.go:10` captures this as a named constant:

```go
const imageSize = tracksPerDisk * sectorsPerTrack * bytesPerSector // 143360
```

**This is the 143360-byte invariant.** Any `.dsk`, `.do`, or `.po` file that is not exactly this size will be rejected. No padding. No truncation. No guessing.

**Diagram 1: The 143360-byte flat layout**

```text
  .dsk file on host filesystem
  +---------------------------------------------------------------+
  | track 0, sec 0 | track 0, sec 1 | ... | track 0, sec 15      |  16 x 256 = 4096 bytes
  +---------------------------------------------------------------+
  | track 1, sec 0 | track 1, sec 1 | ... | track 1, sec 15      |
  +---------------------------------------------------------------+
  | ...                                                           |
  +---------------------------------------------------------------+
  | track 34, sec 0 | track 34, sec 1 | ... | track 34, sec 15   |
  +---------------------------------------------------------------+

  total: 35 tracks x 16 sectors/track x 256 bytes/sector = 143360 bytes
         ^^^^^^^^^   ^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^
         tracksPerDisk  sectorsPerTrack  bytesPerSector

  Any other length is a HARD ERROR. No padding. No truncation.
```

**Scope boundary** -- what this doc does NOT cover:

- **`.nib` (nibble dumps)**, **`.woz` (variable-rate flux)**, **`.2mg` (ProDOS wrapper)**: not supported. Known unimplemented; no current plans. The flat 143360-byte sector format is the only format this emulator handles.
- **13-sector (pre-DOS-3.3) format**: not supported. Only 16-sector 143360-byte files are accepted.
- **GCR encoding**: covered in `13.walkthrough_disk_gcr.md`. This doc treats the nibble stream as an opaque output of `EncodeTrack` and input of `DecodeTrack`.
- **Drive state and nibble cache**: covered in `14.walkthrough_disk_drive.md`.
- **Q6/Q7 softswitches and write path**: covered in `15.walkthrough_disk_controller.md`.
- **RWTS / DOS 3.3 command syntax**: user-facing material in `docs/dos33_user_guide.md` and `docs/dos33_boot_journey.md`.

**Terms this doc OWNS** -- the following terms are defined here and used throughout the series. Other docs cross-link back.

| Term | One-sentence definition | Expanded in |
|------|------------------------|-------------|
| **track** | Concentric ring on the platter surface; 35 per Apple II floppy, indexed 0..34 | §0, §1 |
| **sector** | 256-byte block; 16 per track, indexed 0..15 | §0, §1 |
| **logical sector** | The sector number the OS addresses (0..15); the `.dsk` file stores bytes in this order | §2 |
| **sector order** | `SectorOrder` enum: `OrderDOS` for `.dsk`/`.do`, `OrderProDOS` for `.po` | §3 |

Physical sectors (the order the head encounters them as the disk spins) are a separate concept owned by `13.walkthrough_disk_gcr.md` §2, where the interleave tables live.

### Why It Matters

The flat 143360-byte format is the bridge between the host OS and the emulated machine. Everything the emulator does -- loading, writing, flushing, hot-swapping -- passes through this layer. Getting the invariant right at load time means that every downstream system (GCR encoder, drive state, controller) can assume the image is complete and valid and never has to re-check.

### How the Code Works

`disk/image.go` (199 LOC) is the only file in scope for this walkthrough. It has one public function (`LoadImage`) and a handful of private methods (`trackSectors`, `flush`, `writeImage`, `writeCorruptImage`, `writeImageToFile`). The rest of the package (`controller.go`, `drive.go`, `gcr.go`, `device.go`, `tracer.go`) consumes those surfaces but does not re-implement them.

### Real-World Analogy

A stack of index cards. 35 rings (tracks), 16 cards per ring (sectors), 256 characters per card (bytes). If someone hands you a stack with 34 rings, or 17 cards per ring, or 255 characters per card, you refuse the stack -- you do not guess which card is missing, add a blank one, and hope for the best.

## Section 1: The `diskImage` Struct -- What It Holds

### What It Is

`disk/image.go:19-26` declares the `diskImage` struct that backs every mounted floppy:

```go
// diskImage holds the raw sector data for a 35-track, 16-sector, 256-byte/sector disk.
type diskImage struct {
    path      string
    order     SectorOrder
    writeProt bool
    // data[track][logicalSector][byte] in file (logical) sector order
    data [tracksPerDisk][sectorsPerTrack][bytesPerSector]uint8
}
```

Four fields only. Imports at `disk/image.go:1-8` are deliberately minimal: `fmt`, `os`, `path/filepath`, `strings`. **No binary parsers, no `encoding/hex`, no `encoding/binary`.** A `.dsk` is flat bytes; parsing is a straight `copy`.

The helper struct `decodedTrack` at `disk/image.go:12-17` holds one decoded dirty track (`track int`, `sectors [16][256]uint8`, `ok bool`). It is only used by the flush path (§6) and is introduced here so the rest of the doc can refer to it by name.

### Why It Matters

The `data` field is a **fixed-size 3D array**, not a slice: `[35][16][256]uint8`. That is exactly 143360 bytes embedded directly inside the struct -- no pointer indirection, no heap allocation for sector data. After `LoadImage` returns, the entire image lives in one contiguous allocation. The `raw` buffer that `os.ReadFile` returned is discarded; the image does not pin the OS read buffer in memory.

> The struct stores sectors in **logical** order -- the order the OS
> sees. Interleave (the mapping from logical to physical sector number)
> is the encoder's job, not the image's. The image is "everything the
> OS asked to read/write, laid out linearly". This split is why
> `trackSectors` (§5) can return `img.data[track]` verbatim without
> consulting `order`.

### How the Code Works

- `path string` -- the host filesystem path the image was loaded from. Also the flush destination in §6.
- `order SectorOrder` -- `OrderDOS` or `OrderProDOS`, inferred from the file extension or overridden via `-order`. Fully covered in §3.
- `writeProt bool` -- derived from file mode at load time, NOT from the image format or its contents. Fully covered in §4.
- `data [tracksPerDisk][sectorsPerTrack][bytesPerSector]uint8` -- the full image in memory. Once populated, nothing inside `image.go` touches it except during load and flush.

### Real-World Analogy

A warehouse storing crates by aisle (track) and shelf number (sector). What the crates contain, and whether the shelves are visited in a rotation order while the conveyor belt spins, is the shipping department's problem. The warehouse just stores crates.

## Section 2: Loading the Image -- `LoadImage`

### What It Is

`LoadImage` is the only exported function in `disk/image.go`. Its signature at `disk/image.go:30`:

```go
func LoadImage(path, orderOverride string) (*diskImage, error)
```

Two arguments: the filesystem path and an optional order override (`""` means "infer from extension"; `"dos"` or `"prodos"` force a value). One return value plus error.

### Why It Matters

Every mount operation in the emulator -- whether from a `-disk1` flag at startup, a drag-and-drop hot-swap, or a `Ctrl+1` eject-and-reload -- passes through `LoadImage`. If it returns an error, the drive slot stays empty. There is no second chance; the caller does not retry with a different size or patch the bytes.

### How the Code Works

The function is a strict five-step pipeline (`disk/image.go:30-74`):

**Step 1: read the whole file** (`disk/image.go:31-34`). `os.ReadFile` returns the full byte slice or an error. No streaming, no memory-mapping. At 140 KB this is trivial.

**Step 2: size check** (`disk/image.go:35-37`). This is **L12-2**: the hard-error invariant.

```go
if len(raw) != imageSize {
    return nil, fmt.Errorf("disk image %s: size %d != %d", path, len(raw), imageSize)
}
```

Exactly `imageSize` (= 143360) bytes or the function returns. A 140000-byte `.dsk` is NOT padded to 143360. A 150000-byte file is NOT truncated. Both are errors, period.

**Step 3: sector-order decision** (`disk/image.go:39-49`). Deferred to §3.

**Step 4: write-protect decision** (`disk/image.go:51-56`). Deferred to §4.

**Step 5: linear copy** (`disk/image.go:60-74`). The outer loop walks tracks 0..34; the inner loop walks sectors 0..15; each iteration copies 256 bytes and advances an offset counter:

```go
offset := 0
for t := 0; t < tracksPerDisk; t++ {
    for s := 0; s < sectorsPerTrack; s++ {
        copy(img.data[t][s][:], raw[offset:offset+bytesPerSector])
        offset += bytesPerSector
    }
}
```

At the end, `offset == 143360`. The loop matches the file layout exactly -- track 0 sector 0 lands at file offset 0, track 0 sector 1 at offset 256, ... track 34 sector 15 at offset 143104.

The file format and the in-memory layout are byte-for-byte identical: track 0 sector 0 is at file offset 0, track 0 sector 1 at offset 256, track 34 sector 15 at offset 143104. We could skip the copy and `unsafe.Slice` the raw buffer straight into `img.data`, but `img.data` is a fixed-size array (not a slice) and deterministic ownership matters -- the `raw` slice from `os.ReadFile` goes out of scope after `LoadImage` returns. The copy severs that dependency.

### Real-World Analogy

Unloading a truck into a warehouse. The truck bed (`raw`) is one flat surface; the warehouse has labelled shelves (`img.data[track][sector]`). The forklift moves 256 boxes at a time in order. The truck leaves; the clipboard goes in the drawer.

## Section 3: Sector Order -- Extension Inference and `-order` Override

### What It Is

`SectorOrder` is an integer type defined in `disk/gcr.go:6-13`:

```go
// SectorOrder selects the logical-to-physical sector mapping used when
// encoding/decoding a disk image.
type SectorOrder int

const (
    OrderDOS    SectorOrder = iota // .dsk / .do  -- DOS 3.3 order
    OrderProDOS                    // .po         -- ProDOS order
)
```

The two values correspond to two different filesystems, not two different physical layouts. The file stores sector bytes in "logical order" -- the order the OS addresses them. What differs between `OrderDOS` and `OrderProDOS` is which interleave table the encoder (`EncodeTrack`) uses when converting those logical bytes into the physical nibble stream the drive head emits. The interleave tables themselves (`dosInterleave` at `disk/gcr.go:17` and `prodosInterleave` at `disk/gcr.go:20`) are covered in `13.walkthrough_disk_gcr.md` §3.

### Why It Matters

Loading a ProDOS disk with `OrderDOS` (or vice versa) produces a nibble stream with the sectors in the wrong physical rotation. The boot code reads garbage, the DOS directory is unreadable, and the disk appears blank or corrupt. The order flag is not cosmetic -- it determines which sectors the head finds at which angular positions.

**L12-3: extension-based inference is the only heuristic.** There is no boot-sector inspection. `disk/image.go:77-89`:

```go
func inferOrder(path string) SectorOrder {
    switch strings.ToLower(filepath.Ext(path)) {
    case ".po":
        return OrderProDOS
    case ".dsk", ".do":
        return OrderDOS
    default:
        fmt.Fprintf(os.Stderr, "disk: unknown extension %q, defaulting to DOS order (use -order to override)\n",
            filepath.Ext(path))
        return OrderDOS
    }
}
```

The `.dsk` and `.do` cases are treated identically -- both return `OrderDOS`. The emulator **cannot distinguish them**. Community convention is that `.do` explicitly labels a DOS-order file, while `.dsk` is ambiguous-but-usually-DOS. This emulator treats them as one case, which is a known simplification: real heuristic tools can inspect the boot sector for a DOS or ProDOS signature. This emulator does not.

Any other extension (`.img`, `.bin`, or no extension) prints a stderr warning and defaults to DOS order.

### How the Code Works

**L12-4: the `-order` override** (`disk/image.go:40-49`):

```go
switch strings.ToLower(orderOverride) {
case "dos":
    order = OrderDOS
case "prodos":
    order = OrderProDOS
case "":
    // keep inferred
default:
    fmt.Fprintf(os.Stderr, "disk: unknown -order %q; using inferred order\n", orderOverride)
}
```

- `strings.ToLower` case-folds the user input. `"DOS"`, `"dos"`, and `"Dos"` all work.
- Accepts exactly two non-empty values: `"dos"` and `"prodos"`.
- The empty string `""` falls into `case "":` and keeps the inferred order. This is an explicit case, not the default -- the distinction matters because `""` and `"garbage"` land in different branches.
- Any other non-empty value (e.g. a `"prdos"` typo) prints a stderr warning and **keeps the inferred order** -- it is NOT an error. The code reaches the `default:` branch only for non-empty unknown values.

> One reason the override is lenient (warning, not error) is to keep
> drag-and-drop hot-swap paths from failing: the main loop cannot
> always pass an override at runtime, and a loud stderr message is
> enough to tell a curious user that the flag was ignored. Quiet
> fallback + visible warning is the Go stdlib flag-parsing style.

### Real-World Analogy

The filename extension is the envelope's return address -- a hint, not a proof. The `-order` flag is a postmark override: you can stamp the envelope yourself if you know better. If your stamp says "Mars", the post office ignores it and ships to the return address anyway, with a sticky note saying "we ignored your stamp."

## Section 4: Write-Protect -- From File Mode, Not Image Contents

### What It Is

The `.dsk` / `.do` / `.po` formats have no header and no metadata fields. There is nowhere inside the 143360-byte body to store a "this disk is read-only" flag. The emulator derives write-protect from the host filesystem's permission bits instead.

`disk/image.go:56`:

```go
wp := info.Mode()&0200 == 0 // write bit clear -> write-protected
```

`0200` is an octal literal -- the Unix owner-write bit. When it is clear (the file is read-only on the host), `writeProt` is set to `true` and the emulated floppy behaves as if the write-protect notch is covered.

### Why It Matters

**L12-5**: this is a file-mode decision, not an image-format decision. The image contents have no say.

- `chmod -w foo.dsk` before launching the emulator is how you ship a disk as read-only in this emulator. No `.locked` sidecar, no special filename prefix, just standard filesystem permissions.
- Copying a read-only `.dsk` via `cp` / `unzip` / `git checkout` usually produces a writable copy -- the destination file's mode comes from the umask or the archive's flags, not from the original. Re-check the mode bit of any copy you intend to use as read-only in the emulator.
- Windows users see the Go runtime's approximation of `0200` from NTFS ACLs. It works for the common case; the mapping from NTFS to the Unix bit is a Go runtime implementation detail outside this package's concern.

### How the Code Works

`disk/image.go:51-58` calls `os.Stat(path)` and derives the flag:

```go
wp := info.Mode()&0200 == 0 // write bit clear -> write-protected
img := &diskImage{path: path, order: order, writeProt: wp}
```

After `LoadImage` returns, the flag is copied at two sites (teaser -- full coverage in `15.walkthrough_disk_controller.md` §7):

- `disk/controller.go:67` -- `Mount` copies `img.writeProt` onto `c.drives[driveIdx].writeProt`.
- `disk/controller.go:245` -- `Swap` does the same on hot-swap.

> The emulator does not store write-protect in the image file because
> there is nowhere to put it -- a `.dsk` has no reserved header bytes
> and the 143360-byte invariant leaves no slack. The filesystem's
> permission bit is the only out-of-band metadata we can consult
> without inventing a new format. A future `.woz` implementation
> would have a proper "write protected" header field and this
> heuristic would be replaced.

### Real-World Analogy

A library book's check-out slip. The book itself does not know whether it is available -- the slip glued to the inside back cover is external metadata kept by the library, and the emulator's librarian checks the slip before handing the book to someone with a pen.

## Section 5: `trackSectors` -- The Logical-Order Accessor

### What It Is

`trackSectors` is the smallest method in `disk/image.go`. Its full body (`disk/image.go:91-95`):

```go
// trackSectors returns the 16 sectors of a track in logical order, ready for
// EncodeTrack. The caller owns the returned array.
func (img *diskImage) trackSectors(track int, order SectorOrder) [sectorsPerTrack][bytesPerSector]uint8 {
    return img.data[track]
}
```

Three lines including the closing brace.

### Why It Matters

**L12-8**: the `order` parameter is deliberately unused. The body returns `img.data[track]` verbatim, with no branch on `order`.

This is intentional API symmetry, not an oversight:

- The image holds sectors in **logical** order, always. It does not know about physical layouts.
- Re-interleaving logical -> physical is the **encoder's** job. `EncodeTrack` (covered in `13.walkthrough_disk_gcr.md` §3) owns the `dosInterleave` and `prodosInterleave` tables and applies the rotation when building the nibble stream.
- Keeping `order` in the signature means that both call sites pass the same `order` value they will need downstream, and the image does not need to branch on it. The parameter travels through `trackSectors` unchanged and arrives at `EncodeTrack` with its semantics intact.
- Moving the interleave into `trackSectors` would also require moving it into the decode path in `flush` (§6), creating two places that must agree. The current design keeps the responsibility boundary clean.

The parameter is a candidate for cleanup (a `_ = order` annotation or dropping the parameter entirely), but that is a code task for a future round, not a walkthrough finding. Meta-plan §6 Q8 confirmed: document as intentional.

### How the Code Works

`trackSectors` is called from exactly two places:

- `disk/drive.go:94` -- `trackData` calls `d.image.trackSectors(t, order)` and feeds the result into `EncodeTrack`. This is the lazy nibble-encoding path (covered in `14.walkthrough_disk_drive.md` §4).
- The controller write path transitively calls `d.trackData(d.image.order)`, which lands here via `trackData`.

Both sites pass `d.image.order` -- so the value threads through even though `trackSectors` ignores it.

> Reading `trackSectors`' body and expecting to see a branch on
> `order` is a reasonable instinct. It is not there because this
> package draws a strict line: the image is logical bytes, the
> encoder applies the physical-layout rotation. If you moved the
> interleave up here, you would also have to move it into every
> caller of `img.data[track]` on the decode path in `flush` (§6).
> Keeping the image interleave-blind keeps the responsibility
> boundary clean.

### Real-World Analogy

A filing cabinet whose drawers are labelled "Customer 1" through "Customer 15". You pull the drawer the same way every time. How the receptionist walks the aisle (the interleave) is the receptionist's job -- the cabinet stores folders in the order the OS assigned them.

## Section 6: The Flush Path -- Writeback, Sidecar, Atomic Rename

### What It Is

The flush path is the write side of the image layer. When the emulated CPU writes to a floppy, the controller marks the affected track as "dirty" in the drive state. When the motor turns off (or the emulator closes), those dirty tracks are decoded back from GCR nibbles to logical sectors and written to the host filesystem. `flush` is the method that orchestrates this.

### Why It Matters

Without a flush path, every write would be lost the moment the emulator exits. The flush path is also where data integrity decisions happen: what to do when a GCR decode fails, whether to risk overwriting the original file with partial data, and how to ensure that a mid-write crash leaves the host file intact.

### How the Code Works

#### 6.1 Who Calls `flush`, and When

Three call sites trigger `flush`:

- `disk/controller.go:75` -- `Close()` calls `flushAll()`, which calls `img.flush`. This is the "emulator exit" path.
- `disk/controller.go:333` -- the MOTOROFF strobe (`$C0E8`) calls `flushAll()`. This is the **primary flush trigger in normal operation**: every time DOS 3.3 turns off the drive motor, dirty tracks land on the host filesystem. Full coverage of the MOTOROFF strobe is in `15.walkthrough_disk_controller.md` §4.
- `disk/controller.go:190` -- `Swap` flushes the outgoing image before loading the new one on a hot-swap.

All three go through `flushAll` at `disk/controller.go:79-94` (see §6.2).

#### 6.2 Dirty-Track Collection (L12-7)

`flushAll` (`disk/controller.go:79-94`) is the outer loop. It walks both drives, skips nil images, and uses a `map[*diskImage]bool` to call `img.flush(&c.drives)` exactly once per distinct image pointer. If the same `*diskImage` is mounted in both slots, flush fires once.

Inside `flush`, the dirty-track collection loop at `disk/image.go:108-114` applies a second filter:

```go
for di := range drives {
    for t := 0; t < tracksPerDisk; t++ {
        if drives[di].dirty[t] && drives[di].image == img {
            dirty = append(dirty, dirtyEntry{di, t})
        }
    }
}
```

The `drives[di].image == img` check is pointer identity. This is a two-tier defence: `flushAll` deduplicates at the image level; `flush` deduplicates at the track level. `disk/image.go:115-117` adds an early return when nothing is dirty (`if len(dirty) == 0 { return nil }`).

#### 6.3 Per-Entry Decode and Error Accumulation

`disk/image.go:119-136` iterates over the dirty list and calls `DecodeTrack` (from `13.walkthrough_disk_gcr.md`) on each:

- If `d.nibbles[de.track] == nil` (`disk/image.go:124-127`): the track was marked dirty but never had its nibble buffer allocated (a defensive edge case). The existing `img.data[de.track]` is used as the decoded result with `ok: true`.
- On decode error (`disk/image.go:129-132`): `results[i].ok = false` and `allOK = false`. A `disk: flush: track N decode error: ...` message is printed to stderr immediately.
- On success (`disk/image.go:133-135`): `results[i]` holds the decoded sectors with `ok: true`.

`DecodeTrack` converts a GCR nibble buffer back into `[16][256]uint8`. If any sector's checksum fails, `DecodeTrack` returns an error. That is the L13-11 claim from the GCR doc -- partial decode returns an error -- and it is what triggers the `.corrupt` sidecar path below.

#### 6.4 The Two-Branch Decision (L12-6 Foundation)

`disk/image.go:138-150` branches on `allOK`:

- `allOK` true: call `img.writeImage(img.path, drives, results)` -- atomic replace of the original file (§6.6).
- `allOK` false: compute `corruptPath := img.path + ".corrupt"`, call `img.writeCorruptImage(corruptPath, ...)`, log to stderr, and return an error. The original `img.path` is **left untouched**.

This mirrors the "no-patching" philosophy of `LoadImage`: the emulator refuses to overwrite a good image with partially-decoded data, just as it refuses to load a wrong-size file rather than pad it.

#### 6.5 The `.corrupt` Sidecar (L12-6 Continued)

The suffix is the literal string `".corrupt"` appended to `img.path` at `disk/image.go:143`. A file named `foo.dsk` produces `foo.dsk.corrupt`. The sidecar is a valid 143360-byte image -- `writeCorruptImage` (`disk/image.go:173-182`) overlays only the tracks that decoded successfully and leaves the rest from `img.data`.

The critical difference between `writeImage` and `writeCorruptImage` is that `writeImage` (`disk/image.go:162-167`) clears dirty flags after a successful write:

```go
img.data[r.track] = r.sectors
for di := range drives {
    if drives[di].image == img {
        drives[di].dirty[r.track] = false
    }
}
```

`writeCorruptImage` (`disk/image.go:173-182`) has no such loop. The dirty flags remain set. This means the next MOTOROFF will retry flushing the same dirty tracks -- which is the correct behaviour: if the decode failure was transient (a GCR buffer corruption that was overwritten in the interval), the retry may succeed.

If writing the sidecar itself fails (`disk/image.go:144-145`), a louder message is emitted, but the original file is still intact. The contract -- "original file UNCHANGED on any decode failure" -- is unconditional.

> The `.corrupt` path is a **belt-and-braces** design. If GCR decode
> fails on any dirty track, the simple answer would be: do nothing,
> leave the image alone, warn. That is almost what we do -- except
> the sidecar preserves the user's work-in-progress for post-mortem
> inspection. A developer who wrote a custom low-level format to a
> dirty track and hit a decoder bug can recover the partially-valid
> remainder from `foo.dsk.corrupt`, feeding it back into a patched
> decoder. The original `foo.dsk` is never touched by the failure
> path -- the atomic rename only commits to `foo.dsk.corrupt`, and
> a missing rename just leaves a `.tmp` file next to the sidecar.

#### 6.6 Atomic Rename (L12-6 Complete)

`writeImageToFile` at `disk/image.go:184-199` serialises the 3D sector array into a flat 143360-byte buffer (the exact inverse of the `LoadImage` copy loop), writes it to `dest + ".tmp"`, and renames:

```go
tmp := dest + ".tmp"
if err := os.WriteFile(tmp, raw, 0666); err != nil {
    return err
}
return os.Rename(tmp, dest)
```

`os.Rename` is atomic on POSIX filesystems within the same mount point. Because `tmp` is `dest + ".tmp"`, both are always on the same mount. A crash between `WriteFile` and `Rename` leaves `dest` intact and a `.tmp` alongside it; the next run overwrites `.tmp` and renames cleanly. In no case is `dest` left partially written.

**Diagram 2: The two-path flush flow**

```text
  flush(drives)
       |
       v
  collect dirty tracks (both drives, filter image == img)
       +--- none dirty? -> return nil
       v
  for each (drive, track): DecodeTrack(nibs, img.order)
       +--- err? -> ok=false, allOK=false, print to stderr
       +--- ok?  -> ok=true

  allOK?
   |                                   |
   | yes                               | no
   v                                   v
  writeImage(img.path, ...)      writeCorruptImage(img.path+".corrupt", ...)
  overlay + clear dirty flags    overlay ok tracks only; dirty flags UNCHANGED
  writeImageToFile(img.path)     writeImageToFile(img.path+".corrupt")
  dest+".tmp" -> Rename(dest)    dest+".corrupt.tmp" -> Rename(dest+".corrupt")
   |                                   |
   v                                   v
  SUCCESS: dest updated atomically    original file UNCHANGED; return error
```

### Real-World Analogy

A bank's safe-deposit-box clerk. Three rules:
1. The customer's sealed box (the image file) is never opened without a successful key-check (decode).
2. If the key does not fit (decode failure), the clerk slides the papers the customer brought into a labelled envelope marked "pending review" (`.corrupt`) and puts the original box back untouched.
3. If the clerk does succeed, the box is replaced atomically -- the customer's old papers are removed and the new ones slotted in as a single action (`os.Rename`), never half and half.

## Section 7: Putting It Together -- One Full Mount -> Write -> Eject Cycle

This section traces a single disk session end-to-end through the code paths introduced in §2 through §6. The GCR encoding, drive state, and controller details mentioned here are teasers; their full treatment is in `13.walkthrough_disk_gcr.md`, `14.walkthrough_disk_drive.md`, and `15.walkthrough_disk_controller.md` respectively.

**Step 1: launch with `-disk1 foo.dsk`.**
Main calls `dc.Mount(0, "foo.dsk", "")` (`disk/controller.go:58-71`). `Mount` calls `LoadImage("foo.dsk", "")`. The size check at `disk/image.go:35-37` passes (143360 bytes). `inferOrder("foo.dsk")` returns `OrderDOS` (the `.dsk` extension matches `case ".dsk", ".do":`). `os.Stat` finds the file writable, so `wp = false`. `LoadImage` returns a valid `*diskImage`.

**Step 2: image copied into the drive slot.**
`Mount` (`disk/controller.go:66-67`) stores the pointer at `c.drives[0].image` and copies `img.writeProt` onto the drive. `writeProt = false` means writes reach the flush path. A stderr line confirms the mount.

**Step 3: CPU writes a sector.**
The user runs a program that calls DOS RWTS to write data. The controller (covered in `15.walkthrough_disk_controller.md`) receives the nibble stream via $C0EC write-run accesses and stores them into `drives[0].nibbles[trackN]`, setting `drives[0].dirty[trackN] = true`. The image's `data` field is unchanged at this point -- dirty bytes live only in the nibble buffer.

**Step 4: DOS turns off the motor.**
The MOTOROFF strobe at `$C0E8` fires `Strobe(0x0008)` in the controller (`disk/controller.go:327-333`). `Strobe` sets `motorOn = false` and immediately calls `flushAll()`.

**Step 5: `flushAll` finds the image.**
`disk/controller.go:79-94`: the `flushed` map is empty; drive 0 has a non-nil `image`. `flushed[img] = true`; then `img.flush(&c.drives)` is called.

**Step 6: dirty-track collection.**
`disk/image.go:108-114`: drive 0, track N is dirty AND `drives[0].image == img`. One `dirtyEntry{0, trackN}` is appended. Drive 1 has `image == nil`, so nothing is appended from it.

**Step 7: `DecodeTrack` succeeds.**
`disk/image.go:119-136` calls `DecodeTrack(d.nibbles[trackN], img.order)`. GCR decode succeeds (normal case -- see `13.walkthrough_disk_gcr.md` for the decode details). `results[0] = decodedTrack{track: trackN, sectors: ..., ok: true}`. `allOK = true`.

**Step 8: `writeImage` commits to disk.**
`disk/image.go:138-139` calls `writeImage("foo.dsk", drives, results)`. `writeImage` (`disk/image.go:155-171`) overlays `results[0].sectors` into `img.data[trackN]`, clears `drives[0].dirty[trackN] = false`, then calls `writeImageToFile("foo.dsk", newData)`. `writeImageToFile` writes `foo.dsk.tmp` (143360 bytes) and `os.Rename("foo.dsk.tmp", "foo.dsk")`. The file is updated atomically.

**Step 9: user drag-drops a new disk.**
The main loop receives an SDL drop event and calls `dc.Swap(0, newPath)` (`disk/controller.go:175-251`). `Swap` calls `d.image.flush(&c.drives)` on the outgoing image first (`disk/controller.go:190`). Because `dirty[trackN]` was cleared in step 8, `flush` returns nil immediately (the early-return at `disk/image.go:115-117`). Then `Swap` resets the per-drive state, calls `LoadImage(newPath, "")`, stores the new `*diskImage`, and logs the swap. The `label` field (cached display name for the title bar -- see `14.walkthrough_disk_drive.md` §6 for full coverage) is updated via `deriveLabel(newPath)` at `disk/controller.go:246`.

**Step 10: user quits.**
The deferred `dc.Close()` in main calls `flushAll()` one last time. Nothing is dirty (the last motor-off already flushed, and no writes happened after the swap). `flush` returns nil at `disk/image.go:115-117`. The process exits cleanly.

## Section 8: Design Decisions and Hardware Reality

### What It Is

Questions a careful reader will ask after §2 through §6, answered from source.

### Why It Matters

Understanding why these decisions were made -- not just what they are -- separates a reader who can extend the code from one who can only read it.

### How the Code Works

**Q1: Why a hard error on size mismatch instead of auto-padding?** (L12-1, L12-2)

143360 is the product of three hardware geometry constants. Any file that is not exactly this size did not come from a 35-track 16-sector 256-byte/sector Apple II floppy. Auto-padding would let truncated or corrupt images boot to garbage, making the failure mode worse than a clean refusal at load time. The error message at `disk/image.go:35-37` states the expected and actual sizes, which is the actionable information the user needs. Nothing more is needed.

**Q2: Why can the emulator not tell `.do` from `.dsk`?** (L12-3)

Both are DOS-order by convention. Neither has a header or signature. A boot-sector heuristic would work for well-formed images but misfire on damaged or custom disks. This emulator does not implement it. Users with an ambiguous file can use `-order prodos`.

**Q3: Why is write-protect from the file mode and not the image?** (L12-5)

The formats have no header bytes; the 143360-byte invariant is exact with no slack. File-mode bit `0200` (`disk/image.go:56`) is the only out-of-band signal available without inventing a new format. A future `.woz` implementation would read the format's own write-protect header field instead.

**Q4: Why does `trackSectors` ignore its `order` parameter?** (L12-8)

API symmetry. The image stores logical bytes; the encoder applies the physical interleave. Keeping `order` in the signature means callers pass it through to `EncodeTrack` without the image needing to branch on it. See §5 for the full argument.

**Q5: Why write to a `.tmp` file and then rename?** (L12-6)

`os.Rename` is atomic within a single mount point (`disk/image.go:194-198`). A crash mid-`WriteFile` leaves `dest` intact and a partial `.tmp` the next run overwrites. Without the rename, a crash could leave a 70 KB `foo.dsk` that fails the size invariant on the next load, stranding the user's data.

**Q6: Why write a `.corrupt` sidecar instead of just logging and bailing?** (L12-6)

The sidecar is forensic evidence. It is a valid 143360-byte image -- decoded where possible, unchanged elsewhere -- that a developer can load into a patched emulator or diff with the original. The original is never touched; the sidecar at `img.path + ".corrupt"` is strictly additive.

**Q7: Why does the dirty-collection loop filter on `drives[di].image == img`?** (L12-7)

`flush` is called per-image by `flushAll`. Without the filter, if the same `*diskImage` pointer appeared in both drive slots, `flush` would collect duplicate dirty entries for the same track. The pointer-identity filter plus `flushAll`'s `map[*diskImage]bool` is a two-tier defence.

**Q8: Why does `writeImage` clear dirty flags but `writeCorruptImage` does not?**

`writeImage` commits changes to the canonical file; clearing dirty flags is correct there. `writeCorruptImage` writes only a sidecar; the canonical file is unchanged. Leaving dirty flags set lets the next MOTOROFF retry -- correct if the decode failure was transient.

### Real-World Analogy

The whole design is belt-and-braces. The size invariant refuses damaged input. The file-mode bit reads permissions without touching the image. The atomic rename prevents half-written files. The sidecar preserves evidence without touching originals.

## Section 9: Summary -- What Is Here and What Is Next

`disk/image.go` (199 LOC) is deliberately the smallest of the four `disk/` files. Its job is narrow: load 143360 bytes, expose them as a 35x16x256 array, and flush dirty tracks atomically. Encoding, caching, and CPU-side access are the responsibility of the next three docs in the series.

> An Apple II disk image is 143360 bytes -- exactly 35 tracks times
> 16 sectors times 256 bytes per sector, laid out in logical order
> with no header and no checksum. The emulator refuses to patch up
> wrong-sized files at load time, reads write-protect from the host
> file's mode bit, and infers sector order from the `.dsk` / `.do` /
> `.po` extension with a `-order` override. On flush, dirty tracks
> are decoded from their GCR nibble buffers; if any track fails to
> decode, the original file is left untouched and a `.corrupt`
> sidecar preserves the partial result. Successful flushes land via
> tmp-file + atomic rename. The image object stays interleave-blind;
> reinterpreting logical sectors into physical nibble streams is the
> encoder's job, covered in the next doc.
