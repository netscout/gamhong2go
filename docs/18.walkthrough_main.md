## Section 0: Background -- What `main.go` Does at Phase-5+

### What It Is

`main.go` is the wiring node of the Apple II emulator. It is not itself a device; it is the
conductor that assembles six (or eight) devices onto a shared bus, launches the SDL2 host window, and
runs the per-frame pipeline that keeps them all synchronized. A reader who has worked through the
device walkthroughs knows what each device does in isolation; this doc shows how they meet.

The user sees an SDL2 window at 840x576 pixels (3x the native 280x192 Apple II resolution) running at
60 fps. The title bar shows `Apple II Emulator -- 60 fps` plus per-drive indicators like
`[D1:karateka ●]` when a disk is loaded. Dragging a `.dsk` file onto the window loads it into drive 1
(left half of window) or drive 2 (right half). Holding F12 engages turbo mode; the title bar switches
to `Apple II Emulator -- TURBO -- ...`. Ctrl+R resets the machine. Ctrl+1 / Ctrl+2 eject drives.
Shift+Esc quits.

**What changed since Phase 4.** Doc `09.walkthrough_main_phase4.md` walks the Phase-4 skeleton
(~285 LOC): SDL window, 60 Hz event loop, keyboard latch, CPU step inner loop. Phase 5+ layered
eight distinct features onto that same skeleton, tripling the LOC to 835. Each feature is packageless
-- it sits in `main.go` because it is host-side glue, not a new device:

- **F12 turbo (hold-not-toggle)** -- bypasses the frame cap while F12 is physically held.
- **Drag-and-drop hot-swap** -- loads a `.dsk` onto either drive mid-session without restart.
- **Paddle/button host input** -- arrow keys drive virtual paddle axes; LALT/RALT drive buttons.
- **Focus-loss safety** -- pauses audio, releases stuck inputs, disarms turbo on alt-tab/minimize.
- **Disk activity title bar** -- per-drive label + read/write glyph refreshed at 1 Hz.
- **VBL-aligned frame cap** -- sub-ms time.Sleep with audio back-pressure rationale (replaces the
  naive cap Phase 4 used).
- **Lazy `installDiskCard` closure** -- wires slot-6 PROM + softswitches on first need; one closure
  both startup and drag-drop reach.
- **Partial-ROM size detection** -- `loadROM` accepts any ROM whose size is in (0, 12288] via the
  `0x10000 - size` base formula.

### Why It Matters

`main.go` is the only file in the repository where all device packages appear together. No individual
device package knows about the bus (except through the `Device` interface). No bus knows which
devices belong together. Only `main.go` knows the correct install order, the correct clock-sharing
arrangement, and the correct tear-down sequence. Getting any of those wrong -- wrong order, wrong
pointer, wrong defer sequence -- silently mis-wires the machine.

### Real-World Analogy

A CNC-shop control cabinet that started life with a single power switch (Phase 3, trace harness).
Phase 4 added the operator console with screen and keyboard. Phase 5+ added a tool loader
(drag-drop), a turbo dial (F12), an emergency-pause sensor (focus loss), an activity-light board
(title-bar disk LEDs), and a proper sleep-controlled spindle pacing system (frame cap with
audio-aware floor). The cabinet box is the same; the wiring inside is now end-to-end.

## Section 1: Process Startup -- Imports, Constants, Flags

### What It Is

The first 75 lines of `main.go` do three things: import every device package by name, declare the
four constants that govern the whole emulator's timing and window geometry, and parse the nine
command-line flags that form the runtime configuration API.

### Why It Matters

Every runtime knob lives here. Every default lives here. Every hard-exit path is announced here.
A reader who understands §1 can predict what the process will do before any Go code runs.

### How the Code Works

**The import block** at `main.go:3-22` is flat: eight internal packages plus `go-sdl2`, `flag`,
`fmt`, `os`, `path/filepath`, `strings`, `time`, and `unsafe`. Each internal package is a device
walkthrough: `bus`, `cpu`, `disk`, `io` (aliased `appleio`), `languageCard`, `memory`, `speaker`,
`video`. `main.go` directly names every shipped package; no intermediaries.

**The constants** at `main.go:24-43` set the timing spine:

```go
// Apple II runs at 1.023 MHz; display refreshes at ~60 Hz.
//
// cyclesPerFrame = cpuClock / targetFPS = 17050 is deliberately 20
// cycles larger than the real NTSC video frame (262x65 = 17030, see
// io/softswitches.go). Speaker math keys samplesPerFrame to
// cpuClock/sampleRate = 735 exactly at 44.1 kHz; shrinking the CPU
// slice to 17030 would drain SDL's queue ~58 samples/sec. Games
// care about CPU clock accuracy (pitch, disk nibble timing) far
// more than host-frame wall-clock length; the resulting ~4.2 s/hour
// CPU-vs-video drift is imperceptible.
cpuClock       = 1023000
targetFPS      = 60
cyclesPerFrame = cpuClock / targetFPS // 17050
```

**L18-1** -- `cyclesPerFrame = 17050` is calibrated to speaker math, NOT to NTSC video timing. The
real NTSC video frame is 262x65 = 17030 cycles. Speaker math keys `samplesPerFrame` to
`cpuClock/sampleRate = 1023000/44100 = ~23.2 cycles/sample`, which yields exactly 735 samples/frame
at 17050. Shrinking to 17030 would drain SDL's audio queue by ~58 samples/second. Games care about
CPU clock accuracy (pitch, disk nibble timing) far more than host-frame wall-clock length; the
resulting ~4.2 s/hour CPU-vs-video drift is imperceptible. Cross-cite `11.walkthrough_speaker.md` §3
for the samples-per-frame math.

Window geometry: `windowScale = 3`, `windowW = video.ScreenW * 3 = 840`,
`windowH = video.ScreenH * 3 = 576` (all at `main.go:39-43`).

**The nine runtime flags** are declared at `main.go:46-55` and validated at `:57-75`.

**Diagram D2a (runtime flag table):**

```
  flag           default                  type      validation              line
  -------------  -----------------------  --------  ----------------------  ------
  -rom           "roms/Apple2_Plus.rom"   string    loadROM error -> exit1  46
  -volume        0.25                     float64   clamped to [0,1]        47, 67-75
  -samplerate    44100                    int       passed to speaker.New   48
  -disk1         ""                       string    passed to dc.Mount      49
  -disk2         ""                       string    passed to dc.Mount      50
  -order         ""                       string    passed to dc.Mount      51
                                                    (extension fallback)
  -disktrace     false                    bool      enables Tracer          52
  -disktracen    200                      int       max nibble lines        53
  -paddle        "arrows"                 string    arrows | off | exit1    54, 57-65
```

The `-paddle` flag at `main.go:57-65` is an exit-1 on unrecognized value. An unknown value would
silently fall through to `paddleArrows = false`, re-routing arrow keys to the keyboard latch -- a
surprising mode change. Hard exit forces the user to fix the typo. The `-volume` clamp at
`main.go:67-75` warns to stderr but does not exit; out-of-range volume is recoverable.

ROM load at `main.go:78-85`: `loadROM(*romPath)` is called here; on error the process prints a usage
hint and calls `os.Exit(1)`. This is the first of eight `os.Exit` calls in main.go (see §11 for the
full list and why defers do not run on these paths).

### Real-World Analogy

The front panel of a hi-fi amplifier. Each knob has a default, a labelled range, and a defined
failure mode. The volume knob can be turned past max but the amp clamps internally; the input
selector rejects invalid positions.

## Section 2: Bus Wire-Up -- 6 Devices Always, 8 with Disk

### What It Is

`main.go:87-186` plus the lazy install closure at `:212-241` together produce the complete bus
device registry. Six devices are always registered; two more appear when `installDiskCard` fires.
The order of `b.Map` calls is a correctness requirement, not a style choice.

### Why It Matters

The bus resolves overlapping address ranges by last-mapping-wins (`04.walkthrough_bus.md` §5). Three
device pairs have overlapping ranges; in each pair the later-registered device must shadow the
earlier one. If `b.Map` order changes, the wrong device wins.

### How the Code Works

**The `diskCycle` declaration** comes first:

```go
// diskCycle must be declared before sw so its address can be passed to
// NewSoftSwitches (paddle timers share this monotonic counter).
var diskCycle uint64

ram := memory.NewRAM()
sw  := appleio.NewSoftSwitches(&diskCycle)
b   := bus.NewBus()
```

**L18-4** -- `diskCycle` is declared BEFORE `sw` so its address can be passed to
`appleio.NewSoftSwitches(&diskCycle)` at `main.go:93`. The same pointer feeds the disk controller
at `main.go:196`. Paddle 555-timers in `SoftSwitches` consult this monotonic counter; sharing it
with the disk controller is a correctness requirement (paddle timeout must use the same monotonic
clock the disk uses). Cross-cite `15.walkthrough_disk_controller.md` §1.

**The six always-installed devices** at `main.go:96-186`:

```go
b.Map(0x0000, 0xBFFF, ram)              // main.go:96
b.Map(0xC000, 0xC0FF, sw)               // main.go:97
b.Map(rom.Base, rom.End(), rom)          // main.go:98
lc := languageCard.NewCard(rom)
b.Map(0xD000, 0xFFFF, lc)               // main.go:111
b.Map(0xC080, 0xC08F, languageCard.NewSwitches(lc))  // main.go:112
// ... speaker init ...
b.Map(0xC030, 0xC03F, speaker.NewDevice(spk))        // main.go:186
```

**L18-3** -- Six devices always installed; eight when disk is mounted; three overlap pairs resolved
by last-mapping-wins.

**Diagram D2 -- bus install order (extends `04.walkthrough_bus.md` §8):**

```
  Index  Range            Device                  Notes               Always?
  -----  ---------------  ----------------------  ------------------  --------
  0      $0000-$BFFF      ram (memory.RAM)        48 KB main RAM      yes
  1      $C000-$C0FF      sw (io.SoftSwitches)    256-byte I/O page   yes
  2      rom.Base-End()   rom (memory.ROM)        12 KB or 16 KB      yes
                                                  (12=$D000-$FFFF;
                                                   16=$C000-$FFFF)
  3      $D000-$FFFF      lc (languageCard.Card)  16 KB write RAM     yes
                                                  + ROM passthrough   (LC always
                                                                       installed)
  4      $C080-$C08F      languageCard.Switches   16-way bank-        yes
                                                  switch decoder
  5      $C030-$C03F      speaker.Device          16-way speaker      yes
                                                  toggle decoder
  6      $C600-$C6FF      prom (memory.ROM)       256-byte boot       OPTIONAL
                                                  PROM                (lazy)
  7      $C0E0-$C0EF      disk.Switches           16-way disk         OPTIONAL
                                                  decoder             (lazy)

  Last-mapping-wins overlaps:
    $C030-$C03F : sw (idx 1) shadowed by speaker.Device (idx 5)
    $C080-$C08F : sw (idx 1) shadowed by languageCard.Switches (idx 4)
    $D000-$FFFF : rom (idx 2) shadowed by lc (idx 3); lc delegates to
                  rom.Read when ramRead=false

  $C600-$C6FF (PROM) and $C0E0-$C0EF (disk switches) only present
  when installDiskCard() has fired. See §3.
```

**L18-2** -- LC unconditional install is intentional. The doc-comment at `main.go:100-107` states:

> Language Card (slot 0) -- 16 KB RAM overlaying $D000-$FFFF.
> Unconditional install: the three shipped ROMs (Apple2.rom,
> Apple2_Plus.rom at $D000 covering 12 KB; Apple2e.rom at $C000
> covering 16 KB) all fully cover $D000-$FFFF. If a future change
> ships a partial/minimal ROM that does not cover $D000-$FFFF,
> NewCard will hold a rom pointer whose Read returns 0xFF for
> uncovered offsets (see memory/rom.go) -- that is a configuration
> bug in the loader, not a runtime concern here.

The comment at `main.go:108-109` explains the SW/LC ordering: "Mapped AFTER io.SoftSwitches so its
`$C080-$C08F` handler wins the address-decode race (bus last-mapping-wins)."

The comment at `main.go:113-114` explains the LC/ROM passthrough: "ROM remains mapped underneath but
is never reached via bus fallthrough; the LC delegates to rom.Read when ramRead=false." Cross-cite
`10.walkthrough_languagecard.md` §5.

The speaker `b.Map` at `main.go:185-186` is placed after the disk controller construction code but
the comment says "Map speaker AFTER SoftSwitches so it wins $C030-$C03F." This is the same
last-mapping-wins reason: `sw` covers all of `$C000-$C0FF`, so speaker.Device at `$C030-$C03F` must
register later.

### Real-World Analogy

Hot-plug PCI on a workstation. The chipset has a fixed enumeration order (RAM, north-bridge,
south-bridge, BIOS). Each card has an assigned address window; later cards can shadow earlier ones (a
network card with a boot ROM shadows a chunk of the BIOS region). The Disk II card is the one card
that is optional and gets enumerated late.

**CPU and video init.** `main.go:116` prints "Iteration 7" -- a magic-string phase-wave marker.
`main.go:120-122`: `c := cpu.NewCPU(b); c.Reset()`. The reset reads vector `$FFFC/$FFFD`; at this
point LC has `ramRead=false` (the `NewCard` default), so `Read` delegates to `rom.Read` -- cross-
cite `10.walkthrough_languagecard.md` §3. `main.go:125`: `vid := video.NewVideo(ram.Data[:])` --
direct slice, no copy; cross-cite `16.walkthrough_video_lores.md` §1.

## Section 3: SDL Init + Speaker + Disk Controller + Lazy `installDiskCard`

### What It Is

Three sub-stories in sequence: (a) SDL window/renderer/texture/audio init (host-window plumbing),
(b) speaker init and bus install, (c) disk controller init and the lazy `installDiskCard` closure.
The lazy closure is the doc's headline novel exhibit.

### Why It Matters

SDL init determines the host-window contract. The speaker init wires `frameCycle` into the audio
path. The lazy install closure is the only place in the codebase where a single function body is
reachable from two distinct call sites (startup and drag-drop) and must remain idempotent across
both.

### How the Code Works

**SDL init** at `main.go:128-134` initializes VIDEO, EVENTS, and AUDIO subsystems, then explicitly
enables drag-and-drop events:

```go
sdl.EventState(sdl.DROPFILE, sdl.ENABLE)
```

The comment at `main.go:132-133` explains: "macOS defaults-on, but Linux X11/Wayland does not
guarantee this. Cite go-sdl2@v0.4.40/sdl/events.go:1357." The `defer sdl.Quit()` at `main.go:135`
is the first defer registered, and therefore the last to run (see §11).

Window and renderer creation at `main.go:137-158`. The renderer is created WITHOUT VSync:

```go
// No RENDERER_PRESENTVSYNC: we use time.Sleep-based pacing in the main loop
// as the single frame cap. VSync + manual cap cause speed drift on
// non-60 Hz displays (e.g. 120 Hz ProMotion, 59.94 Hz NTSC).
renderer, err := sdl.CreateRenderer(window, -1, sdl.RENDERER_ACCELERATED)
```

**L18-6** -- VSync was deliberately rejected; sleep-based pacing is the single frame cap. A
display running at 120 Hz ProMotion would VSync at 120 Hz while the manual cap tries to hold 60 Hz,
producing a drift that accumulates. The 59.94 Hz NTSC TV case similarly produces a slow drift in the
wrong direction. Sleep-based pacing adapts to the actual wall-clock host. Full pacing math in §8.

Nearest-neighbor scaling for crisp pixels at `main.go:160-161`:
`sdl.SetHint(sdl.HINT_RENDER_SCALE_QUALITY, "0")`. Texture creation at `main.go:163-172` with
`PIXELFORMAT_RGBA32` and `TEXTUREACCESS_STREAMING`.

**Speaker init** at `main.go:174-186`. `var frameCycle uint64` at `main.go:174` is a local in
`main()`. The speaker receives a POINTER to it; `main.go:361` resets `frameCycle = 0` every frame.
`speaker.New(speaker.Config{SampleRate, CPUClock, Volume}, &frameCycle)` at `main.go:175-179`.
`spkErr` is warning-not-fatal: an audio-less emulator still runs. `defer spk.Close()` at
`main.go:183` with comment `// LAST defer -> FIRST to run` -- that comment is now outdated (see §11
and L18-16); `dc.Close()` added later at `:200` is the actual last-declared defer. Speaker bus
install at `main.go:185-186`: "Map speaker AFTER
SoftSwitches so it wins `$C030-$C03F`." Cross-cite `11.walkthrough_speaker.md` §3 for the
`Config{}` field meanings.

**Disk controller init** at `main.go:188-200`. The doc-comment at `main.go:189-195` explains why
`diskCycle` never wraps: unlike `frameCycle` (reset to 0 each frame), diskCycle is monotonic so the
controller's `lastCycle` subtraction never underflows and causes `nibblePos` to jump. Cross-cite
`15.walkthrough_disk_controller.md` §1. `dc := disk.NewController(&diskCycle)` at `main.go:196`.
Tracer opt-in via `-disktrace`; cross-cite `15.walkthrough_disk_controller.md` §9.
`defer dc.Close()` at `main.go:200` flushes dirty tracks; cross-cite `12.walkthrough_disk_image.md`
§6.

**L18-5** -- The lazy `installDiskCard` closure. This is the headline novel exhibit of this doc.
The doc-comment at `main.go:202-211`:

> installDiskCard wires the Disk II slot-6 PROM and softswitches. It is idempotent: once installed,
> subsequent calls are no-ops. Called at startup (if any disk flag was given) and lazily on
> drag-and-drop so a user who launches with no -disk1/-disk2 flag can drop a disk mid-session.
>
> Ordering: PROM load first. If it fails, bail BEFORE mapping softswitches (avoids a half-installed
> card whose PROM region is blank). promFailed rate-limits stderr: first failure is verbose,
> subsequent failures are terse so three consecutive drops with a missing DISK2.rom produce one
> detailed line + two terse lines, not three identical long lines.

The closure body at `main.go:216-241` captures two state booleans (`diskCardInstalled`,
`promFailed`) and the bus `b`. The idempotency guard at `main.go:217-219` returns immediately if
`diskCardInstalled` is true. On first call: load `roms/DISK2.rom` at `$C600`; on PROM failure print
verbose or terse stderr depending on `promFailed`, return WITHOUT mapping softswitches. On PROM
success: `b.Map(prom.Base, prom.End(), prom)` then `b.Map(0xC0E0, 0xC0EF, disk.NewSwitches(dc))`,
set `diskCardInstalled = true`, reset `promFailed = false`.

Four design points:

- **Why a closure, not a function**: it captures `b`, `dc`, `diskCardInstalled`, and `promFailed`
  without package-level state. A free function would need four-arg dispatch or global state.
- **Why one-shot guarded by `diskCardInstalled`**: idempotency. Both startup (`main.go:246`) and
  drag-drop (`main.go:755` via `installCard` parameter) reach this closure. The bool short-circuits
  subsequent calls.
- **Why PROM-first**: if `roms/DISK2.rom` is missing, the closure bails BEFORE mapping the
  softswitches at `main.go:235`. This avoids a half-installed card whose PROM region is blank but
  whose softswitches respond -- a ghost device that would crash the firmware's slot scan. Cross-cite
  `15.walkthrough_disk_controller.md` §7.
- **Why `promFailed` is a second boolean**: rate-limits stderr. First failure prints verbose "disk
  PROM: %v (card not installed)"; subsequent calls print terse "still missing -- install failed on
  prior attempt". Reset to false on success so a later failure can fire the verbose message again.

The startup gate at `main.go:245-261`: the closure fires only if `-disk1` or `-disk2` was given.
No flag -> no PROM, no slot-6 boot, Applesoft falls through to its no-disk path. Drag a `.dsk` later
to install lazily.

**Diagram D3 -- lazy installDiskCard state machine:**

```
  Closure state:  diskCardInstalled bool   promFailed bool

  First call (startup -disk1/-disk2 or drag-drop with no prior install):
      diskCardInstalled? no
           |
           v
      LoadROM "roms/DISK2.rom"
           |
           +-- FAIL --> if !promFailed:
           |                stderr "disk PROM: %v (card not installed)"
           |                promFailed = true
           |            else:
           |                stderr "still missing -- install failed on prior attempt"
           |            return  (does NOT set installed; softswitches NOT mapped)
           |
           v
      b.Map(prom.Base, prom.End(), prom)         <-- $C600-$C6FF
           |
           v
      b.Map(0xC0E0, 0xC0EF, disk.NewSwitches(dc)) <-- 16-way disk decoder
           |
           v
      diskCardInstalled = true
      promFailed = false      <-- reset: future failure will re-verbose

  Subsequent calls (startup branch 2, or second drag-drop):
      diskCardInstalled? yes -> return immediately (no-op)

  Call sites:
      (a) main.go:246  startup gate
      (b) main.go:755  handleDropFile via installCard parameter
```

### Real-World Analogy

## Section 4: The Main Loop -- Per-Frame Pipeline

### What It Is

`main.go:265-412` is the outer loop that runs every host frame. Six phases execute in fixed order.
The detailed walk of each phase is in §5 (event poll), §6 (turbo), §8 (frame cap), and §9 (title),
but the reader needs the overall pipeline picture first.

### Why It Matters

The pipeline shape determines correctness. Turbo edge detection MUST precede the CPU step so
audio-queue clearing happens before `EndFrame`. `frameCycle = 0` MUST happen before the CPU step so
the speaker's `Toggle` timestamps are frame-relative. The title update and frame cap both run AFTER
present, not before, to minimize latency between CPU action and what the user sees.

### How the Code Works

Loop preamble at `main.go:265-270`: `running := true`, `frameCount := 0`, `fpsTimer := time.Now()`.

Per-frame anchor at `main.go:271`: `frameStart := time.Now()` -- used at the bottom of the loop for
the frame-cap math.

Per-frame gate at `main.go:274-275`: `droppedThisFrame := false`. Declared INSIDE the for-running
loop, not at module scope, so it resets to false every frame. SDL's `PollEvent` drains all queued
events in one call; without the gate, a sloppy double-drop would mount twice. With the gate: one drop
per frame maximum.

`frameCycle = 0` at `main.go:361`: frame-relative cycle counter reset at the start of each CPU
step inner loop. `diskCycle += consumed` at `main.go:369`: monotonic, never reset. Cross-cite
`11.walkthrough_speaker.md` §3 and `15.walkthrough_disk_controller.md` §1.

## Section 6: F12 Turbo

### What It Is

The F12 turbo state machine spans four locations in `main.go`: the KEYDOWN/KEYUP handler call sites
in the event loop (`:310-312`, `:327`), the edge-detect block immediately after event polling
(`:354-357`), the frame-cap bypass at the bottom of the loop (`:404-411`), and the two helper
functions `handleTurboKeyDown` / `handleTurboKeyUp` at `main.go:638-652`.

### Why It Matters

Turbo changes the CPU speed from 60-frames-per-second to "as fast as the host allows". While turbo
is held, the speaker generates audio at an accelerated rate. When turbo releases, that accelerated
backlog must be discarded BEFORE the next real-speed frame is pushed, or the user hears up to one
second of fast-speed audio spool out after releasing F12. The edge-detect block is the mechanism
that makes this work.

### How the Code Works

The package-level variables at `main.go:522-527`:

```go
// turboMode is toggled by F12. While true, the frame cap is bypassed so
// the CPU emulation speed scales with host capacity. Render still happens
// every frame; frame-skip is a future tuning knob only useful if profiling
// shows render dominates host cost.
var turboMode bool
var prevTurbo bool
```

**L18-11** -- Source-comment-vs-code disagreement. The doc-comment at `main.go:522` says "toggled by
F12" but the `handleTurboKeyDown` and `handleTurboKeyUp` bodies at `main.go:638-652` do NOT toggle;
they SET:

```go
// handleTurboKeyDown / handleTurboKeyUp: F12 held = turbo on.
// Hold-to-activate (not toggle) so releasing always returns to 60 fps.
func handleTurboKeyDown(sym sdl.Keycode) bool {
    if sym == sdl.K_F12 {
        turboMode = true   // SET, not flip
        return true
    }
    return false
}
func handleTurboKeyUp(sym sdl.Keycode) {
    if sym == sdl.K_F12 {
        turboMode = false  // SET, not flip
    }
}
```

The functional behaviour is HOLD-not-toggle. The word "toggled" in the doc-comment is a copy-edit
slip; the helper-function comment at `main.go:638-639` correctly says "Hold-to-activate (not
toggle)". See also §12 Q3.

**L18-9** -- F12 is HOLD, not toggle. KEYDOWN sets `turboMode = true`; KEYUP sets `turboMode =
false`. Hold guarantees bounded duration: the user's finger has physical limits, so turbo cannot be
silently left on.

**The turbo edge-detect block** at `main.go:354-357`:

```go
// 1b. Turbo edge detect: if turbo just released, drop the queued
// fast-speed audio samples BEFORE this frame's EndFrame push, so
// the new real-speed audio frame is queued cleanly.
if prevTurbo && !turboMode {
    spk.ClearAudioQueue()
}
prevTurbo = turboMode
```

**L18-10** -- Audio queue cleared at turbo-release edge BEFORE `EndFrame`. While turbo is held, the
CPU runs uncapped: many CPU frames per host frame. `EndFrame(frameCycle)` pushes the resulting
samples to SDL's audio queue. SDL plays audio at ~44.1 kHz wall-clock regardless of how fast the
CPU produced it, so uncapped CPU produces a queue larger than one frame deep. When turbo releases,
the next normal frame's `EndFrame` would pile on top. The user would hear up to one second of
fast-speed audio spool out before normal audio resumed. `ClearAudioQueue` drops the SDL queue's
contents at the release edge, BEFORE the next `EndFrame` runs. Cross-cite
`11.walkthrough_speaker.md` §6 for the `ClearAudioQueue` docstring.

The placement in the pipeline (Phase 2, between event poll and CPU step) is mandatory: if
`ClearAudioQueue` ran AFTER `EndFrame`, it would also discard the first real-speed frame.

Frame-cap bypass at `main.go:404`: `if !turboMode { ... time.Sleep(remaining) }`. In turbo, no
sleep; the loop iterates as fast as CPU and SDL allow. Render still runs every frame.

**Diagram D6 -- F12 turbo state machine:**

```
                    turboMode     prevTurbo     audio queue   loop sleep
  STATE             (key state)   (loop state)  state         path
  ---------------   -----------   -----------   -----------   -----------
  idle              false         false         normal-rate   sleep on cap
  entering          true          false         starts fast   bypass cap
                      (KEYDOWN F12 fires; prevTurbo updates at frame end)
  holding           true          true          fast-rate     bypass cap
  releasing         false         true          fast-rate     SLEEP-CAP
                                                + queue       (after queue
                                                  cleared at  cleared)
                                                edge detect

  Transitions:

      idle  --F12 KEYDOWN-->  entering  --frame end-->  holding
       ^                                                   |
       |                                                   | F12 KEYUP
       |                                                   v
       +---frame end (queue cleared)----  releasing  <-----+
                                            |
                                            +-- focus-loss also forces this
                                                (main.go:344: turboMode=false)

  Key behaviour: every release crosses through 'releasing' for exactly one
  host frame, during which ClearAudioQueue drops the queue.
```

### Real-World Analogy

Pressing a car's overdrive-cancel pedal. Hold = bypass overdrive, run in low-gear power mode.
Release = back to overdrive. Releasing flushes the transmission's pending shift queue (the audio
queue clear) so the new gear takes immediate effect.

## Section 7: Drop-File Drive Selection

### What It Is

The drag-drop hot-swap entry point. The drag-drop handler suite at `main.go:721-788`
(`handleDropFile` at `:740-766`, `isShiftHeld` at `:773-776`, `dropDriveFromPosition` at
`:782-788`) validates the file extension, selects the target drive, lazily installs the disk card
if needed, and calls `dc.Swap`.

### Why It Matters

The mouse-x heuristic makes drag-drop reliable on macOS (where cross-app drags give SDL a stale
keyboard state snapshot). The SHIFT override covers within-app drags where keyboard focus is
reliable.

### How the Code Works

The `handleDropFile` doc-comment at `main.go:721-739` is load-bearing. Key excerpt at
`main.go:728-731`:

> Position-based selection exists because on macOS cross-app drags (e.g. Finder -> our window) the
> source app owns keyboard focus, so SDL's GetKeyboardState() returns a stale snapshot and SHIFT is
> not observable. The mouse position at drop is always accurate.

**L18-12** -- Mouse-x at drop is the primary drive selector; SHIFT held overrides to drive 2. On
macOS, dragging a `.dsk` from Finder means Finder has keyboard focus while the drag happens.
`GetKeyboardState` returns whatever was true at the last polled state (before the drag started).
Mouse position, by contrast, is always live.

Handler body at `main.go:740-766`:

```go
func handleDropFile(path string, dc *disk.Controller, installCard func()) {
    ext := strings.ToLower(filepath.Ext(path))
    switch ext {
    case ".dsk", ".do", ".po":
        // accepted
    default:
        fmt.Fprintf(os.Stderr, "disk: drop rejected -- unsupported extension %q ...\n", ext)
        return

        driveIdx = 1
    }

    if err := dc.Swap(driveIdx, path); err != nil {
        fmt.Fprintf(os.Stderr, "disk: swap into drive %d failed: %v -- drive is now empty\n", ...)
        return
    }
    fmt.Fprintf(os.Stderr, "disk: drive %d loaded %s -- press Ctrl+R to reboot\n", ...)
}
```

Extension validation only accepts `.dsk`, `.do`, `.po` (case-insensitive). The emulator
intentionally does not autodetect by content; the extension is the contract. Cross-cite
`12.walkthrough_disk_image.md` §3 for the order-inference logic inside `dc.Swap`.

`dropDriveFromPosition` at `main.go:778-788`: reads `sdl.GetMouseState()` -- the x coordinate at
drop time -- and returns 0 (drive 1) if x is in the left half of the window, else 1 (drive 2).

`isShiftHeld` at `main.go:768-776`: reads `sdl.GetKeyboardState()` for LSHIFT/RSHIFT. Reliable for

`installCard()` at `main.go:755`: the closure from §3. If no disk was mounted at startup, this is

`dc.Swap(driveIdx, path)` atomically ejects the old image BEFORE attempting to load the new one. If
the new load fails, the drive is empty (no ghost-mounted old image). Cross-cite

## Section 8: VBL-Aligned Frame Cap (the Pacing Math)

### What It Is

The frame-cap / VBL-aligned sleep at `main.go:390-411`. This is the mechanism that holds the loop at
60 fps, accounts for audio back-pressure, and explains why VSync was not used.

### Why It Matters

Under-sleeping makes the loop iterate faster than 60 Hz, which over-fills the SDL audio queue.
Over-sleeping under-runs the queue. The 100us floor prevents hot-spin in the edge case where
CPU+render finishes within microseconds of the 16.67 ms budget.

### How the Code Works

The verbatim doc-comment at `main.go:390-403`:

```
// 6. Frame cap -- bypassed in turbo.
// Frame cap -- sleep until target frame time. Uses time.Sleep for sub-ms
// precision so we don't truncate ~900us/frame.
//
// Why this matters for audio: under-sleeping makes our loop iterate faster
// than 60 Hz, which over-fills the SDL audio queue. Speaker back-pressures
// (drops frames at >4*bytesPerFrame queued, see speaker.go:191), eventually
// underrunning and emitting the warning at speaker.go:184. Sub-ms sleep
// keeps the queue near 1 frame deep.
//
// Floor at 100us avoids hot-spin when the remaining budget is near-zero
// (Go's time.Sleep guarantees AT LEAST the duration; on darwin, very
// small sleeps still take ~50us of overhead, but 0-budget skips here
// would be a tight retry loop).
```

Note: the `speaker.go:191` and `speaker.go:184` cites above are in the source comment itself. They
are the speaker package's internal line numbers for back-pressure drop and underrun warning; this doc
does not independently verify them. The outbound cross-cite is `11.walkthrough_speaker.md` §6.

**L18-13** -- Frame-cap aligns to speaker's 4-frame back-pressure drop and 1-frame underrun warning.
Sub-ms sleep keeps the queue near 1 frame deep. The quote above is the authoritative rationale.

The actual sleep code at `main.go:404-411`:

```go
if !turboMode {
    elapsed := time.Since(frameStart)
    target := time.Second / targetFPS
    remaining := target - elapsed
    if remaining > 100*time.Microsecond {
        time.Sleep(remaining)
    }
}
```

**L18-14** -- 100us sleep floor avoids hot-spin when the remaining budget is near-zero. Go's
`time.Sleep` guarantees AT LEAST the specified duration; on darwin, very small sleeps still take
~50us of overhead, but a 0-budget skip would be a tight retry loop, not a sleep.

`frameStart` at `main.go:271` is declared at the TOP of the loop body. It measures wall-clock from
the start of THIS frame's work. Jitter from long frames does not compound: if a single frame takes
50 ms (rare; typically a host context-switch), the NEXT frame's `frameStart` starts fresh after that
50 ms finishes. elapsed for the next frame measures only that frame's own CPU+render cost.

**Diagram D8 -- VBL-aligned frame-cap math:**

```
                                              16.67 ms = time.Second / 60 = target
  frame start                                                    frame end
  |                                                              |
  |--- elapsed (PHASES 1-5) ---|------ remaining (sleep) ------->|
  |                            |                                  |
  t = frameStart           t = ...                               t = frameStart + target

  if remaining > 100us:
      time.Sleep(remaining)        <-- sub-ms precision via Go scheduler
  else:
      (skip sleep; CPU+render took >= 16.57 ms; let next iteration readjust)

  Pathological cases:
    elapsed > 16.67 ms (over-budget):  remaining < 0 -> skip sleep -> loop
                                       iterates immediately. Next frame's
                                       elapsed is measured from THAT frameStart,
                                       which starts after the over-budget finishes,
                                       so jitter does NOT compound.
    elapsed = 16.66 ms (hairline):    remaining = 10us, < 100us, skip sleep.
                                       Hot spin avoided; next iteration's
                                       elapsed will absorb the missing 10us.
    elapsed = 1 ms (under-budget):    remaining = 15.67 ms, sleep 15.67 ms.
                                       Loop wakes at exactly the next frame
                                       boundary on a healthy host.

  Audio back-pressure interaction:
    under-sleep -> >60 Hz iteration -> SDL queue grows
                -> >4*bytesPerFrame -> speaker drops frame (speaker.go:191 cited
                                       in the source doc-comment)
    over-sleep  -> <60 Hz iteration -> SDL queue drains
                -> <bytesPerFrame   -> speaker logs underrun (speaker.go:184)

    Sweet spot: queue stays at ~1 frame deep.
```

### Real-World Analogy

A thermostat with a 100us deadband. The setpoint is "one frame's worth of audio in the SDL queue".
Under-sleep heats the queue (back-pressure drops frames); over-sleep cools it (underrun). The
deadband prevents hot-spin around the setpoint when CPU+render finishes within microseconds of the
target.

**L18-15** -- 1 Hz cadence is intentional. `window.SetTitle` does an SDL internal allocation every
call; doing it 60 times/second is wasteful. Once per second is the user-perception sweet spot for
FPS reporting. `frameCount` accumulates across the last second; the number passed to `buildTitle` is
the actual measured FPS for the previous second -- NOT a fixed 60.

The `buildTitle` function at `main.go:677-719` with its format-examples doc-comment at
`main.go:677-685`:

```go
// buildTitle composes the SDL window title, showing FPS plus per-drive
// activity indicators. dc may be nil if no disk image was loaded.
//
// Format examples:
//
//   Apple II Emulator -- 60 fps                         (no disks)
//   Apple II Emulator -- 60 fps -- [D1:karateka ●]       (drive 1 reading)
//   Apple II Emulator -- 60 fps -- [D1:dos33 ◉] [D2 ]   (drive 1 writing, drive 2 idle)
//   Apple II Emulator -- TURBO -- [D1:karateka ●]        (turbo engaged, drive 1 active)
```

The activity glyph at `main.go:700-704`:

```go
glyph := " "
switch {
case dc.HadRecentWrite(i):
    glyph = "◉" // write activity (higher priority than read)
case dc.HadRecentRead(i):
    glyph = "●" // read activity
}
```

The `◉` (U+25C9) and `●` (U+25CF) characters are intentional Unicode source literals used as
title-bar activity indicators. They are NOT in the standard ASCII-only rule for this doc corpus;
the ASCII-sweep allow-list for this document explicitly permits `§`, `◉`, and `●` -- and exactly
those three non-ASCII characters.

Write activity has higher priority than read (write is rarer but more user-relevant: write means
data is being committed to the disk image in RAM, which can be lost if the user quits before
the image is flushed).

The per-drive label path at `main.go:706-713`:

```go

    parts = append(parts, fmt.Sprintf("[D%d:%s %s]", i+1, label, glyph))

```

`dc.DriveLabel(i)` returns the pre-computed basename-minus-ext cached at Swap/Eject time. No
`filepath.Ext` or `filepath.Base` calls at title cadence. Cross-cite
`14.walkthrough_disk_drive.md` §6.

`truncateLabel` at `main.go:663-675` is rune-safe:

```go

    return string(runes[:maxRunes])
}
```

`labelMax = 8` runes fits "karateka" exactly (`main.go:654-656`). Multi-byte UTF-8 filenames
truncate at rune boundaries, not byte boundaries.

## Section 10: Paddle / Button / Arrow / Eject Helpers

### What It Is

Seven helper functions that map host keys onto Apple II paddle, button, and disk-eject behaviour.
These are simple per-key dispatchers; the complexity is the `-paddle` mode switch and the held-state
restoration on arrow-key release.

### Why It Matters

Arrow-key handling must be stateful (the held direction is preserved on release if the opposite is
still held). Button handling must be symmetric (KEYDOWN presses, KEYUP releases). The eject key must
not fall through to the character translator.

### How the Code Works

**`paddleArrows` mode** at `main.go:517-520`:

```go
// paddleArrows is set from the -paddle flag at startup.
// true  -> arrow keys drive the virtual paddle (default).
// false -> arrow keys emit Apple II cursor codes ($08/$15/$0B/$0A) to the keyboard latch.
var paddleArrows = true
```

When `paddleArrows = true` (default, `-paddle=arrows`): arrow keys call `sw.SetPaddle(axis, value)`
with values 0 (left/up) or 255 (right/down). When `paddleArrows = false` (`-paddle=off`): arrow keys
call `sw.PressKey` with cursor codes ($08 left, $15 right, $0B up, $0A down -- same as real IIe
hardware).

**`sdlKeyToApple` and the arrow-key non-mapping** at `main.go:441-442`:

```go
// Note: arrow keys (K_LEFT, K_RIGHT, K_UP, K_DOWN) are intentionally NOT
// mapped here -- they drive the virtual paddle via handleArrowKey* instead.
```

This comment is the guard against a future maintainer adding arrow mappings in `sdlKeyToApple` and
unknowingly breaking paddle mode.

**Held-state restoration in `handleArrowKeyUp`** at `main.go:573-612` is the trickiest exhibit:

```go
// handleArrowKeyUp maps arrow key releases to virtual paddle positions.
// If the opposite direction key is still held, that direction is maintained;
// otherwise the axis snaps back to center (128).
// No-op under -paddle=off (Apple II keyboard has no release events).
```

Inline state table:

```
  release LEFT:
      leftHeld = false
      if rightHeld: SetPaddle(0, 255)   <-- restore to right direction
      else:         SetPaddle(0, 128)   <-- snap to center

  release RIGHT:
      rightHeld = false
      if leftHeld: SetPaddle(0, 0)      <-- restore to left direction
      else:        SetPaddle(0, 128)    <-- snap to center

  (UP and DOWN are symmetric on paddle axis 1.)
```

The held flags `leftHeld`, `rightHeld`, `upHeld`, `downHeld` at `main.go:509-515` are also cleared
by the focus-loss handler (§5). This prevents the race: press LEFT, alt-tab away (KEYUP for LEFT
never arrives), alt-tab back. Without clearing, `leftHeld` would remain true indefinitely.

**`handleButtonKeyDown/Up`** at `main.go:614-636`:

```go
case sdl.K_LALT:
    sw.PressButton(0) // $C061 -- punch / fire 1 (Open-Apple)
case sdl.K_RALT:
    sw.PressButton(1) // $C062 -- kick / fire 2 (Closed-Apple)
```

LALT -> button 0 (Open-Apple, `$C061`); RALT -> button 1 (Closed-Apple, `$C062`). The mnemonics
reference Karateka's punch/kick mapping. Cross-cite `05.walkthrough_io.md` §3 for the
`PressButton`/`ReleaseButton` entry points.

**`handleDiskEjectKey`** at `main.go:790-814`: Ctrl+1 ejects drive 0, Ctrl+2 ejects drive 1.
Returns true to consume the key so the digit does not fall through to `sdlKeyToApple`. Has a
`HasDisk` guard at `main.go:806-809` that warns to stderr if the drive is already empty -- avoids
a confusing silent failure.

**`loadROM`** at `main.go:817-835`: detects ROM size via `os.Stat`, maps 12288-byte ROMs to
`$D000`, 16384-byte ROMs to `$C000`. Partial-ROM clause at `main.go:830-831`: any size in
(0, 12288] loads at `base = 0x10000 - size`, allowing minimal test ROMs smaller than 12 KB.

### Real-World Analogy

The cursor keys on an old keyboard with "key rollover". Press LEFT, then press RIGHT (without
releasing LEFT). The keyboard reports both. Release LEFT. Quality keyboards (and this handler)
restore the still-held key's direction rather than snapping to center.

## Section 11: Shutdown / Defer Stack

### What It Is

The LIFO defer stack that runs when `main()` returns. Six `defer` declarations in `main()` execute
in reverse-of-declaration order. The disk controller closes first; SDL subsystems close last.

### Why It Matters

Audio teardown must happen BEFORE the SDL renderer and window close. Disk flush must happen BEFORE
SDL so dirty tracks are written to disk even if SDL cleanup is slow. Texture/renderer/window must
close in dependency order (texture depends on renderer, renderer depends on window).

### How the Code Works

**L18-16** -- Six defers; Close order is: dc -> spk -> texture -> renderer -> window -> sdl.Quit.
`dc.Close()` (`:200`) is the last-declared defer and therefore runs first in LIFO order.

> **Source-comment-vs-code flag (second known disagreement in this corpus):** The comment at
> `main.go:183` reads `// LAST defer -> FIRST to run`. That comment was accurate when written, but
> `defer dc.Close()` was added later at `:200` without updating the comment. The comment now
> describes `:183` as "LAST" when `:200` is actually the last-declared defer. Execution order is
> determined by the declaration line numbers -- dc first, then spk -- not by what the comment says.
> This is the same shape of drift as L18-11 (`main.go:522` doc-comment vs. handler behaviour). No
> Go source edit here; the comment is a code-hygiene cleanup task for later.

**Diagram D9 -- defer-stack LIFO at normal exit:**

```
  Declaration order (as written in main()):

     :135  defer sdl.Quit()          <-- declared 1st, runs LAST
     :147  defer window.Destroy()    <-- runs 5th
     :158  defer renderer.Destroy()  <-- runs 4th
     :172  defer texture.Destroy()   <-- runs 3rd
     :183  defer spk.Close()         <-- declared 5th, runs 2nd
     :200  defer dc.Close()          <-- declared LAST, runs FIRST

  Execution order at normal exit (LIFO):

     Step 1:  dc.Close()         <-- flushAll() dirty tracks
                                     (tmp+rename per image; cross-cite 12 §6)
     Step 2:  spk.Close()        <-- audio device released
                                     (SDL pause + close)
     Step 3:  texture.Destroy()
     Step 4:  renderer.Destroy()
     Step 5:  window.Destroy()
     Step 6:  sdl.Quit()         <-- SDL subsystems released

  os.Exit(1) site         | defers registered at that point
  ----------------------- | -------------------------------------------
  :64 paddle validation   | (none)
  :84 ROM load fail       | (none)
  :130 SDL init fail      | (none)
  :145 window create fail | sdl.Quit only
  :156 renderer create    | sdl.Quit, window.Destroy
  :170 texture create     | sdl.Quit, window.Destroy, renderer.Destroy
  :251 disk1 mount fail   | all 6 (sdl.Quit .. dc.Close)
  :258 disk2 mount fail   | all 6 (same as :251)

  Note: os.Exit bypasses defer; panic does NOT (all registered defers still run).
  Mount failures use os.Exit since they are CLI configuration errors.
```

Mount failures use `os.Exit(1)` (CLI config errors; OS reclaims SDL resources; no dirty data at
those points). Panics do run all registered defers (Go's guarantee; `main.go` has no `recover()`).

### Real-World Analogy

The closing checklist on a vintage analog console. Save sessions FIRST (so dirty tracks are
committed to disk even if downstream cleanup is slow -- this is the disk flush). Then power down
speakers. Then the analog hardware in declaration order. Then the master power switch (sdl.Quit).
Reverse of the startup sequence -- which is why `defer` is the right primitive.

## Section 12: Design Q&A

**Q1: Why is `cyclesPerFrame` 17050 instead of 17030 (the real NTSC video frame)?**

Speaker math. 17050 cycles/frame yields exactly 735 samples/frame at 44100 Hz; 17030 (real NTSC:
262 x 65) drains the audio queue ~58 samples/second. Games care about CPU clock accuracy (speaker
pitch, disk nibble timing) far more than wall-clock length; the ~4.2 s/hr drift is imperceptible.
See §1, L18-1, and `11.walkthrough_speaker.md` §3.

**Q2: Why was VSync rejected in favour of `time.Sleep`?**

Non-60-Hz host displays. A 120 Hz ProMotion display would synchronize the renderer to 120 Hz while
the manual cap tries to hold 60 Hz, causing speed drift. A 59.94 Hz NTSC TV would synchronize to
59.94 Hz, slightly under-running the audio queue. Sleep-based pacing targets the wall clock
directly, adapting to whatever the host's actual refresh rate is. See §3, L18-6, and §8 for the
full audio back-pressure math.

**Q3: Why is F12 turbo HOLD, not toggle?**

Hold guarantees bounded duration. A toggle would let the user enable turbo and forget, leaving the
emulator running at uncapped CPU usage silently. Hold-to-activate means turbo lasts only as long as
the user's finger is on F12.

Note also the **source-comment-vs-code disagreement** at `main.go:522` (L18-11): the package-var
doc-comment says "toggled" but the handlers at `:640-643` / `:648-651` SET the boolean. The
helper-function comment at `:638-639` correctly says "Hold-to-activate (not toggle)". See §6.

A second disagreement exists at `main.go:183` (L18-16, §11): the inline comment "LAST defer ->
FIRST to run" became stale once `defer dc.Close()` was added at `:200`. See §11 for the flag.

**Q4: Why does `installDiskCard` use a closure rather than a method on `dc`?**

It captures `b` (the bus) and state booleans (`diskCardInstalled`, `promFailed`) without requiring
`disk.Controller` to know about its parent bus or PROM loading. If it were a method on `Controller`,
that package would need to import `bus` and `memory` -- breaking single-responsibility. See §3, L18-5.

**Q5: Why is the drop-position selector primary, with SHIFT as override?**

macOS cross-app drag keyboard-state staleness. During a cross-app drag, `sdl.GetKeyboardState()`
returns the last event-poll snapshot (stale); `sdl.GetMouseState()` is always accurate. SHIFT
override still works for within-app drags where keyboard focus is reliable. See §7, L18-12.

**Q6: How does Phase 5+ differ from Phase 4 in one sentence?**

Phase 5+ adds turbo, hot-swap drag-drop, paddle/button input, focus-loss safety, disk-activity
title bar, sub-ms frame pacing with audio back-pressure rationale, the lazy `installDiskCard`
closure, and partial-ROM detection -- all layered on the same SDL loop skeleton Phase 4 established.
See §0 timeline (D1) and `09.walkthrough_main_phase4.md` for the Phase-4 baseline.
